# Контракты

## Статус

Accepted

---

## Введение

Граница модуля определяет, какие части его реализации являются внутренними.

Однако другим частям платформы всё равно необходимо взаимодействовать с модулем.

Для этого модуль публикует контракты.

Контракт определяет стабильное соглашение между владельцем возможности и её потребителем.

Он описывает:

* что можно запросить;
* что можно выполнить;
* какие данные могут быть получены;
* какие события могут произойти;
* какие гарантии предоставляет модуль.

Контракт позволяет взаимодействовать с возможностью модуля, не зная, каким образом она реализована.

---

## Что такое контракт

Контракт представляет собой публичное архитектурное соглашение между частями системы.

Он определяет доступную снаружи семантику модуля.

```text
Потребитель
     │
     ▼
┌──────────────┐
│   Контракт   │
└──────┬───────┘
       │
       ▼
┌──────────────────────┐
│       Модуль         │
│                      │
│ Внутренняя реализация│
└──────────────────────┘
```

Потребитель зависит от контракта.

Он не зависит от внутренней реализации.

---

## Пример

Модуль видеонаблюдения позволяет получить состояние камеры.

Публичный контракт может предоставлять:

```text
CameraState
  │
  ├── Identity
  ├── Availability
  ├── Direction
  └── StreamState
```

При этом внутри модуль может использовать значительно более сложную модель:

```text
Camera Internal Model
  │
  ├── DeviceConnection
  ├── PTZController
  ├── StreamSession
  ├── RetryState
  ├── ProviderMetadata
  └── InternalDiagnostics
```

Потребителю не требуется знать о существовании этих механизмов.

---

## Контракт описывает смысл, а не реализацию

Контракт должен определять, **что означает взаимодействие**.

Он не должен заставлять потребителя знать, **как оно реализовано**.

---

## Пример

Команда:

```text
ChangeCameraDirection
```

означает:

> изменить направление обзора камеры.

Контракт не должен требовать от вызывающей стороны:

```text
SetMotorHorizontalPosition
SetMotorVerticalPosition
UpdateCameraState
SaveCameraVersion
PublishCameraEvent
```

Эти операции являются внутренними деталями Camera Module.

```text
Потребитель
     │
     ▼
ChangeCameraDirection
     │
     ▼
┌────────────────────────┐
│     Camera Module      │
│                        │
│ Motor                  │
│ Validation             │
│ State                  │
│ Version                │
│ Event                  │
└────────────────────────┘
```

Контракт выражает намерение.

Реализация остаётся внутри владельца.

---

## Виды контрактов

Архитектура допускает несколько типов публичных контрактов.

Основными являются:

* командные;
* запросные;
* событийные;
* информационные.

Каждый из них решает собственную задачу.

```text
                   Module
                     │
        ┌────────────┼────────────┐
        │            │            │
        ▼            ▼            ▼
     Commands      Queries      Events
        │            │            │
        └────────────┼────────────┘
                     ▼
               Data Contracts
```

---

## Командный контракт

Командный контракт описывает намерение изменить состояние.

Он сообщает владельцу предметной области, какое действие требуется выполнить.

---

## Пример

Транспортный модуль может предоставить команды:

```text
AssignVehicleRoute
ChangeVehicleStatus
UpdateTechnicalState
```

Модуль видеонаблюдения:

```text
ChangeCameraDirection
StartCameraStream
StopCameraStream
```

Команда не предоставляет вызывающей стороне доступ к внутренней модели.

```text
Operator
    │
    ▼
AssignVehicleRoute
    │
    ▼
Transport Module
    │
    ▼
Execution Model
```

---

## Запросный контракт

Запросный контракт позволяет получить информацию без изменения цифрового мира.

Запрос не является командой.

Он не должен запускать предметное изменение как скрытый побочный эффект.

---

## Пример

Camera Module может предоставить:

```text
GetCameraState
GetAvailableStreams
GetObservedObjects
```

```text
Consumer
   │
   ▼
Query
   │
   ▼
Projection
   │
   ▼
Result
```

Получение списка видеопотоков не должно неожиданно изменять состояние камеры.

---

## Событийный контракт

Событийный контракт описывает факт, который уже произошёл.

Модуль публикует событие, не зная всех его будущих потребителей.

---

## Пример

Transport Module публикует:

```text
VehicleEnteredZone
```

Событие могут использовать:

* Camera Module;
* Analytics Module;
* Notification Module;
* будущий модуль, которого ещё не существовало в момент создания Transport Module.

```text
                 VehicleEnteredZone
                         │
             ┌───────────┼───────────┐
             ▼           ▼           ▼
          Cameras    Analytics   Notifications
```

Издатель события не управляет реакцией потребителей.

---

## Информационный контракт

Информационный контракт определяет форму данных, которую модуль предоставляет другим частям платформы.

Это не обязательно внутренняя модель сущности.

Чаще это специально сформированное представление.

---

## Пример

Внутренний объект транспорта может содержать десятки параметров.

Для карты достаточно:

```text
VehicleMapState
  │
  ├── Identity
  ├── Position
  ├── Heading
  └── VisualStatus
```

Для аналитики:

```text
VehicleAnalyticsState
  │
  ├── Identity
  ├── Route
  ├── Distance
  ├── MovementTime
  └── TechnicalState
```

Один модуль может предоставлять несколько информационных контрактов для разных задач.

---

## Контракт не равен транспортному формату

Контракт не должен отождествляться с JSON, HTTP, WebSocket или другим способом передачи.

Например, архитектурный контракт:

```text
GetVehicleState
```

может технически использовать:

```text
In-process call
```

или:

```text
HTTP
```

или:

```text
Message Bus
```

Архитектурный смысл остаётся прежним.

```text
                 GetVehicleState
                        │
             архитектурный контракт
                        │
          ┌─────────────┼─────────────┐
          ▼             ▼             ▼
      In-process       HTTP        Messaging
```

Транспорт является реализацией контракта.

Не самим контрактом.

---

## Контракт не равен DTO

DTO может использоваться для технической передачи данных.

Но архитектурный контракт включает не только структуру данных.

Он также определяет семантику и гарантии.

---

## Пример

Структура:

```text
{
    cameraId,
    direction
}
```

сама по себе ничего не говорит о том:

* можно ли выполнить действие повторно;
* какие значения допустимы;
* что произойдёт при отсутствии камеры;
* является ли операция командой или просто сообщением;
* какие гарантии даёт владелец.

Контракт отвечает на эти вопросы на архитектурном уровне.

---

## Контракт принадлежит владельцу

Контракт должен определяться модулем, который владеет соответствующей возможностью.

Потребитель не должен диктовать внутреннюю модель поставщика.

---

## Пример

Analytics Module хочет получать данные автомобиля.

Неправильная зависимость:

```text
Analytics Module
      │
      │ требует собственную структуру
      ▼
Transport Internal Model
```

Правильная модель:

```text
Transport Module
      │
      ▼
Published Contract
      │
      ▼
Analytics Module
```

Если аналитике требуется другое представление, стороны могут определить новый публичный контракт.

Но внутреннее состояние транспорта не становится частью контракта автоматически.

---

## Контракт должен быть стабильнее реализации

Внутренняя реализация модуля должна иметь возможность изменяться чаще, чем его публичные контракты.

```text
                 Public Contract
                       │
              остаётся стабильным
                       │
          ┌────────────┴────────────┐
          ▼                         ▼
Implementation v1            Implementation v2
```

Именно это позволяет независимо развивать модули.

---

## Пример

Первоначально камера управляется напрямую через API производителя.

Позже появляется собственный сервис управления устройствами.

```text
До

Camera Contract
      │
      ▼
Provider API


После

Camera Contract
      │
      ▼
Device Service
      │
      ▼
Provider API
```

Потребители Camera Contract не должны измениться.

---

## Изменение контракта

Изменение публичного контракта является архитектурно значимым действием.

Оно потенциально затрагивает всех потребителей.

Поэтому необходимо различать совместимые и несовместимые изменения.

---

## Совместимое изменение

Совместимое изменение не требует немедленного изменения существующих потребителей.

Например, контракт может получить дополнительное необязательное поле.

```text
Version 1

CameraState
  ├── Identity
  └── Availability


Version 2

CameraState
  ├── Identity
  ├── Availability
  └── Direction
```

Если старый потребитель способен продолжить работу, изменение является совместимым.

---

## Несовместимое изменение

Несовместимое изменение меняет существующее архитектурное обещание.

Например:

```text
Было:

Direction → degrees


Стало:

Direction → normalized vector
```

Существующие потребители больше не способны правильно интерпретировать данные.

Такое изменение требует контролируемой миграции.

---

## Версионирование контрактов

Если невозможно сохранить обратную совместимость, архитектура должна позволять временно существовать нескольким версиям контракта.

```text
              Camera Module
                    │
            ┌───────┴───────┐
            ▼               ▼
       Contract v1      Contract v2
            │               │
            ▼               ▼
       Old Consumer     New Consumer
```

После миграции потребителей старая версия может быть удалена.

Версионирование не должно использоваться вместо нормального проектирования.

Оно является механизмом контролируемой эволюции.

---

## Контракты и ошибки

Ошибки также являются частью публичного соглашения.

Потребитель должен понимать возможные результаты взаимодействия.

---

## Пример

Команда:

```text
ChangeCameraDirection
```

может завершиться:

```text
Success

CameraNotFound

CameraUnavailable

DirectionNotAllowed

AccessDenied
```

Это часть семантики контракта.

Внутреннее исключение:

```text
MotorControllerTimeoutException
```

не обязано становиться частью публичного контракта.

```text
Internal Error
     │
     ▼
Camera Module
     │
     │ преобразование
     ▼
Public Contract Error
```

Внутренние детали ошибки не должны протекать через границу модуля.

---

## Контракт должен быть самодостаточным

Потребителю не должно требоваться знание внутренних правил модуля для правильного использования контракта.

Контракт должен явно определять необходимые входные данные и ожидаемые результаты.

---

## Пример

Плохой контракт:

```text
UpdateCamera(Camera camera)
```

Потребитель вынужден знать внутреннюю структуру Camera.

Более устойчивый контракт:

```text
ChangeCameraDirection
  │
  ├── CameraIdentity
  └── Direction
```

Он выражает конкретное намерение и раскрывает только необходимые данные.

---

## Контракты уменьшают связанность

Без контрактов модули начинают зависеть от внутренних моделей друг друга.

```text
Module A
   │
   ▼
Internal Model B
   │
   ▼
Database B
```

С контрактом зависимость становится контролируемой:

```text
Module A
   │
   ▼
Contract B
   │
   ▼
Module B
```

Теперь Module B способен менять собственную реализацию независимо.

---

## Контракты и Platform Core

Не каждый контракт должен принадлежать отдельному прикладному модулю.

Фундаментальные контракты цифрового мира принадлежат Platform Core.

Например:

```text
Object Identity
Relation Contract
Event Contract
State Version
```

Прикладные модули строят собственные контракты поверх этих фундаментальных понятий.

```text
              Platform Core Contracts
                       │
          ┌────────────┼────────────┐
          ▼            ▼            ▼
     Transport       Cameras     Analytics
     Contracts       Contracts    Contracts
```

---

## Практическое значение

При проектировании взаимодействия между двумя частями платформы необходимо сначала определить контракт.

Только после этого выбирается технический механизм его реализации.

Правильная последовательность:

```text
Что необходимо сделать?
          │
          ▼
Какова семантика взаимодействия?
          │
          ▼
Какой нужен контракт?
          │
          ▼
Какие гарантии он предоставляет?
          │
          ▼
Как его технически реализовать?
```

Не наоборот:

```text
Сделаем HTTP endpoint
          │
          ▼
потом решим, что он означает
```

Такой подход позволяет архитектуре не зависеть от текущего технологического стека.

---

## Проверка контракта

Перед публикацией нового контракта необходимо определить:

* кто является его владельцем;
* какое намерение или информацию он представляет;
* кому он действительно необходим;
* какие данные должны быть публичными;
* какие гарантии предоставляются;
* какие ошибки являются частью контракта;
* может ли реализация измениться без изменения контракта;
* как контракт будет эволюционировать;
* является ли взаимодействие командой, запросом или событием.

Если для использования контракта необходимо знать внутреннее устройство модуля, контракт спроектирован неправильно.

---

## Инварианты контракта

Любой публичный контракт обязан соблюдать следующие правила.

* Контракт принадлежит владельцу соответствующей архитектурной возможности.
* Контракт раскрывает семантику, но не внутреннюю реализацию.
* Потребитель зависит от контракта, а не от внутренней модели владельца.
* Команды выражают намерение изменить состояние.
* Запросы не должны скрыто изменять цифровой мир.
* События описывают уже произошедшие факты.
* Транспортный протокол не является частью архитектурного смысла контракта.
* Внутренние ошибки не должны автоматически становиться публичными.
* Контракт должен быть стабильнее его реализации.
* Несовместимые изменения требуют контролируемой эволюции.

---

## Архитектурное значение

Контракты превращают границы модулей из организационного соглашения в устойчивую архитектурную модель взаимодействия.

Они позволяют независимо изменять реализацию, технологии и способы развёртывания отдельных частей платформы, сохраняя их совместимость.

```text
Module A
   │
   ▼
Contract
   │
   ▼
Module B

      реализация B меняется

Module A
   │
   ▼
Contract
   │
   ▼
Module B'
```

Для потребителя система остаётся архитектурно той же.

---

## Заключение

Контракты определяют допустимую форму взаимодействия между частями платформы.

Однако наличие контрактов ещё не отвечает на другой важный вопрос.

Модуль может использовать десятки других возможностей платформы.

Если эти зависимости формируются бесконтрольно, система постепенно превращается в сеть связей, которую невозможно безопасно изменить.

Поэтому необходимо определить:

> В каком направлении могут существовать зависимости и кто от кого имеет право зависеть?

Ответ на этот вопрос определяет **модель зависимостей**.

Этому посвящена следующая глава.
