# Модель расширения платформы

## Статус

Accepted

---

## Введение

Платформа не может заранее знать все будущие сценарии использования.

Со временем появляются:

* новые предметные области;
* новые источники данных;
* новые способы анализа;
* новые пользовательские представления;
* новые сценарии автоматизации;
* новые интеграции.

Если каждое такое изменение требует модификации Platform Core, ядро постепенно теряет стабильность.

Поэтому архитектура должна позволять добавлять новые возможности через расширения.

Расширение — это способ добавить новую функциональность, используя существующие фундаментальные механизмы платформы.

---

## Что такое расширение

Расширение представляет собой архитектурную возможность добавить новое поведение, данные или представление без изменения фундаментальных сущностей Platform Core.

Расширение может добавлять:

* новый модуль;
* новый тип компонента;
* новый тип отношения;
* новую команду;
* новую проверку;
* новое событие;
* новую проекцию;
* новый сценарий;
* новую интеграцию.

```text
Platform Core
      │
      ├────────► Extension A
      ├────────► Extension B
      ├────────► Extension C
      └────────► Extension N
```

Core предоставляет точки расширения.

Расширения используют их.

---

## Пример

Платформа уже умеет работать с автомобилями и камерами.

Позже необходимо добавить модуль контроля доступа.

Для этого не требуется изменять Object или Relation.

Новый модуль может использовать существующие фундаментальные конструкции:

```text
Access Module
   │
   ├── AccessStateComponent
   ├── AccessGranted
   ├── AccessDenied
   ├── RequestAccess
   └── Access Projection
```

```text
Access Module
      │
      ▼
Platform Core
      │
      ├── Object
      ├── Component
      ├── Relation
      ├── Event
      └── Scenario
```

Новая предметная область появляется поверх существующего языка платформы.

---

## Расширение не изменяет фундаментальные сущности

Расширение не должно добавлять специальные условия в Core.

Недопустимо:

```text
if module == Access
    ...
```

или:

```text
if object has CameraComponent
    special core behavior
```

Если Core начинает распознавать конкретные расширения, направление зависимостей нарушается.

Правильная модель:

```text
Extension
   │
   ▼
uses Core contracts
```

а не:

```text
Core
 │
 ▼
knows Extension
```

---

## Пример

Camera Module добавляет:

```text
VideoStreamComponent
```

Platform Core не должен содержать:

```text
if component is VideoStreamComponent
```

Core знает только:

```text
Component
```

Всё предметное поведение принадлежит Camera Module.

---

## Точки расширения

Расширяемость должна быть управляемой.

Платформа не должна позволять расширению произвольно вмешиваться в любой внутренний процесс.

Для этого определяются явные точки расширения.

Например:

```text
Extension Points
   │
   ├── Components
   ├── Commands
   ├── Validators
   ├── Event Handlers
   ├── Projections
   ├── Scenarios
   └── Integration Adapters
```

Каждая точка имеет известный контракт.

---

## Пример

Если новый модуль должен реагировать на изменение положения автомобиля, он не подключается к внутреннему сервису Transport Module.

Он использует опубликованное событие:

```text
VehiclePositionChanged
        │
        ▼
Extension Handler
```

Таким образом расширение подключается в разрешённой точке.

---

## Расширение должно иметь владельца

Любое расширение принадлежит определённой архитектурной области.

Оно не должно существовать как “общий код без владельца”.

```text
Extension
   │
   ▼
Owner Module
```

Владелец отвечает за:

* семантику;
* контракт;
* жизненный цикл;
* совместимость;
* поддержку.

---

## Пример

Плагин визуализации маршрутов относится к Transport Module.

Даже если его код технически находится отдельно, архитектурный владелец остаётся определён.

```text
Transport Module
      │
      └── Route Visualization Extension
```

---

## Расширение не равно отдельному сервису

Расширение может быть:

* частью существующего процесса;
* отдельной библиотекой;
* модулем;
* отдельным сервисом;
* внешним подключаемым компонентом.

Физическая форма не определяет архитектурный смысл.

```text
Extension
   │
   ├── in-process
   ├── package
   ├── service
   └── remote integration
```

Главное — соблюдение контракта расширения.

---

## Пример

Аналитический обработчик может сначала работать внутри основного приложения:

```text
Prizma
  │
  └── Analytics Extension
```

Позже из-за нагрузки его можно вынести:

```text
Prizma
  │
  ▼
Analytics Contract
  │
  ▼
Analytics Service
```

Архитектурная роль остаётся той же.

---

## Расширение может быть обязательным или опциональным

Не все расширения одинаковы.

Некоторые являются частью стандартной поставки платформы.

Другие могут подключаться только для конкретного мира или клиента.

```text
Platform
   │
   ├── Core Modules
   │
   └── Optional Extensions
```

Опциональность не должна менять фундаментальную модель.

---

## Пример

Один мир использует:

```text
Transport
Cameras
Analytics
```

Другой:

```text
Transport
Cameras
Access Control
```

Platform Core в обоих случаях одинаков.

---

## Расширение не должно требовать fork ядра

Если для подключения новой возможности необходимо создавать отдельную версию Platform Core, модель расширения нарушена.

```text
Плохо

Core
├── Customer A version
├── Customer B version
└── Customer C version
```

Это создаёт несколько расходящихся платформ.

Правильнее:

```text
Core
 │
 ├── Extension A
 ├── Extension B
 └── Extension C
```

Один фундамент.

Разные конфигурации возможностей.

---

## Пример

Для одного предприятия требуется специфический расчёт состояния автомобиля.

Неправильно:

```text
if customer == "A"
    special calculation
```

в Platform Core.

Правильно:

```text
Customer A Extension
      │
      ▼
Transport Contract
```

Специфика остаётся снаружи ядра.

---

## Расширение должно использовать публичные контракты

Расширение не получает особых прав только потому, что оно “часть платформы”.

Оно должно соблюдать те же границы модулей.

```text
Extension
   │
   ▼
Public Contract
   │
   ▼
Module
```

Недопустимо:

```text
Extension
   │
   ▼
Module Internal State
```

---

## Пример

Аналитическое расширение использует историю движения автомобиля.

Оно не должно напрямую читать внутреннее хранилище Transport Module.

Вместо этого:

```text
Transport Events
      │
      ▼
Analytics Extension
```

или:

```text
Transport Projection
      │
      ▼
Analytics Extension
```

---

## Расширения и события

События являются одной из основных точек расширения.

Новый потребитель может подписаться на опубликованный факт, не изменяя издателя.

```text
VehicleEnteredZone
        │
        ├────────► Existing Handler
        ├────────► Existing Handler
        └────────► New Extension
```

Transport Module не требует изменений.

---

## Расширения и команды

Расширение также может публиковать собственные команды.

```text
Extension Command
      │
      ▼
Execution Model
      │
      ▼
Extension Owner
```

Они проходят тот же Execution Model, что и встроенные возможности платформы.

---

## Пример

Модуль доступа добавляет:

```text
GrantAccess
RevokeAccess
```

Эти команды проходят:

```text
Command
   │
   ▼
Validation
   │
   ▼
Transaction
   │
   ▼
State
   │
   ▼
Event
```

Новый модуль не создаёт собственный обходной механизм исполнения.

---

## Расширение и проекции

Новая возможность может добавить собственное представление существующего цифрового мира.

---

## Пример

Необходимо добавить тепловую карту перемещений автомобилей.

Для этого не требуется менять Transport Module.

```text
VehicleMovement Events
        │
        ▼
Heatmap Projection
        │
        ▼
3D / Map UI
```

Проекция является расширением чтения.

Источник истины остаётся прежним.

---

## Расширение и интеграции

Новый внешний поставщик также является формой расширения.

```text
Provider A
   │
Adapter A
   │
   ├────────► Internal Contract

Provider B
   │
Adapter B
   │
   └────────► Internal Contract
```

Добавление Provider B не должно менять Domain Model.

---

## Регистрация расширений

Платформа должна иметь явный механизм регистрации расширений.

Это не обязательно означает динамическую загрузку плагинов.

Смысл в том, что набор активных возможностей должен быть определён явно.

```text
Application Composition
        │
        ├── Core
        ├── Transport
        ├── Cameras
        ├── Analytics
        └── Access
```

Композиция приложения определяет, какие расширения активны.

---

## Пример

При запуске конкретной конфигурации:

```text
Prizma Instance
   │
   ├── Platform Core
   ├── Transport Module
   ├── Camera Module
   └── Analytics Module
```

Модуль Access Control не зарегистрирован.

Следовательно, его команды, проекции и сценарии недоступны.

---

## Расширение не должно зависеть от порядка регистрации

По возможности расширения должны быть независимыми.

Нежелательно:

```text
Register A
then B
then C
otherwise system fails
```

Если порядок имеет предметный смысл, зависимость должна быть явной.

---

## Пример

Если Analytics Extension требует Transport Module:

```text
Analytics
   │
   ▼
Transport Contract
```

эта зависимость должна быть задекларирована.

Не скрыта в порядке инициализации.

---

## Зависимости расширений

Расширения подчиняются общей модели зависимостей.

```text
Extension A
    │
    ▼
Public Contract B
    │
    ▼
Module B
```

Циклические зависимости запрещены так же, как и для обычных модулей.

---

## Пример

Недопустимо:

```text
Extension A
    │
    ▼
Extension B
    │
    ▼
Extension C
    │
    ▼
Extension A
```

Такая структура делает расширения неотделимыми друг от друга.

---

## Совместимость расширения

Расширение зависит от публичных контрактов платформы.

Если контракт меняется несовместимо, расширение может перестать работать.

Поэтому расширение должно явно определять совместимые версии контрактов.

```text
Extension
   │
   └── requires Contract >= 2 < 4
```

Конкретный механизм версионирования определяется реализацией.

Архитектурный принцип — совместимость должна быть известна заранее.

---

## Пример

Analytics Extension использует:

```text
VehicleMovementEvent v2
```

Если Transport Module публикует только несовместимый `v3`, система должна определить несовместимость при сборке или запуске, а не после случайной ошибки в runtime.

---

## Изоляция отказов расширений

Ошибка опционального расширения не должна автоматически разрушать фундаментальную платформу.

```text
Optional Extension
      X
      │
      ▼
Platform Core remains available
```

Степень изоляции зависит от типа расширения.

---

## Пример

Дополнительная аналитическая проекция перестала обновляться.

Это не должно блокировать изменение положения автомобилей.

```text
Vehicle Update     ✔
Transport State    ✔
Map Projection     ✔
Analytics Extension X
```

Деградирует аналитика.

Не основной цифровой мир.

---

## Расширение может иметь собственное состояние

Расширение может создавать собственное авторитетное состояние, если оно обладает самостоятельным предметным смыслом.

В этом случае расширение становится владельцем этого состояния.

```text
Extension
   │
   ▼
Own State
```

При этом оно всё равно не становится владельцем состояния других модулей.

---

## Пример

Analytics Module вычисляет:

```text
MovementAnomaly
```

Это самостоятельное аналитическое состояние.

```text
Transport State
      │
      ▼
Analytics
      │
      ▼
MovementAnomaly
```

Analytics владеет результатом анализа.

Transport продолжает владеть исходным состоянием автомобиля.

---

## Удаление расширения

Опциональное расширение должно иметь понятную стратегию удаления.

Необходимо определить:

* что происходит с его состоянием;
* что происходит с проекциями;
* какие контракты исчезают;
* какие зависимости становятся недоступны;
* сохраняется ли история.

---

## Пример

Удаляется Analytics Extension.

Допустимо удалить:

```text
Analytics Projections
Analytics Caches
```

Но если аналитические события уже являются частью истории:

```text
MovementAnomalyDetected
```

их нельзя переписывать только потому, что расширение больше не установлено.

История мира остаётся историей.

---

## Динамическое подключение

Архитектура может в будущем поддерживать динамическое подключение расширений.

Однако это не является обязательным свойством самой модели.

```text
Static Composition

build
  │
  ▼
extensions fixed
```

или:

```text
Dynamic Composition

runtime
  │
  ▼
load extension
```

Оба варианта могут использовать одинаковые архитектурные контракты.

---

## Практическое значение

При добавлении новой возможности необходимо определить:

> Можно ли реализовать её как расширение существующей архитектуры?

Последовательность принятия решения:

```text
Новая возможность
      │
      ▼
Можно выразить через Core?
      │
   ┌──┴──┐
   │     │
  Да    Нет
   │     │
   ▼     ▼
Module / Extension
         │
         ▼
Нужна новая фундаментальная сущность?
         │
         ▼
Architecture Review
```

Изменение Core должно быть последним вариантом.

Не первым.

---

## Проверка расширения

Перед добавлением расширения необходимо определить:

* кто является владельцем;
* какую предметную область оно добавляет;
* какие точки расширения использует;
* какие контракты публикует;
* от каких контрактов зависит;
* создаёт ли собственное состояние;
* можно ли удалить его без повреждения Core;
* как оно ведёт себя при ошибке;
* какие версии платформы поддерживает;
* не требует ли оно знания внутренних реализаций других модулей.

Если расширение невозможно реализовать без прямого доступа к внутренностям Core или чужого модуля, архитектурную границу необходимо пересмотреть.

---

## Инварианты модели расширения

Любое расширение обязано соблюдать следующие правила.

* Расширение не изменяет фундаментальную модель Platform Core.
* Core не зависит от конкретных расширений.
* Расширение подключается через явные точки расширения.
* Расширение имеет архитектурного владельца.
* Расширение использует публичные контракты других областей.
* Расширение не получает доступ к внутренней реализации модулей.
* Расширение подчиняется общему Execution Model.
* Опциональное расширение не должно без необходимости определять доступность Core.
* Совместимость расширения с контрактами платформы должна быть явной.
* Удаление расширения не переписывает историю цифрового мира.
* Специфика конкретного клиента не должна требовать fork Platform Core.

---

## Архитектурное значение

Модель расширения позволяет платформе развиваться в течение многих лет без постоянного роста ядра.

```text
                   Platform Core
                        │
             ┌──────────┼──────────┐
             ▼          ▼          ▼
          Module A   Module B   Module C
             │                     │
             ▼                     ▼
        Extension X           Extension Y
```

Фундаментальная архитектура остаётся стабильной.

Функциональность растёт вокруг неё.

Именно это позволяет «Призме» быть платформой, а не одним заранее определённым приложением.

---

## Заключение

Модель расширения определяет, как новые возможности подключаются к платформе.

Однако архитектурные модули и расширения являются логическими единицами.

Во время работы системы их необходимо физически где-то исполнять.

Несколько модулей могут находиться в одном процессе.

Другие могут быть выделены в самостоятельные сервисы.

Третьи могут масштабироваться независимо.

Возникает следующий вопрос:

> Какая часть архитектуры должна развёртываться как единое целое, а где допустимо физическое разделение?

Эту задачу определяют **единицы развёртывания**.
