# Модули

## Статус

Accepted

---

## Введение

Platform Core содержит только фундаментальные понятия цифрового мира.

Он намеренно не знает о конкретных предметных областях.

Однако реальная платформа должна работать с автомобилями, камерами, зданиями, оборудованием, документами, аналитикой и множеством других возможностей.

Для этого используются модули.

Модуль представляет собой ограниченную прикладную область, которая расширяет Platform Core, не изменяя его фундаментальных правил.

---

## Что такое модуль

Модуль — это самостоятельная архитектурная единица платформы, отвечающая за определённую область функциональности.

Модуль может определять:

* собственные компоненты;
* типы отношений;
* команды;
* проверки;
* сценарии;
* проекции;
* интеграционные контракты;
* внутренние сервисы.

При этом модуль использует фундаментальные сущности Platform Core и не создаёт альтернативную модель мира.

---

## Пример

Модуль видеонаблюдения может определять:

* `VideoStreamComponent`;
* `CameraControlComponent`;
* команду изменения направления камеры;
* проверку доступности камеры;
* проекцию списка видеопотоков;
* интеграцию с внешней системой видеонаблюдения.

```text
                 Platform Core
                       │
                       ▼
              Модуль видеонаблюдения
                       │
          ┌────────────┼────────────┐
          ▼            ▼            ▼
     Components      Commands    Projections
```

При этом Object, Event, Relation и другие фундаментальные сущности продолжают принадлежать Core.

---

## Модуль не является отдельным миром

Каждый модуль работает с одной общей моделью цифрового мира.

Он не создаёт собственные копии объектов и отношений.

Если один и тот же автомобиль используется одновременно транспортным модулем и модулем видеонаблюдения, это остаётся один объект.

---

## Пример

В цифровом мире существует автомобиль №42.

Транспортный модуль использует его компоненты движения.

Модуль видеонаблюдения связывает автомобиль с камерой.

Аналитический модуль строит статистику его перемещений.

```text
                     Object #42
                         │
         ┌───────────────┼───────────────┐
         │               │               │
         ▼               ▼               ▼
     Transport         Cameras        Analytics
      Module            Module          Module
```

Не существует:

```text
TransportVehicle #42
CameraVehicle #42
AnalyticsVehicle #42
```

Существует только один объект цифрового мира.

---

## Модуль определяет предметные компоненты

Основным способом расширения объекта являются компоненты.

Модуль может добавлять компоненты, смысл которых относится к его предметной области.

---

## Пример

Транспортный модуль может добавить:

```text
Vehicle Object
      │
      ├── PositionComponent
      ├── MovementComponent
      ├── FuelComponent
      └── TechnicalStateComponent
```

Platform Core не знает, что означают эти компоненты.

Он знает только правила существования Component.

Именно модуль определяет их предметный смысл.

---

## Модуль может определять команды

Если модуль разрешает изменять принадлежащую ему область состояния, он определяет соответствующие команды.

---

## Пример

Модуль видеонаблюдения может определить команды:

```text
ChangeCameraDirection
StartVideoStream
StopVideoStream
```

Каждая команда проходит стандартный Execution Model:

```text
Module Command
      │
      ▼
Validation
      │
      ▼
Transaction
      │
      ▼
Digital World
```

Модуль не создаёт собственный альтернативный механизм исполнения.

---

## Модуль определяет собственные проверки

Предметные правила должны находиться в том модуле, которому принадлежит соответствующая область знаний.

---

## Пример

Предположим, камера может вращаться только в определённом диапазоне.

Это не правило Platform Core.

Это правило модуля видеонаблюдения.

```text
ChangeCameraDirection
         │
         ▼
Camera Module Validation
         │
     ┌───┴───┐
     │       │
 допустимо  запрещено
```

Core при этом знает только общий механизм Validation.

---

## Модуль может создавать проекции

Модуль вправе создавать специализированные представления собственных данных.

---

## Пример

Транспортный модуль может иметь:

* список автомобилей;
* состояние движения;
* историю маршрута;
* сводку технического состояния.

Модуль видеонаблюдения:

* список камер;
* состояние потоков;
* раскладку видеостены.

```text
              Digital World
                    │
        ┌───────────┴───────────┐
        ▼                       ▼
 Transport Projections     Camera Projections
```

Обе группы проекций строятся из одной модели мира.

---

## Модуль владеет предметными правилами

Каждое предметное правило должно иметь одного владельца.

Владелец отвечает за:

* смысл правила;
* его проверки;
* изменение контракта;
* совместимость;
* связанные сценарии.

Это предотвращает ситуацию, когда одна и та же бизнес-логика распределена между несколькими модулями.

---

## Пример

Правило:

> Камера не может начать поток, если она недоступна.

принадлежит модулю видеонаблюдения.

Транспортный модуль не должен повторять эту проверку, даже если использует данные камеры.

```text
Camera Module
      │
      └── owns Camera availability rule

Transport Module
      │
      └── consumes result
```

---

## Модули должны быть независимыми

Один модуль не должен требовать знания внутренней реализации другого.

Взаимодействие происходит только через опубликованные архитектурные контракты.

---

## Пример

Транспортному модулю требуется узнать, наблюдает ли камера автомобиль.

Он не должен обращаться к внутренней таблице или внутреннему сервису модуля видеонаблюдения.

Вместо этого используется публичный контракт.

```text
Transport Module
      │
      ▼
Public Contract
      │
      ▼
Camera Module
```

---

## Модуль не должен владеть чужими данными

Если состояние относится к предметной области другого модуля, модуль не должен хранить собственную авторитетную копию этого состояния.

Он может:

* использовать проекцию;
* кэшировать данные;
* подписываться на изменения;
* хранить производное представление.

Но источник истины остаётся у владельца.

---

## Пример

Аналитическому модулю нужна информация о техническом состоянии автомобиля.

Он может хранить аналитическую проекцию:

```text
VehicleTechnicalStateProjection
```

Но не должен становиться владельцем:

```text
TechnicalStateComponent
```

```text
Transport Module
      │
      │ owns state
      ▼
TechnicalState
      │
      ▼
Synchronization
      │
      ▼
Analytics Projection
```

---

## Модуль не обязан быть отдельным сервисом

Архитектурный модуль и развёртываемый сервис — разные понятия.

Несколько модулей могут работать внутри одного процесса.

Один модуль в будущем может быть вынесен в отдельный сервис.

Это не должно менять его архитектурную ответственность.

```text
В начале

┌──────────────────────────────┐
│        Prizma Process        │
│                              │
│ Transport | Cameras | Core   │
└──────────────────────────────┘


Позже

┌───────────────┐     ┌───────────────┐
│ Transport     │     │ Cameras       │
│ Service       │     │ Service       │
└───────────────┘     └───────────────┘
         \                 /
          \               /
           ▼             ▼
             Platform Core
```

Физическое разделение не должно создавать новые логические границы задним числом.

---

## Модульный монолит

На ранних этапах платформа может развиваться как модульный монолит.

Все модули работают внутри одного приложения, но имеют явные архитектурные границы.

Это позволяет:

* проще разворачивать систему;
* выполнять локальные транзакции;
* избегать ранней операционной сложности;
* сохранять возможность будущего разделения.

---

## Пример

```text
┌─────────────────────────────────────────┐
│               Prizma                    │
│                                         │
│  ┌───────────┐  ┌───────────┐           │
│  │ Transport │  │  Cameras  │           │
│  └─────┬─────┘  └─────┬─────┘           │
│        │              │                  │
│        └──────┬───────┘                  │
│               ▼                          │
│         Platform Core                    │
└─────────────────────────────────────────┘
```

Модули находятся в одном процессе.

Но один модуль не получает право обращаться к внутренностям другого только потому, что технически это возможно.

---

## Когда модуль может стать сервисом

Выделение модуля в отдельный сервис должно происходить только при наличии измеримой причины.

Например:

* требуется независимое масштабирование;
* отличается жизненный цикл развёртывания;
* необходима изоляция отказов;
* существенно отличается нагрузка;
* существуют отдельные требования безопасности;
* необходима независимая команда разработки.

Само наличие модуля не является основанием для создания микросервиса.

---

## Пример

Видеопотоки создают значительно большую нагрузку, чем остальные части платформы.

Модуль видеонаблюдения может быть разделён:

```text
Prizma
  │
  ├────────► Core Application
  │
  └────────► Media Service
```

При этом архитектурные контракты самого Camera Module сохраняются.

Изменяется deployment topology, а не предметная модель.

---

## Расширение платформы

При добавлении новой возможности разработчик должен сначала определить:

> К какому модулю относится эта возможность?

Если подходящего модуля нет, необходимо решить:

* является ли это новой независимой областью;
* или существующий модуль просто необходимо расширить.

Новые модули не должны создаваться для каждой небольшой функции.

---

## Пример

Не следует создавать:

```text
Fuel Module
Speed Module
VehicleColor Module
VehicleRouteModule
```

Если всё это относится к одной транспортной предметной области.

Рациональнее:

```text
Transport Module
      │
      ├── Fuel
      ├── Speed
      ├── Routes
      └── Technical State
```

Модуль должен описывать связную область знаний, а не отдельное поле данных.

---

## Практическое значение

Модульность позволяет развивать «Призму» частями.

Новая команда может работать над отдельной предметной областью, не изменяя ядро и не изучая внутреннюю реализацию всей платформы.

Правильно спроектированный модуль:

* владеет собственной предметной логикой;
* имеет явные публичные контракты;
* не зависит от внутренних деталей других модулей;
* использует общую Domain Model;
* использует общий Execution Model;
* может развиваться независимо;
* может быть физически выделен при необходимости.

---

## Инварианты модуля

Любой модуль обязан соблюдать следующие правила.

* Модуль расширяет Platform Core, но не изменяет его фундаментальную модель.
* Модуль работает с общей моделью цифрового мира.
* Один реальный объект не дублируется между модулями.
* Модуль владеет собственной предметной логикой.
* Модуль не изменяет внутреннее состояние другого модуля напрямую.
* Межмодульное взаимодействие происходит только через публичные контракты.
* Модуль не должен зависеть от внутренней реализации другого модуля.
* Архитектурный модуль не обязан быть отдельным развёртываемым сервисом.
* Новый модуль создаётся для самостоятельной области знаний, а не для отдельной функции.

---

## Архитектурное значение

Модули являются основным механизмом прикладного развития «Призмы».

Platform Core сохраняет стабильность.

Модули добавляют предметную семантику.

Execution Model обеспечивает единый способ изменения цифрового мира.

Благодаря этому платформа может расширяться новыми областями, не превращая ядро в монолитную коллекцию всей существующей бизнес-логики.

---

## Заключение

Разделение системы на модули само по себе ещё не гарантирует слабую связанность.

Даже хорошо выделенные модули могут постепенно начать обращаться к внутренним данным друг друга и сформировать скрытый распределённый монолит.

Поэтому следующая задача архитектуры — определить:

> Где именно проходит граница модуля и какие взаимодействия через неё разрешены?

Этому посвящена следующая глава — **границы модулей**.
