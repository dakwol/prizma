# Границы модулей

## Статус

Accepted

---

## Введение

Разделение платформы на модули само по себе не обеспечивает модульность.

Два компонента могут находиться в разных директориях, пакетах или сервисах и при этом оставаться тесно связанными.

Настоящая модульность появляется только тогда, когда между областями существуют явные границы.

Граница модуля определяет:

* чем модуль владеет;
* что он предоставляет другим модулям;
* какие зависимости разрешены;
* какие детали остаются внутренними;
* каким образом изменения могут пересекать границу.

---

## Что такое граница модуля

Граница модуля отделяет его внутреннюю реализацию от остальной платформы.

Внутри границы модуль свободен развивать собственную предметную модель.

За пределами границы доступна только явно опубликованная часть модуля.

```text
┌─────────────────────────────────────┐
│          Transport Module           │
│                                     │
│   Internal Components               │
│   Validation Rules                  │
│   Internal Services                 │
│   Internal Projections              │
│                                     │
│          ┌──────────────┐           │
│          │ Public API   │───────────┼────► другие модули
│          └──────────────┘           │
│                                     │
└─────────────────────────────────────┘
```

Физическая доступность внутреннего кода не означает архитектурного разрешения на его использование.

---

## Пример

Модулю видеонаблюдения необходимо показать информацию об автомобиле, находящемся в зоне камеры.

Транспортный модуль уже владеет информацией об автомобиле.

Модуль видеонаблюдения не должен обращаться к внутреннему хранилищу транспортного модуля.

Вместо этого он использует опубликованный контракт.

```text
Camera Module
      │
      ▼
Transport Public Contract
      │
      ▼
Transport Module
      │
      ▼
Vehicle State
```

Внутреннее устройство Transport Module остаётся скрытым.

---

## Внутренняя и публичная части модуля

Каждый модуль логически состоит как минимум из двух областей:

```text
Module
  │
  ├── Public
  │     ├── Contracts
  │     ├── Commands
  │     ├── Events
  │     └── Queries
  │
  └── Internal
        ├── Domain Logic
        ├── Services
        ├── Persistence
        ├── Internal Models
        └── Implementation Details
```

Публичная область является архитектурным обещанием модуля.

Внутренняя область является его реализацией.

Другие модули могут зависеть только от публичной области.

---

## Публичный контракт должен быть минимальным

Модуль не должен публиковать всё своё внутреннее состояние.

Публичный контракт содержит только то, что действительно необходимо другим частям платформы.

Чем больше публичная поверхность модуля, тем сложнее изменять его внутреннюю реализацию.

---

## Пример

Транспортный модуль хранит подробное техническое состояние автомобиля:

```text
VehicleTechnicalState
  │
  ├── FuelLevel
  ├── EngineTemperature
  ├── BatteryVoltage
  ├── OilPressure
  ├── DiagnosticCodes
  └── ServiceInformation
```

Модулю карты может быть необходимо только:

```text
VehicleMapState
  │
  ├── Position
  ├── Heading
  └── Status
```

Нет необходимости раскрывать картографическому представлению всю внутреннюю модель автомобиля.

---

## Граница определяет владение

Каждое изменяемое предметное состояние должно иметь одного архитектурного владельца.

Только владелец определяет:

* структуру состояния;
* правила его изменения;
* допустимые команды;
* инварианты;
* жизненный цикл.

Другие модули могут использовать это состояние, но не становятся его совладельцами.

---

## Пример

Транспортный модуль владеет техническим состоянием автомобиля.

```text
             Transport Module
                    │
                    ▼
           TechnicalState
              OWNER
                    │
          ┌─────────┴─────────┐
          │                   │
          ▼                   ▼
    Analytics Module      UI Projection
       consumer             consumer
```

Аналитика может читать техническое состояние.

UI может его отображать.

Но изменить его можно только через контракт Transport Module.

---

## Нельзя изменять чужое состояние напрямую

Модуль не имеет права напрямую изменять состояние, принадлежащее другому модулю.

Даже если технически оба модуля используют одну базу данных или работают внутри одного процесса.

---

## Пример

Модуль аналитики обнаружил критическое техническое состояние автомобиля.

Недопустимый вариант:

```text
Analytics
    │
    ▼
UPDATE Vehicle
SET status = 'Critical'
```

Архитектурно корректный путь:

```text
Analytics Module
      │
      ▼
   Command
      │
      ▼
Transport Module
      │
      ▼
 Validation
      │
      ▼
 Execution
      │
      ▼
Vehicle State
```

Транспортный модуль сохраняет контроль над собственной моделью.

---

## Общая база данных не отменяет границы

На раннем этапе несколько модулей могут использовать одну физическую базу данных.

Это допустимо.

Однако общая технология хранения не означает общего владения данными.

```text
┌──────────────────────── Database ────────────────────────┐
│                                                         │
│  Transport Data       Camera Data       Analytics Data  │
│        ▲                   ▲                   ▲         │
└────────┼───────────────────┼───────────────────┼─────────┘
         │                   │                   │
     Transport            Cameras            Analytics
```

Каждая область данных всё равно имеет собственного владельца.

---

## Пример

Transport Module и Camera Module работают с одной PostgreSQL.

Физически Camera Module способен выполнить запрос к таблицам транспорта.

Архитектурно такой доступ запрещён.

```text
Camera Module ─────X────► Transport Tables

Camera Module ──────────► Transport Contract
                               │
                               ▼
                         Transport Module
```

Если позже транспортный модуль сменит структуру хранения, Camera Module не должен потребовать изменений.

---

## Граница должна сохраняться внутри монолита

Модульный монолит особенно легко нарушить.

Внутри одного процесса разработчик может напрямую импортировать любой класс или вызвать любой сервис.

Архитектурная граница должна существовать независимо от технической возможности её обойти.

```text
┌─────────────────────────────────────────────┐
│                  Prizma                     │
│                                             │
│  ┌──────────────┐       ┌──────────────┐    │
│  │  Transport   │       │   Cameras    │    │
│  │              │       │              │    │
│  │  Internal    │ X──── │  Internal    │    │
│  │      │       │       │      │       │    │
│  │    Public ◄──┼───────┼──────┘       │    │
│  └──────────────┘       └──────────────┘    │
│                                             │
└─────────────────────────────────────────────┘
```

Модули взаимодействуют через те же логические контракты, которые использовались бы при физическом разделении.

---

## Граница не обязана быть сетевой

Межмодульный контракт не означает обязательный HTTP-запрос или сообщение через брокер.

В модульном монолите взаимодействие может происходить обычным вызовом внутри процесса.

```text
Camera Module
      │
      │ in-process
      ▼
Transport Contract
      │
      ▼
Transport Module
```

После физического разделения реализация может измениться:

```text
Camera Service
      │
      │ network
      ▼
Transport Contract
      │
      ▼
Transport Service
```

Смысл архитектурной границы остаётся прежним.

---

## Синхронное взаимодействие

Иногда одному модулю требуется получить результат другого непосредственно во время операции.

Такое взаимодействие может быть синхронным.

---

## Пример

Оператор открывает карточку камеры.

Интерфейсу необходимо определить объект, с которым камера сейчас связана.

```text
Camera Module
      │
      ▼
Relation Query
      │
      ▼
Platform Core
      │
      ▼
Object Identity
```

Результат требуется непосредственно сейчас, поэтому синхронное взаимодействие оправдано.

---

## Асинхронное взаимодействие

Если немедленный ответ не требуется, модули должны иметь возможность взаимодействовать через события и синхронизацию.

---

## Пример

Автомобиль въехал в зону наблюдения камеры.

Transport Module завершил изменение своего состояния.

После этого опубликовано событие.

```text
Transport Module
      │
      ▼
VehicleEnteredZone
      │
      ├────────► Camera Module
      ├────────► Analytics Module
      └────────► Notification Module
```

Transport Module не обязан знать, какие модули обработают событие.

---

## Модуль не должен координировать чужую внутреннюю работу

Модуль может запросить действие другого модуля.

Но он не должен определять внутреннюю последовательность выполнения этого действия.

---

## Пример

Модулю сценариев необходимо изменить направление камеры.

Он может отправить:

```text
ChangeCameraDirection
```

Но не должен управлять внутренними шагами:

```text
Scenario Module
   │
   ├── update motor
   ├── update camera state
   ├── save camera version
   └── publish camera event
```

Эти действия принадлежат Camera Module.

Правильная граница:

```text
Scenario Module
      │
      ▼
ChangeCameraDirection
      │
      ▼
┌─────────────────────┐
│    Camera Module    │
│                     │
│ Validation          │
│ State Change        │
│ Version             │
│ Event               │
└─────────────────────┘
```

---

## Циклические зависимости запрещены

Если два модуля напрямую зависят друг от друга, их невозможно независимо изменять.

```text
Transport
    │
    ▼
Cameras
    │
    ▼
Transport
```

Такая структура означает, что архитектурная граница выбрана неправильно.

Взаимодействие необходимо перестроить через:

* события;
* общий контракт;
* Platform Core;
* отдельный координирующий модуль.

---

## Пример

Transport Module требует состояние камеры.

Camera Module одновременно требует внутреннее состояние транспорта.

Вместо взаимной зависимости:

```text
Transport ◄──────► Cameras
```

может использоваться отношение цифрового мира:

```text
Transport ─────┐
               ▼
            Relation
               ▲
Cameras ───────┘
```

Оба модуля используют фундаментальную модель Platform Core вместо зависимости друг от друга.

---

## Граница является архитектурным контрактом

Граница должна быть понятна не только из документации.

Её желательно выражать непосредственно структурой системы.

Например:

```text
modules/
  transport/
    public/
    internal/

  cameras/
    public/
    internal/
```

или эквивалентной структурой конкретной реализации.

Цель заключается не в названии директорий.

Цель — сделать неправильную зависимость заметной и, где возможно, технически невозможной.

---

## Практическое значение

При работе внутри модуля разработчик должен иметь возможность изменять его внутреннюю реализацию, не анализируя всю платформу.

Если изменение внутреннего класса транспортного модуля требует исправления Camera Module, Analytics Module и пользовательского интерфейса, граница нарушена.

Хорошая модульная граница позволяет заменить:

```text
Internal Implementation A
          │
          ▼
Internal Implementation B
```

при сохранении:

```text
Public Contract
```

без изменений для потребителей.

---

## Проверка границы

При проектировании зависимости между модулями необходимо задать несколько вопросов:

* Кто владеет этими данными?
* Кто имеет право их изменять?
* Нужен ли другому модулю весь объект или только часть информации?
* Требуется ли синхронный ответ?
* Можно ли использовать событие?
* Зависит ли потребитель от внутренней реализации?
* Сохранится ли взаимодействие, если модули окажутся в разных процессах?
* Не возникает ли циклическая зависимость?

Если ответы требуют знания внутренностей другого модуля, архитектурную границу необходимо пересмотреть.

---

## Инварианты границы модуля

Любая модульная граница обязана соблюдать следующие правила.

* Каждый модуль владеет собственной предметной областью.
* Каждое изменяемое состояние имеет одного владельца.
* Внутренняя реализация модуля недоступна другим модулям.
* Взаимодействие происходит через опубликованные контракты.
* Модуль не изменяет чужое состояние напрямую.
* Общая база данных не создаёт общего владения.
* Граница сохраняется независимо от физического способа развёртывания.
* Синхронное взаимодействие используется только там, где результат действительно необходим немедленно.
* Асинхронные события не требуют знания потребителей.
* Циклические зависимости между модулями запрещены.

---

## Архитектурное значение

Границы превращают набор функциональных областей в настоящую модульную архитектуру.

Они позволяют каждой области развиваться независимо, сохраняя при этом единый цифровой мир.

```text
┌──────────────┐
│  Transport   │
│              │
│   Internal   │
│      │       │
│    Public    │
└──────┬───────┘
       │
       │ contracts
       │
┌──────▼───────┐
│   Cameras    │
│              │
│    Public    │
│      │       │
│   Internal   │
└──────────────┘
```

Связь между модулями существует.

Зависимость от их внутреннего устройства — нет.

---

## Заключение

Граница определяет, что модуль скрывает и что он разрешает использовать остальной платформе.

Но одной границы недостаточно.

Чтобы модули действительно могли взаимодействовать независимо от внутренней реализации друг друга, необходимо точно определить форму их публичных обещаний.

Возникает следующий вопрос:

> Что именно модуль может гарантированно предоставить другим частям платформы и как это обещание должно изменяться со временем?

Ответом является **контракт**.

Этому посвящена следующая глава.
