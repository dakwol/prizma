# Модель зависимостей

## Статус

Accepted

---

## Введение

Модули разделяют платформу на предметные области.

Границы скрывают их внутреннюю реализацию.

Контракты определяют допустимые способы взаимодействия.

Однако даже при наличии этих механизмов архитектура может постепенно потерять структуру.

Причиной становятся зависимости.

Если любая часть системы может зависеть от любой другой части, со временем платформа превращается в связанный граф, в котором изменение одного компонента затрагивает множество остальных.

Модель зависимостей определяет допустимое направление связей между архитектурными областями «Призмы».

---

## Что такое зависимость

Зависимость возникает тогда, когда одна архитектурная область требует существования другой для выполнения своей задачи.

Если изменение контракта или поведения области `B` потенциально требует изменения области `A`, то `A` зависит от `B`.

```text
A
│
│ зависит от
▼
B
```

Направление стрелки показывает направление знания.

`A` знает о `B`.

`B` не обязан знать о существовании `A`.

---

## Пример

Модуль видеонаблюдения использует фундаментальную сущность `Object`.

```text
Camera Module
      │
      ▼
Object
      │
      ▼
Platform Core
```

Следовательно, Camera Module зависит от Platform Core.

Platform Core при этом ничего не знает о Camera Module.

---

## Зависимость не равна вызову

Направление выполнения операции и направление архитектурной зависимости могут различаться.

Важно не то, кто кого вызывает технически.

Важно то, кто определяет контракт.

---

## Пример

Infrastructure Layer сохраняет состояние объекта.

Во время исполнения Core может инициировать сохранение.

На уровне выполнения это выглядит так:

```text
Platform Core
      │
      │ сохранить
      ▼
Database
```

Однако фундаментальная модель не должна зависеть от конкретной базы данных.

Поэтому архитектурно используется контракт:

```text
              Platform Core
                    │
                    ▼
             Storage Contract
                    ▲
                    │
             Infrastructure
```

Infrastructure реализует контракт, определённый внутренней архитектурной областью.

Таким образом технический вызов направлен наружу, а архитектурная зависимость остаётся направленной внутрь.

---

## Основное правило зависимостей

Зависимости должны быть направлены в сторону более фундаментальных и стабильных архитектурных областей.

```text
Менее стабильное
      │
      ▼
Более стабильное
```

Для «Призмы» общая модель выглядит следующим образом:

```text
┌──────────────────────────────┐
│       Представления         │
└──────────────┬───────────────┘
               │
               ▼
┌──────────────────────────────┐
│          Модули             │
└──────────────┬───────────────┘
               │
               ▼
┌──────────────────────────────┐
│      Execution Model        │
└──────────────┬───────────────┘
               │
               ▼
┌──────────────────────────────┐
│       Platform Core         │
└──────────────────────────────┘
```

Чем ниже область находится на схеме, тем меньше причин у неё знать о расположенных выше областях.

---

## Platform Core является центром зависимостей

Platform Core содержит наиболее фундаментальные и стабильные концепции платформы.

Поэтому другие архитектурные области могут зависеть от Core.

Core не должен зависеть от них.

```text
       Transport
           │
           ▼
Cameras ─► Core ◄─ Analytics
           ▲
           │
        Scenarios
```

Core является фундаментом.

Он не становится координатором всех модулей.

---

## Пример

Transport Module использует:

* Object;
* Component;
* Relation;
* State;
* Event.

Camera Module использует те же фундаментальные сущности.

```text
Transport ─────┐
               │
               ▼
          Platform Core
               ▲
               │
Cameras ───────┘
```

При этом Platform Core не содержит:

```text
if module == Transport

if module == Cameras
```

Появление нового модуля не должно требовать изменения ядра.

---

## Модули зависят от Core

Предметные модули строятся поверх фундаментальной модели.

Они могут использовать Core для определения собственных сущностей и правил.

```text
Transport Module
      │
      ├── Vehicle Components
      ├── Vehicle Commands
      └── Vehicle Rules
              │
              ▼
        Platform Core
```

Core предоставляет язык.

Модуль использует этот язык для описания предметной области.

---

## Core не зависит от модулей

Обратная зависимость запрещена.

Недопустимо:

```text
Platform Core
      │
      ▼
Transport Module
```

Если Core необходимо знать о конкретном модуле, фундаментальная модель перестаёт быть универсальной.

---

## Пример

Неправильное решение:

```text
Object
  │
  └── if objectType == Vehicle
          calculateFuel()
```

Правильная модель:

```text
Object
  │
  ▼
Component
  │
  ▼
FuelComponent
  │
  ▼
Transport Module
```

Core предоставляет механизм компонентов.

Транспортный модуль определяет их предметный смысл.

---

## Execution Model зависит от фундаментальных правил

Execution Model работает с цифровым миром и поэтому использует понятия Core:

* State;
* Version;
* Invariant;
* Constraint;
* Consistency.

```text
Execution Model
      │
      ▼
Platform Core
```

При этом Core не должен знать, каким способом организовано выполнение команд.

Domain Model способна существовать независимо от конкретной модели исполнения.

---

## Модули используют Execution Model

Предметные модули определяют команды и проверки, но не создают собственный механизм изменения мира.

```text
Transport Command
        │
        ▼
Execution Model
        │
        ▼
Platform Core
```

То же правило действует для всех модулей.

```text
Camera Command
        │
        ▼
Execution Model
        │
        ▼
Platform Core
```

Это обеспечивает единый жизненный цикл изменений во всей платформе.

---

## Представления зависят от публичных контрактов

Пользовательские интерфейсы должны зависеть от опубликованных возможностей платформы.

Они не должны зависеть от внутренних предметных моделей.

```text
3D Scene
   │
   ▼
Projection Contract
   │
   ▼
Platform
```

То же относится к карте:

```text
Map
 │
 ▼
Map Projection
 │
 ▼
Platform
```

UI является потребителем платформы.

Он не становится частью её Domain Model.

---

## Пример

Для отображения автомобиля карте необходимы:

```text
VehicleMapState
  │
  ├── Identity
  ├── Position
  ├── Heading
  └── VisualState
```

Карта не должна импортировать:

```text
VehicleAggregate
VehicleRepository
FuelCalculationService
TransportValidationService
```

Эти сущности принадлежат внутренней реализации Transport Module.

---

## Инфраструктура находится снаружи

Базы данных, брокеры сообщений, сетевые клиенты и файловые системы являются техническими механизмами.

Они должны адаптироваться к архитектуре платформы.

Не наоборот.

```text
┌─────────────────────────────────────┐
│           Infrastructure            │
│                                     │
│ Database  Messaging  Network  Files │
└──────────────────┬──────────────────┘
                   │
                   ▼
             Contracts
                   │
                   ▼
           Platform Logic
```

---

## Инверсия зависимости

Иногда внутренняя область должна использовать внешнюю техническую возможность.

Например, сохранять состояние.

Если Core напрямую зависит от конкретного механизма хранения:

```text
Platform Core
      │
      ▼
PostgreSQL
```

архитектурная граница нарушается.

Вместо этого внутренняя область определяет необходимый контракт:

```text
Platform Core
      │
      ▼
State Repository Contract
      ▲
      │
PostgreSQL Adapter
```

Теперь направление архитектурной зависимости сохранено.

---

## Пример

Сегодня состояние хранится в PostgreSQL.

```text
PostgreSQL Adapter
       │
       ▼
Storage Contract
       │
       ▼
Platform
```

Позже часть состояния переносится в другое хранилище.

```text
New Storage Adapter
       │
       ▼
Storage Contract
       │
       ▼
Platform
```

Domain Model и Execution Model не требуют изменений.

---

## Межмодульные зависимости

Самая опасная область архитектуры — зависимости между прикладными модулями.

Прямая зависимость допустима только через публичный контракт владельца.

```text
Module A
   │
   ▼
Public Contract B
   │
   ▼
Module B
```

Однако большое количество таких зависимостей постепенно создаёт связанный граф.

```text
A ─────► B
│       ▲
│       │
▼       │
C ─────► D
▲       │
└───────┘
```

Такой граф становится сложно изменять.

Поэтому прямая межмодульная зависимость должна использоваться осознанно.

---

## Предпочтение слабой связанности

Если одному модулю не требуется немедленный результат другого, предпочтительно использовать событие.

```text
Сильнее связаны

Module A
   │
   ▼
Module B


Слабее связаны

Module A
   │
   ▼
Event
   │
   ├────────► Module B
   └────────► Module C
```

Издатель события не зависит от количества и состава потребителей.

---

## Пример

Transport Module фиксирует въезд автомобиля на территорию.

Ему не требуется знать, что после этого:

* Camera Module начинает наблюдение;
* Analytics Module фиксирует поездку;
* Notification Module отправляет сообщение.

```text
Transport
    │
    ▼
VehicleEnteredTerritory
    │
    ├────────► Cameras
    ├────────► Analytics
    └────────► Notifications
```

Transport Module сообщает факт.

Другие области самостоятельно решают, как на него реагировать.

---

## Оркестрация не должна создавать скрытые зависимости

Иногда бизнес-процесс действительно требует последовательного взаимодействия нескольких модулей.

Такую координацию не следует помещать внутрь одного из участвующих модулей.

---

## Пример

Сценарий въезда автомобиля может потребовать:

1. зарегистрировать въезд;
2. активировать наблюдение камеры;
3. открыть доступ к зоне;
4. отправить уведомление.

Плохая архитектура:

```text
Transport Module
    │
    ├── Camera Module
    ├── Access Module
    └── Notification Module
```

Transport Module превращается в координатор всей платформы.

Более устойчивый вариант:

```text
              Scenario
                 │
       ┌─────────┼─────────┐
       ▼         ▼         ▼
   Transport   Cameras    Access
       │
       └──────────────► Notifications
```

Координация принадлежит отдельному сценарию.

Предметные модули сохраняют собственную ответственность.

---

## Циклические зависимости запрещены

Граф архитектурных зависимостей должен оставаться ацикличным.

Недопустимо:

```text
Transport
    │
    ▼
Cameras
    │
    ▼
Analytics
    │
    ▼
Transport
```

Такой цикл означает, что ни один модуль невозможно независимо изменить.

---

## Разрешение цикла

При обнаружении цикла необходимо определить причину зависимости.

Обычно решение заключается в одном из вариантов:

* вынести общий фундаментальный контракт;
* использовать событие;
* использовать Relation из Platform Core;
* создать отдельный координирующий сценарий;
* пересмотреть границы модулей.

---

## Пример

Camera Module должен знать положение автомобиля.

Transport Module должен знать, наблюдается ли автомобиль камерой.

Наивная модель:

```text
Transport ◄──────► Cameras
```

Можно разделить ответственности:

```text
Transport
    │
    ▼
VehiclePosition
    │
    ▼
Projection
    │
    ▼
Cameras
```

А информацию о наблюдении представить через отношение:

```text
Camera
   │
   ▼
observes
   │
   ▼
Vehicle
```

Оба модуля используют общую модель мира вместо взаимного знания внутренних реализаций.

---

## Стабильность зависимостей

Зависимость предпочтительно направлять к области, которая изменяется реже.

```text
Часто изменяется
      │
      ▼
Редко изменяется
```

Например:

```text
UI
 │
 ▼
Module Contract
 │
 ▼
Platform Core
```

UI может изменяться ежедневно.

Предметный контракт — значительно реже.

Фундаментальные концепции Core — ещё реже.

Такое направление уменьшает влияние изменений.

---

## Зависимость должна быть минимальной

Даже разрешённая зависимость не означает, что потребителю необходимо знать весь публичный API поставщика.

Он должен зависеть только от минимального необходимого контракта.

---

## Пример

Analytics Module необходим только поток событий перемещения автомобиля.

Нет необходимости зависеть от всего Transport Module.

```text
Плохо

Analytics
   │
   ▼
Entire Transport API


Лучше

Analytics
   │
   ▼
VehicleMovement Events
```

Чем меньше поверхность зависимости, тем меньше связанность.

---

## Архитектурный граф

На высоком уровне граф зависимостей «Призмы» должен выглядеть направленным к центру архитектуры.

```text
                  ┌───────────────┐
                  │      UI       │
                  └───────┬───────┘
                          │
                          ▼
             ┌────────────────────────┐
             │    Module Contracts    │
             └────────────┬───────────┘
                          │
              ┌───────────┼───────────┐
              ▼           ▼           ▼
          Transport    Cameras    Analytics
              │           │           │
              └───────────┼───────────┘
                          ▼
                 Execution Model
                          │
                          ▼
                   Platform Core

Infrastructure
      │
      └────────────► архитектурные контракты
```

Это не схема физического развёртывания.

Это схема **архитектурного знания**.

---

## Практическое значение

При добавлении новой зависимости разработчик должен задавать не вопрос:

> Как мне получить этот класс или сервис?

А сначала:

> Почему моя область вообще должна знать об этой области?

После этого необходимо определить:

* кто владеет требуемой возможностью;
* существует ли публичный контракт;
* нужен ли синхронный ответ;
* можно ли использовать событие;
* не появляется ли цикл;
* можно ли уменьшить поверхность зависимости;
* направлена ли зависимость к более стабильной области.

Только после этого выбирается технический механизм.

---

## Проверка зависимости

Перед созданием новой архитектурной зависимости необходимо проверить:

```text
Нужны данные другого модуля?
        │
        ▼
Кто ими владеет?
        │
        ▼
Есть публичный контракт?
        │
     ┌──┴──┐
     │     │
    Да    Нет
     │     │
     │     └────► определить контракт
     ▼
Нужен результат немедленно?
        │
     ┌──┴──┐
     │     │
    Да    Нет
     │     │
     ▼     ▼
   Query  Event / Projection
     │     │
     └──┬──┘
        ▼
Проверить отсутствие цикла
```

Такой процесс позволяет контролировать рост связности системы.

---

## Инварианты модели зависимостей

Архитектурные зависимости обязаны соблюдать следующие правила.

* Зависимости направляются к более фундаментальным и стабильным областям.
* Platform Core не зависит от прикладных модулей.
* Platform Core не зависит от инфраструктуры.
* Модули используют единый Execution Model.
* Представления зависят только от публичных контрактов и проекций.
* Внутренние модели модулей не являются допустимыми зависимостями.
* Межмодульные зависимости проходят через публичные контракты.
* При отсутствии необходимости в немедленном ответе предпочтительно асинхронное взаимодействие.
* Циклические архитектурные зависимости запрещены.
* Инфраструктура адаптируется к архитектурным контрактам.
* Любая зависимость должна иметь минимально необходимую поверхность.

---

## Архитектурное значение

Модель зависимостей сохраняет направление развития платформы.

Без неё даже правильно разделённые модули со временем начинают знать слишком много друг о друге.

Контролируемый граф зависимостей позволяет изменять внешние и прикладные части системы, не разрушая фундаментальные области.

```text
Изменяемые части
       │
       ▼
Стабильные контракты
       │
       ▼
Фундаментальная модель
```

Чем ближе область находится к центру архитектуры, тем меньше зависимостей она должна иметь.

---

## Заключение

Модель зависимостей определяет, **кто имеет право знать о ком**.

Но архитектурная зависимость сама по себе ещё не определяет, **как именно две разрешённые области взаимодействуют во время работы системы**.

Одним взаимодействиям требуется немедленный ответ.

Другие представляют собой уведомление о произошедшем факте.

Некоторые проходят внутри одного процесса.

Другие пересекают сеть.

Поэтому следующим шагом необходимо определить:

> Какие модели коммуникации допускает платформа и когда должна использоваться каждая из них?

Этому посвящена следующая глава — **Коммуникация**.
