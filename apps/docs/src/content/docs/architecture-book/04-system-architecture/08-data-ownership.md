# Владение данными

## Статус

Accepted

---

## Введение

Платформа может состоять из множества модулей, проекций, сервисов и пользовательских представлений.

Одна и та же информация может использоваться сразу в нескольких местах.

Однако использование данных не означает владение ими.

Если несколько частей платформы одновременно считают одно и то же состояние своим, постепенно появляются:

* конкурирующие источники истины;
* несогласованные копии;
* прямые изменения чужих данных;
* дублирование предметных правил;
* неопределённость ответственности.

Поэтому архитектура должна явно определять владельца каждого изменяемого состояния.

---

## Что такое владение данными

Владение данными означает архитектурную ответственность за смысл и изменение состояния.

Владелец определяет:

* структуру состояния;
* допустимые изменения;
* команды;
* проверки;
* инварианты;
* жизненный цикл;
* публичные контракты.

```text id="su1d5c"
              State
                │
                ▼
          Owner Module
                │
        ┌───────┼───────┐
        ▼       ▼       ▼
     Rules   Commands  Events
```

Другие части платформы могут использовать это состояние.

Но они не становятся его владельцами.

---

## Пример

Транспортный модуль владеет техническим состоянием автомобиля.

```text id="p5x260"
VehicleTechnicalState
        │
        ▼
 Transport Module
        │
        ├── FuelLevel
        ├── Mileage
        ├── TechnicalStatus
        └── ServiceState
```

Модуль аналитики может использовать эти данные для расчётов.

Интерфейс может их отображать.

Модуль уведомлений может реагировать на изменения.

Но только Transport Module определяет, как техническое состояние автомобиля изменяется.

---

## Один источник истины

Для каждого авторитетного состояния должен существовать один логический источник истины.

Это не обязательно означает одну физическую копию данных.

Репликация может создавать множество технических копий.

Проекции могут создавать множество представлений.

Однако архитектурный владелец остаётся один.

```text id="v7w1rp"
                Owner
                  │
                  ▼
           Authoritative State
                  │
        ┌─────────┼─────────┐
        ▼         ▼         ▼
   Projection   Replica   Cache
```

Копий может быть много.

Источников смысла — один.

---

## Пример

Положение автомобиля используется:

* картой;
* аналитикой;
* мобильным приложением;
* историей движения.

```text id="yy5hca"
               Transport Module
                     │
                     ▼
              Vehicle Position
                     │
          ┌──────────┼──────────┐
          ▼          ▼          ▼
        Map      Analytics    Mobile
```

Карта не становится владельцем координат только потому, что отображает их.

---

## Владение не определяется местом хранения

Физическое расположение данных не определяет архитектурного владельца.

Данные могут храниться:

* в общей базе;
* в отдельном хранилище;
* в распределённой системе;
* в нескольких репликах.

Ответственность при этом остаётся у одного модуля.

---

## Пример

Transport Module и Camera Module используют одну базу данных.

```text id="8muucg"
┌──────────────────────────────┐
│           Database           │
│                              │
│ VehicleState   CameraState   │
└───────▲────────────▲─────────┘
        │            │
        │            │
   Transport       Cameras
```

Наличие общей базы не означает:

```text id="brgahy"
Transport owns CameraState
```

или:

```text id="xy44qp"
Cameras own VehicleState
```

Владение определяется архитектурной ответственностью, а не SQL-схемой.

---

## Только владелец изменяет состояние

Изменение авторитетного состояния должно происходить через владельца.

Другие модули не должны изменять его напрямую.

```text id="8pxhpo"
Consumer Module
       │
       ▼
     Command
       │
       ▼
   Owner Module
       │
       ▼
     State
```

---

## Пример

Analytics Module определил, что автомобиль требует обслуживания.

Неправильно:

```text id="qy0mua"
Analytics
   │
   ▼
VehicleTechnicalState.status = ServiceRequired
```

Правильно:

```text id="c8hu23"
Analytics
   │
   ▼
RequestVehicleServiceStateChange
   │
   ▼
Transport Module
   │
   ▼
Validation
   │
   ▼
VehicleTechnicalState
```

Transport Module может:

* принять изменение;
* отклонить его;
* выполнить дополнительные проверки;
* создать другую предметную реакцию.

Владелец сохраняет контроль над состоянием.

---

## Потребление не создаёт владение

Модуль может активно использовать данные другого модуля и при этом оставаться только потребителем.

---

## Пример

Camera Module использует координаты автомобиля, чтобы определить его присутствие в зоне наблюдения.

```text id="lpk0nr"
Transport Module
      │
      ▼
VehiclePosition
      │
      ▼
Synchronization
      │
      ▼
Camera Module
```

Camera Module может построить собственную локальную проекцию положения.

Но эта проекция не становится новым авторитетным источником координат.

---

## Производные данные могут иметь другого владельца

Данные, вычисленные на основе чужого состояния, могут принадлежать другому модулю, если они представляют новую предметную информацию.

---

## Пример

Transport Module владеет маршрутами автомобиля.

Analytics Module вычисляет:

```text id="hfwo2a"
AverageTravelTime
RouteEfficiency
MovementAnomalyScore
```

Эти данные являются производными.

```text id="lsq6xr"
Transport State
      │
      ▼
Analytics Calculation
      │
      ▼
Analytics State
```

Transport Module не обязан становиться владельцем результатов аналитики.

Возникла новая область смысла.

Следовательно, появился новый владелец.

---

## Дублирование состояния

Иногда потребителю требуется локальная копия данных для производительности или автономной работы.

Это допустимо.

Но такая копия должна явно считаться:

* проекцией;
* кэшем;
* репликой;
* производным состоянием.

Она не должна незаметно превращаться во второй источник истины.

---

## Пример

Camera Module хранит локальную проекцию:

```text id="i7cjlu"
ObservedVehicle
  │
  ├── VehicleIdentity
  ├── Position
  └── Heading
```

Авторитетное положение автомобиля остаётся в Transport Module.

```text id="ezi7vu"
Transport
   │
   ▼
Authoritative Position
   │
   ▼
Synchronization
   │
   ▼
Camera Projection
```

Если значения различаются, локальная проекция должна быть восстановлена из авторитетного источника.

---

## Кэш не является владельцем

Кэш существует для ускорения доступа.

Потеря кэша не должна приводить к потере предметной информации.

```text id="wmbwd6"
Owner State
    │
    ▼
   Cache
    │
   lost
    X
    │
    ▼
rebuild
```

Если данные невозможно восстановить после потери кэша, это уже не просто кэш.

---

## Проекция не является владельцем

Проекция также не владеет отображаемым состоянием.

Она может быть полностью пересоздана.

---

## Пример

Картографическая проекция потеряла все объекты после сбоя.

```text id="7fbf4r"
Map Projection
      X
```

Она восстанавливается:

```text id="pecda1"
Digital World
      │
      ▼
Projection Build
      │
      ▼
Map Projection
```

Domain Model при этом не изменяется.

---

## Реплика не создаёт нового владельца

Реплика хранит копию авторитетного состояния.

Она может физически принимать запросы и участвовать в распределённом исполнении.

Но правила определения итогового состояния должны оставаться едиными.

```text id="rirvrt"
             Logical Owner
                  │
        ┌─────────┼─────────┐
        ▼         ▼         ▼
    Replica A Replica B Replica C
```

Архитектурное владение не размножается вместе с физическими копиями.

---

## Владение отношениями

Отношения являются самостоятельными сущностями цифрового мира.

Поэтому необходимо отдельно определять владельца их предметной семантики.

---

## Пример

Существует отношение:

```text id="yuqgbl"
Camera
  │
  └── observes ──► Vehicle
```

Сам механизм Relation принадлежит Platform Core.

Но семантика:

```text id="dpny9n"
observes
```

может принадлежать Camera Module.

```text id="5e3dy5"
Platform Core
      │
      └── Relation mechanism

Camera Module
      │
      └── observes relation semantics
```

Core знает, как существует отношение.

Модуль знает, что оно означает.

---

## Владение компонентами

Тип компонента принадлежит модулю, который определяет его предметный смысл.

---

## Пример

```text id="awyx8s"
FuelComponent
```

принадлежит Transport Module.

```text id="y3k06p"
VideoStreamComponent
```

принадлежит Camera Module.

```text id="yxg103"
Identity
Object
Component mechanism
```

принадлежат Platform Core.

Так сохраняется разделение между фундаментальным механизмом и предметной семантикой.

---

## Владение командами

Команда принадлежит области, которая способна выполнить соответствующее изменение.

---

## Пример

```text id="u38u7p"
ChangeCameraDirection
```

принадлежит Camera Module.

```text id="44wz5h"
AssignVehicleRoute
```

принадлежит Transport Module.

Потребитель может отправить команду.

Но только владелец определяет её исполнение.

---

## Владение событиями

Событийный контракт должен публиковаться владельцем факта.

---

## Пример

```text id="stt9x5"
VehicleRouteAssigned
```

публикует Transport Module.

```text id="pvc35m"
CameraStreamStarted
```

публикует Camera Module.

Потребители не должны самостоятельно создавать чужие предметные события.

---

## Неправильное совместное владение

Особенно опасна модель, где несколько модулей напрямую меняют одну сущность.

```text id="pq6d7k"
             VehicleState
            ▲      ▲      ▲
            │      │      │
       Transport Cameras Analytics
```

Возникают вопросы:

* чьи инварианты главнее;
* кто создаёт версию;
* кто публикует событие;
* кто разрешает конфликт;
* кто отвечает за неправильное состояние.

Такая модель не имеет однозначной ответственности.

---

## Правильное распределение ответственности

Вместо совместного владения состояние разделяется по смысловым областям.

```text id="zi8bpa"
Vehicle Object
      │
      ├── Transport State
      │       │
      │       └── owner: Transport
      │
      ├── Observation Relations
      │       │
      │       └── owner: Cameras
      │
      └── Analytics State
              │
              └── owner: Analytics
```

Объект остаётся один.

Предметное состояние имеет явных владельцев.

---

## Владение не означает изоляцию

Владелец состояния не должен скрывать его от всей платформы.

Он должен предоставлять необходимые публичные контракты.

```text id="lbhrhf"
Owner
  │
  ├────────► Queries
  ├────────► Projections
  ├────────► Events
  └────────► Commands
```

Владение отвечает за контроль изменений.

Не за запрет доступа.

---

## Пример

Transport Module владеет положением автомобиля.

Но карта должна видеть координаты.

Analytics Module должен получать историю.

Camera Module может использовать положение для пространственных вычислений.

Поэтому владелец публикует необходимые представления и события.

```text id="r6xn4a"
             Transport
                 │
       ┌─────────┼─────────┐
       ▼         ▼         ▼
      Map    Analytics   Cameras
```

Открытое чтение не означает открытое изменение.

---

## Передача владения

В редких случаях архитектурная ответственность может быть передана другому модулю.

Это является значимым изменением архитектуры.

Передача требует:

* определения нового владельца;
* миграции состояния;
* миграции контрактов;
* обновления зависимостей;
* сохранения истории;
* исключения периода двойного владения.

---

## Пример

Допустим, техническое состояние автомобилей первоначально находилось внутри Transport Module.

Позже появляется отдельная полноценная область обслуживания оборудования.

```text id="g9d1ob"
До

Transport
   │
   └── TechnicalState


После

Maintenance
   │
   └── TechnicalState
```

Это не простой перенос таблицы.

Меняется архитектурный владелец предметной области.

Следовательно, необходимо пересмотреть команды, события, инварианты и публичные контракты.

---

## Владение должно быть очевидным

Разработчик должен иметь возможность быстро определить владельца данных.

Недопустима ситуация, когда ответ звучит:

> Вроде транспорт, но камера тоже записывает, а аналитика иногда обновляет.

Такое состояние является архитектурным долгом.

---

## Пример структуры

Архитектурное владение может отражаться непосредственно структурой проекта.

```text id="luzgl9"
modules/
  transport/
    model/
    commands/
    events/
    contracts/

  cameras/
    model/
    commands/
    events/
    contracts/

  analytics/
    model/
    projections/
    contracts/
```

Это не обязательная физическая структура.

Но организация кода должна помогать увидеть ответственность.

---

## Практическое значение

Перед созданием нового состояния необходимо определить:

> Кто им владеет?

Перед использованием существующего состояния:

> Кто является его владельцем?

Перед изменением:

> Через какой контракт владельца должно пройти изменение?

Если на эти вопросы нет однозначного ответа, дальнейшая реализация должна быть остановлена до определения ответственности.

Полезная схема принятия решения:

```text id="fe636e"
Нужно новое состояние
        │
        ▼
Какой у него предметный смысл?
        │
        ▼
Какому модулю он принадлежит?
        │
     ┌──┴──┐
     │     │
 найден   нет
     │     │
     │     ▼
     │  новая область?
     │     │
     ▼     ▼
 Owner   пересмотреть
         границы модулей
```

---

## Инварианты владения данными

Архитектура владения обязана соблюдать следующие правила.

* Каждое авторитетное изменяемое состояние имеет одного логического владельца.
* Использование данных не создаёт владение.
* Место физического хранения не определяет владельца.
* Только владелец определяет правила изменения собственного состояния.
* Другие модули изменяют состояние через контракт владельца.
* Проекции, кэши и реплики не становятся новыми источниками истины.
* Производные данные могут иметь отдельного владельца, если обладают самостоятельным предметным смыслом.
* Типы предметных компонентов принадлежат определяющим их модулям.
* Предметные команды и события принадлежат владельцу соответствующей области.
* Двойное авторитетное владение одним состоянием запрещено.
* Передача владения является отдельным архитектурным изменением.

---

## Архитектурное значение

Владение данными устанавливает однозначную ответственность за цифровой мир.

Оно позволяет определить:

* кто имеет право изменить состояние;
* кто отвечает за его корректность;
* где находятся предметные правила;
* откуда получать авторитетную информацию;
* каким способом восстанавливать производные копии.

```text id="87sglp"
              Digital World
                    │
       ┌────────────┼────────────┐
       ▼            ▼            ▼
  Transport      Cameras      Analytics
     owns          owns          owns
      │             │             │
      ▼             ▼             ▼
Vehicle State  Camera State  Analytics State
```

Мир остаётся единым.

Ответственность внутри него распределена явно.

---

## Заключение

Владение данными определяет, какая часть платформы является авторитетным источником конкретного состояния.

Но значительная часть информации попадает в «Призму» не из её собственных модулей.

Координаты могут приходить от внешнего оборудования.

Видеопотоки — от сторонних систем.

Документы — из корпоративных сервисов.

Внешний мир использует собственные идентификаторы, форматы, протоколы и правила.

Эти особенности не должны проникать в фундаментальную модель платформы.

Поэтому возникает следующий вопрос:

> Где заканчивается архитектура «Призмы» и начинается модель внешней системы?

Эту границу определяет **интеграционный слой**.
