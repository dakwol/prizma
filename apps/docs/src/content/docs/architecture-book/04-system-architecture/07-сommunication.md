# Коммуникация

## Статус

Accepted

---

## Введение

Модель зависимостей определяет, какие части платформы имеют право знать друг о друге.

Контракты определяют, что именно они могут друг другу предоставить.

Однако во время работы системы эти части должны обмениваться командами, запросами, событиями и данными.

Этот обмен называется коммуникацией.

Коммуникация определяет способ взаимодействия архитектурных областей во времени.

Она отвечает на вопросы:

* требуется ли немедленный ответ;
* может ли взаимодействие быть отложено;
* является ли сообщение командой, запросом или событием;
* что происходит при недоступности получателя;
* какие гарантии доставки необходимы;
* должен ли отправитель знать получателя.

---

## Коммуникация начинается с семантики

Выбор коммуникации начинается не с технологии.

Сначала необходимо определить смысл взаимодействия.

```text
Что происходит?
      │
      ▼
Команда, запрос или событие?
      │
      ▼
Нужен немедленный результат?
      │
      ▼
Синхронно или асинхронно?
      │
      ▼
Какие нужны гарантии?
      │
      ▼
Технический транспорт
```

HTTP, WebSocket, брокер сообщений или обычный вызов функции выбираются только после определения архитектурной семантики.

---

## Пример

Оператор хочет изменить направление камеры.

Смысл взаимодействия:

> Выполнить конкретное изменение.

Следовательно, формируется команда:

```text
ChangeCameraDirection
```

Интерфейсу необходимо узнать, была ли команда принята.

Поэтому взаимодействие может потребовать непосредственного ответа.

```text
Operator
    │
    ▼
ChangeCameraDirection
    │
    ▼
Camera Module
    │
    ▼
Result
```

То, будет ли это HTTP, локальный вызов или другой транспорт, является отдельным техническим решением.

---

## Синхронная коммуникация

Синхронная коммуникация используется тогда, когда продолжение операции зависит от результата другой области.

Отправитель ожидает ответ.

```text
Sender
   │
   │ request
   ▼
Receiver
   │
   │ response
   ▼
Sender continues
```

Пока результат не получен, операция не может продолжиться.

---

## Пример

Оператор открывает карточку автомобиля.

Интерфейсу необходимо получить его текущее состояние.

```text
UI
 │
 ▼
GetVehicleState
 │
 ▼
Transport Projection
 │
 ▼
VehicleState
 │
 ▼
UI
```

Без результата интерфейс не способен построить требуемое представление.

Синхронное взаимодействие здесь естественно.

---

## Синхронная коммуникация создаёт временную связанность

При синхронном взаимодействии обе стороны должны быть доступны одновременно.

```text
Module A ─────► Module B
                   │
                 offline
                   │
                   X

Module A cannot continue
```

Поэтому синхронная коммуникация не должна использоваться автоматически.

Каждая синхронная зависимость увеличивает связанность времени выполнения.

---

## Пример

Transport Module завершает изменение положения автомобиля.

После этого ему необходимо сообщить Analytics Module о перемещении.

Если использовать синхронный вызов:

```text
Transport
    │
    ▼
Analytics
    │
   offline
    X

Transport operation fails
```

Получается, что доступность аналитики начинает влиять на изменение транспортного состояния.

Это неправильная граница.

---

## Асинхронная коммуникация

Асинхронная коммуникация используется тогда, когда отправителю не требуется немедленный результат обработки.

Отправитель передаёт сообщение и продолжает работу.

```text
Sender
   │
   ▼
Message
   │
   ├────────► Receiver A
   ├────────► Receiver B
   └────────► Receiver C

Sender continues
```

Получатели могут обработать сообщение позже.

---

## Пример

Автомобиль изменил положение.

Transport Module завершил транзакцию.

После этого публикуется событие:

```text
VehiclePositionChanged
```

```text
Transport
    │
    ▼
VehiclePositionChanged
    │
    ├────────► Map Projection
    ├────────► Analytics
    └────────► History
```

Transport Module не ожидает завершения всех обработчиков.

Изменение автомобиля уже произошло.

---

## Команда и событие имеют разную семантику

Команда выражает намерение:

> Сделай это.

Событие выражает факт:

> Это уже произошло.

```text
COMMAND

ChangeCameraDirection
        │
        ▼
   Camera Module


EVENT

CameraDirectionChanged
        │
        ├────────► Projection
        ├────────► Analytics
        └────────► Other consumers
```

Эти понятия нельзя использовать как взаимозаменяемые.

---

## Пример

Команда:

```text
AssignVehicleRoute
```

может быть отклонена.

Например, маршрут нарушает ограничения.

Событие:

```text
VehicleRouteAssigned
```

уже описывает завершённый факт.

Его нельзя отклонить.

Получатель может только решить, как на этот факт реагировать.

---

## Запрос отличается от команды

Запрос предназначен для получения информации.

Он не выражает намерение изменить цифровой мир.

```text
QUERY

GetCameraState
      │
      ▼
Camera Projection
      │
      ▼
CameraState
```

Команда:

```text
COMMAND

ChangeCameraDirection
      │
      ▼
Execution Model
```

Разделение запросов и команд делает намерение взаимодействия явным.

---

## Коммуникация внутри процесса

Если два архитектурных компонента находятся внутри одного процесса, их взаимодействие не обязано проходить через сеть.

```text
┌─────────────────────────────────┐
│             Prizma              │
│                                 │
│ Transport ──► Contract ──► Camera│
│                                 │
└─────────────────────────────────┘
```

Может использоваться обычный вызов в памяти.

Архитектурная граница при этом сохраняется.

---

## Пример

На раннем этапе Transport Module и Camera Module находятся внутри одного backend-приложения.

Вызов:

```text
Camera Module
      │
      ▼
Transport Query Contract
      │
      ▼
Transport Module
```

может технически выполняться без HTTP.

Если позднее модули будут разделены, контракт сохранится, а транспорт изменится.

---

## Межпроцессная коммуникация

После физического разделения компонентов взаимодействие пересекает процессную или сетевую границу.

```text
┌────────────────┐
│ Camera Service │
└───────┬────────┘
        │
        │ network
        ▼
┌───────────────────┐
│ Transport Service │
└───────────────────┘
```

Это значительно дороже локального взаимодействия.

Появляются:

* задержки;
* сетевые ошибки;
* таймауты;
* частичная недоступность;
* повторная доставка;
* необходимость сериализации;
* несовпадение версий.

Поэтому физическое разделение нельзя считать бесплатным архитектурным решением.

---

## Локальный вызов нельзя считать сетью

Архитектура должна учитывать реальную стоимость коммуникации.

Не следует искусственно моделировать каждый внутрипроцессный вызов как удалённый.

```text
Модульный монолит

Module A
   │
   ▼
Module B

дешёвое взаимодействие
```

и:

```text
Распределённая система

Service A
   │
   ▼
Network
   │
   ▼
Service B

дорогое взаимодействие
```

имеют разные эксплуатационные свойства.

Контракт может быть одинаковым.

Стоимость его реализации — нет.

---

## События не должны знать потребителей

Издатель события сообщает факт.

Он не должен определять список реакций.

---

## Пример

Transport Module публикует:

```text
VehicleEnteredZone
```

Неправильная модель:

```text
Transport
   │
   ├── notify Camera
   ├── notify Analytics
   ├── notify Security
   └── notify UI
```

Transport начинает знать обо всех потребителях.

Правильная модель:

```text
Transport
   │
   ▼
VehicleEnteredZone
   │
   ├────────► Cameras
   ├────────► Analytics
   ├────────► Security
   └────────► UI Projection
```

Transport знает только о произошедшем факте.

---

## Команда должна иметь определённого владельца

В отличие от события, команда направлена конкретному владельцу возможности.

```text
ChangeCameraDirection
        │
        ▼
   Camera Module
```

Не должно существовать нескольких независимых владельцев одной команды.

Иначе становится непонятно, кто отвечает за результат.

---

## Пример

```text
AssignVehicleRoute
```

принадлежит Transport Module.

Недопустима ситуация:

```text
AssignVehicleRoute
      │
      ├────────► Transport Module
      └────────► Analytics Module
```

где оба потребителя независимо пытаются выполнить одну команду.

Команда имеет одного логического исполнителя.

Событие может иметь множество потребителей.

---

## Доставка не равна обработке

Факт получения сообщения ещё не означает успешного выполнения его смысла.

```text
Message
   │
   ▼
Delivered
   │
   ▼
Processing
   │
   ├────► Success
   │
   └────► Failure
```

Архитектура должна различать эти состояния там, где это важно.

---

## Пример

Команда на изменение состояния камеры была доставлена Camera Module.

Но во время проверки выяснилось, что камера недоступна.

Сообщение было доставлено успешно.

Команда не была выполнена.

Это разные результаты.

---

## Повторная доставка

В распределённой системе сообщение может быть доставлено повторно.

Поэтому обработчики должны учитывать возможность повторов.

```text
Message #42
   │
   ├────────► delivery 1
   └────────► delivery 2

Consumer
   │
   ▼
logical effect once
```

Особенно важно это для команд и событий, создающих долговременный эффект.

---

## Пример

Событие:

```text
VehicleEnteredZone
```

было доставлено Analytics Module дважды.

Это не должно автоматически означать два въезда автомобиля.

Потребитель должен уметь определить, что речь идёт об одном событии.

---

## Порядок сообщений

Некоторые последовательности событий имеют причинную зависимость.

```text
VehicleEnteredZone
        │
        ▼
VehicleLeftZone
```

Если получатель увидит их наоборот:

```text
VehicleLeftZone
        │
        ▼
VehicleEnteredZone
```

его локальное представление станет некорректным.

Поэтому там, где порядок влияет на результат, контракт коммуникации должен предоставлять механизм определения последовательности.

Например:

```text
Version 41
Version 42
Version 43
```

или эквивалентную модель порядка.

---

## Не все события требуют глобального порядка

Глобально упорядочивать все изменения платформы дорого и часто бессмысленно.

Порядок необходим только внутри той области, где изменения причинно связаны.

---

## Пример

Изменение направления камеры:

```text
Camera #15
Version 81
Version 82
```

и изменение топлива автомобиля:

```text
Vehicle #42
Version 19
Version 20
```

не обязаны иметь общий порядок:

```text
Camera #15 before Vehicle #42
```

если между этими изменениями нет причинной связи.

Архитектура должна гарантировать только необходимый порядок.

---

## Недоступность получателя

Асинхронная коммуникация должна учитывать ситуацию, когда получатель временно недоступен.

```text
Producer
   │
   ▼
Message
   │
   ▼
Delivery mechanism
   │
   X
Consumer offline
```

Сообщение не должно автоматически теряться только потому, что потребитель отсутствовал в момент его публикации, если контракт требует гарантированной доставки.

---

## Пример

Analytics Module отключён на десять минут.

За это время автомобили продолжают перемещаться.

Transport Module не должен останавливаться.

После восстановления аналитика получает необходимые изменения и догоняет актуальное состояние.

```text
Transport

Event 101
Event 102
Event 103
Event 104
     │
     ▼

Analytics offline


Analytics online
     │
     ▼
101 → 102 → 103 → 104
```

Это позволяет разделять доступность независимых областей.

---

## Коммуникация не должна расширять транзакцию

Внешний сетевой вызов не должен автоматически становиться частью локальной транзакции цифрового мира.

---

## Пример

Неправильно:

```text
BEGIN TRANSACTION

Update Vehicle
      │
      ▼
Call Analytics Service
      │
      ▼
Call Notification Service
      │
      ▼
COMMIT
```

Теперь доступность двух внешних сервисов определяет возможность изменить автомобиль.

Более устойчиво:

```text
BEGIN TRANSACTION
      │
      ▼
Update Vehicle
      │
      ▼
Record Event
      │
      ▼
COMMIT

      │
      ▼

Synchronization
      │
      ├────────► Analytics
      └────────► Notifications
```

Локальная согласованность завершается раньше внешней коммуникации.

---

## Гарантии коммуникации должны быть явными

Для каждого значимого взаимодействия необходимо понимать требуемые гарантии.

Например:

* допустима ли потеря;
* допустим ли повтор;
* важен ли порядок;
* требуется ли ответ;
* существует ли таймаут;
* можно ли повторить операцию;
* должен ли потребитель восстановить пропущенные изменения.

Не каждому сообщению нужны максимальные гарантии.

---

## Пример

Текущее положение автомобиля для плавной анимации может обновляться очень часто.

Если один промежуточный пакет потерян:

```text
Position 100
Position 101  X
Position 102
```

клиент может просто продолжить с `Position 102`.

Но событие:

```text
VehicleAccessRevoked
```

может требовать гарантированной обработки.

Одинаковая политика доставки для этих двух типов информации была бы неоправданной.

---

## Потоковые данные

Некоторые данные имеют высокую частоту и быстро теряют актуальность.

Например:

* координаты движущегося автомобиля;
* телеметрия;
* состояние сенсоров;
* положение камеры;
* кадры видеопотока.

Для таких данных актуальность последнего состояния может быть важнее гарантированной доставки каждого промежуточного значения.

```text
State 1
   │
State 2
   │
State 3
   │
State 4
   │
   ▼
Current State
```

Это отличается от истории предметных событий, где потеря одного элемента может изменить смысл последовательности.

---

## Пример

Автомобиль передаёт положение десять раз в секунду.

```text
P1 → P2 → P3 → P4 → P5
```

Если клиент не получил `P3`, но получил `P4`:

```text
P1 → P2 → X → P4 → P5
```

в большинстве визуальных сценариев достаточно продолжить с более свежего состояния.

Но если потеряно событие:

```text
VehicleRouteAssigned
```

восстановление только следующего события может оказаться недостаточным.

---

## Коммуникация с пользовательскими интерфейсами

Пользовательский интерфейс является таким же потребителем контрактов платформы.

Он может использовать:

* синхронные запросы для получения состояния;
* команды для изменения мира;
* потоковые обновления для актуализации представлений.

```text
                  UI
                  │
        ┌─────────┼─────────┐
        │         │         │
        ▼         ▼         ▼
      Query     Command    Updates
        │         │         │
        ▼         ▼         ▼
   Projection  Execution  Synchronization
```

UI не должен иметь специального обходного пути к Domain Model.

---

## Пример

Карта открывается.

Сначала она получает начальную проекцию:

```text
GetVisibleObjects
```

После этого подписывается на изменения:

```text
ObjectPositionChanged
ObjectStateChanged
ObjectRemoved
```

Пользователь изменяет маршрут:

```text
AssignVehicleRoute
```

Получается три различных вида коммуникации с разной семантикой:

```text
Query   → получить состояние
Command → изменить состояние
Event   → узнать об изменении
```

---

## Коммуникация с внешними системами

Внешние системы не должны напрямую становиться частью внутреннего коммуникационного пространства платформы.

Между ними существует интеграционная граница.

```text
External System
      │
      ▼
Integration Boundary
      │
      ▼
Internal Contract
      │
      ▼
Prizma
```

Внешний формат преобразуется во внутреннюю семантику платформы.

---

## Пример

GPS-провайдер отправляет:

```text
device=481
lat=50.59
lon=36.58
speed=12.4
```

Это ещё не внутренняя команда «Призмы».

Интеграционный слой определяет:

```text
device 481
     │
     ▼
Object #42
```

и формирует внутреннее изменение:

```text
UpdateVehiclePosition
```

```text
GPS Provider
      │
      ▼
Adapter
      │
      ▼
UpdateVehiclePosition
      │
      ▼
Execution Model
```

Внешний протокол заканчивается на интеграционной границе.

---

## Выбор модели коммуникации

Перед созданием взаимодействия необходимо пройти несколько вопросов.

```text
Нужно взаимодействие
        │
        ▼
Это изменение?
    │         │
   Да        Нет
    │         │
    ▼         ▼
 Command     Query
    │
    ▼
Изменение уже произошло?
    │
   Да
    ▼
  Event
```

После определения семантики:

```text
Нужен ответ сейчас?
      │
   ┌──┴──┐
   │     │
  Да    Нет
   │     │
   ▼     ▼
Sync   Async
```

И только затем:

```text
Как реализовать?

In-process
HTTP
WebSocket
```

## Практическое значение

При проектировании коммуникации команда должна избегать вопроса:

> Через что будем это отправлять?

как первого архитектурного решения.

Сначала необходимо определить:

* кто является владельцем действия или данных;
* что именно передаётся;
* является ли это командой, запросом или событием;
* требуется ли немедленный результат;
* что произойдёт при недоступности получателя;
* допустимы ли повторы;
* важен ли порядок;
* допустима ли потеря промежуточных значений;
* каким образом потребитель восстановится после сбоя.

После этого выбирается технический транспорт.

---

## Инварианты коммуникации

Любая коммуникация в платформе обязана соблюдать следующие правила.

* Семантика взаимодействия определяется до выбора транспорта.
* Команда выражает намерение изменить состояние.
* Команда имеет одного логического владельца.
* Запрос получает информацию и не должен скрыто изменять цифровой мир.
* Событие описывает уже произошедший факт.
* Издатель события не зависит от его потребителей.
* Синхронная коммуникация используется только при необходимости немедленного результата.
* Внешняя коммуникация не должна без необходимости расширять локальную транзакцию.
* Повторная доставка должна учитываться там, где она возможна.
* Порядок гарантируется только там, где он влияет на смысл.
* Гарантии доставки соответствуют значимости информации.
* Потоковые данные и предметные события могут использовать разные модели доставки.
* Транспорт является технической реализацией архитектурного взаимодействия.

---

## Архитектурное значение

Коммуникация превращает статический граф зависимостей в работающую систему.

Она определяет, каким образом независимые области платформы взаимодействуют во времени, сохраняя свои границы.

Правильно выбранная модель позволяет одной части системы быть временно недоступной, медленной или физически удалённой без автоматического разрушения остальных частей платформы.

```text
            Prizma

     ┌─────────────────┐
     │    Commands     │
     │    Queries      │
     │    Events       │
     │    Streams      │
     └────────┬────────┘
              │
              ▼
       Communication
              │
     ┌────────┼────────┐
     ▼        ▼        ▼
  Modules     UI    External
```

Конкретные технологии могут меняться.

Семантика взаимодействия должна оставаться стабильной.

---

## Заключение

Коммуникация определяет, каким образом части платформы обмениваются действиями и информацией.

Но возможность получить или изменить данные ещё не определяет, **кому эти данные принадлежат**.

Если несколько модулей начинают считать одно состояние своим, появляются конкурирующие источники истины, прямые изменения чужих данных и невозможность определить ответственность за их корректность.

Поэтому следующим шагом необходимо ответить на вопрос:

> Кто является владельцем каждого состояния цифрового мира и кто имеет право его изменять?

Этому посвящена следующая глава — **Владение данными**.
