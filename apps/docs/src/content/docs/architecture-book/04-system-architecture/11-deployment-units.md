# Единицы развёртывания

## Статус

Accepted

---

## Введение

Архитектура «Призмы» разделена на модули.

Каждый модуль имеет собственную ответственность, границу и публичные контракты.

Однако архитектурный модуль не определяет автоматически способ физического развёртывания.

Несколько модулей могут работать внутри одного процесса.

Один модуль может быть разделён между несколькими процессами.

Отдельная техническая подсистема может обслуживать сразу несколько модулей.

Поэтому необходимо разделять два понятия:

* логическая архитектура;
* физическая топология системы.

Для описания физического размещения используются единицы развёртывания.

---

## Что такое единица развёртывания

Единица развёртывания — это часть системы, которая может быть независимо:

* собрана;
* запущена;
* остановлена;
* обновлена;
* масштабирована;
* восстановлена.

```text
Architecture
     │
     ▼
Modules
     │
     ▼
Deployment Mapping
     │
     ▼
Deployment Units
```

Модуль определяет архитектурную ответственность.

Единица развёртывания определяет физическое исполнение.

---

## Пример

Платформа содержит:

```text
Platform Core
Transport Module
Camera Module
Analytics Module
```

На раннем этапе всё это может работать внутри одного backend-приложения:

```text
┌───────────────────────────────────────┐
│              Prizma API               │
│                                       │
│  Platform Core                        │
│  Transport                            │
│  Cameras                              │
│  Analytics                            │
│                                       │
└───────────────────────────────────────┘
```

Архитектурно существуют несколько модулей.

Физически существует одна единица развёртывания.

Это не противоречие.

---

## Модуль не равен сервису

Наличие архитектурного модуля не является причиной создавать отдельный сервис.

```text
Module ≠ Service
```

Модуль отвечает на вопрос:

> Где проходит граница ответственности?

Сервис отвечает на другой вопрос:

> Что необходимо независимо запускать и эксплуатировать?

Эти решения связаны, но не эквивалентны.

---

## Пример

Camera Module может существовать:

```text
┌──────────────────────────────┐
│          Prizma API          │
│                              │
│ Transport | Cameras | Core   │
└──────────────────────────────┘
```

Позже управление видеопотоками создаёт отдельную эксплуатационную нагрузку.

Тогда часть системы может быть вынесена:

```text
┌─────────────────────┐
│     Prizma API      │
│                     │
│ Core                │
│ Transport           │
│ Camera Domain       │
└──────────┬──────────┘
           │
           ▼
┌─────────────────────┐
│    Media Service    │
│                     │
│ Stream Processing   │
│ Media Sessions      │
└─────────────────────┘
```

Camera Module при этом не обязан исчезать из основного приложения.

Его предметная ответственность и физическая обработка медиаданных — разные вещи.

---

## Начальная модель развёртывания

Для раннего этапа развития «Призмы» предпочтительной является модель модульного монолита.

```text
                  Users
                    │
                    ▼
             ┌────────────┐
             │   Prizma   │
             │    API     │
             └─────┬──────┘
                   │
      ┌────────────┼────────────┐
      ▼            ▼            ▼
 Transport      Cameras      Analytics
      │            │            │
      └────────────┼────────────┘
                   ▼
             Platform Core
```

Основные модули работают внутри одного процесса.

Архитектурные границы сохраняются внутри приложения.

---

## Почему не микросервисы сразу

Распределение системы имеет стоимость.

После разделения появляются:

* сетевые ошибки;
* таймауты;
* повторная доставка;
* частичная недоступность;
* распределённая трассировка;
* согласование версий;
* сложность локальной разработки;
* сложность тестирования;
* дополнительные процессы развёртывания;
* дополнительные требования к мониторингу.

```text
Один процесс

A ─────► B

обычный вызов


Разные процессы

A
│
▼
Network
│
├── latency
├── timeout
├── retry
├── serialization
├── authentication
└── partial failure
│
▼
B
```

Эту стоимость имеет смысл принимать только тогда, когда физическое разделение решает существующую проблему.

---

## Пример

Transport Module и Camera Module имеют небольшую нагрузку.

Для них нет причины создавать:

```text
transport-service
camera-service
relation-service
object-service
event-service
```

только потому, что архитектура содержит соответствующие понятия.

Такое разделение создаст распределённую систему раньше, чем в ней появится необходимость.

---

## Platform Core не является Core Service

Platform Core представляет собой архитектурный фундамент.

Это не означает существование отдельного:

```text
platform-core-service
```

к которому остальные сервисы должны обращаться через сеть.

---

## Пример

Плохая интерпретация:

```text
Transport Service ──┐
                    │
Camera Service ─────┼────► Core Service
                    │
Analytics Service ──┘
```

Теперь каждая фундаментальная операция требует удалённого взаимодействия.

Platform Core превращается в центральный сетевой узел.

Правильнее рассматривать Core как фундаментальные контракты и механизмы, используемые соответствующими единицами исполнения:

```text
┌────────────────────┐
│ Deployment Unit A  │
│                    │
│ Module             │
│ Core mechanisms    │
└────────────────────┘
```

Core — архитектурный слой.

Не обязательный сетевой сервис.

---

## Когда необходимо физическое разделение

Выделение отдельной единицы развёртывания должно иметь конкретную причину.

Например:

* независимое масштабирование;
* существенное отличие нагрузки;
* изоляция отказов;
* отдельные требования безопасности;
* другой жизненный цикл обновлений;
* использование специализированного оборудования;
* необходимость географического размещения;
* независимое управление ресурсами;
* отдельная команда с независимым циклом поставки.

---

## Пример: видеопотоки

Обработка видеопотоков может требовать значительно больше ресурсов, чем работа с обычными объектами.

```text
              Prizma API
                  │
                  ▼
            Camera Contract
                  │
                  ▼
             Media Layer
```

При росте нагрузки:

```text
                     Prizma API
                         │
                         ▼
                   Media Contract
                         │
              ┌──────────┼──────────┐
              ▼          ▼          ▼
          Media #1   Media #2   Media #3
```

Media-компоненты можно масштабировать независимо.

Это реальная причина физического разделения.

---

## Пример: аналитика

Аналитический модуль может выполнять тяжёлые расчёты.

Пока нагрузка мала:

```text
Prizma API
   │
   └── Analytics
```

Позже:

```text
Prizma
   │
   ▼
Analytics Events
   │
   ▼
Analytics Workers
   │
   ├── Worker 1
   ├── Worker 2
   └── Worker 3
```

Domain Model не требует изменений.

Изменяется физическая топология исполнения.

---

## Горизонтальное масштабирование

Единица развёртывания может иметь несколько экземпляров.

```text
                 Load
                  │
          ┌───────┼───────┐
          ▼       ▼       ▼
       Node A   Node B   Node C
```

Архитектура не должна предполагать, что конкретный процесс существует в единственном экземпляре, если это не является осознанным ограничением.

---

## Пример

API платформы получает большое количество запросов.

Вместо изменения модульной архитектуры:

```text
Prizma API
    │
    ├── Instance 1
    ├── Instance 2
    └── Instance 3
```

может быть запущено несколько одинаковых экземпляров.

Масштабирование не обязательно требует создания новых сервисных границ.

---

## Состояние процесса

Горизонтально масштабируемая единица не должна без необходимости хранить критическое авторитетное состояние только в памяти одного процесса.

```text
Request 1 ──► Instance A

Request 2 ──► Instance B
```

Если корректность зависит от того, что оба запроса попадут в один процесс, появляется скрытая инфраструктурная зависимость.

---

## Пример

Неправильно:

```text
Instance A

activeVehicleState = authoritative state
```

После перезапуска:

```text
Instance A
    X

authoritative state lost
```

Процесс может хранить:

* кэши;
* временные вычисления;
* активные соединения;
* локальные оптимизации.

Но долговременное авторитетное состояние должно иметь соответствующий механизм хранения.

---

## Stateful-компоненты допустимы

Это не означает, что все процессы должны быть stateless.

Некоторые задачи естественно требуют локального состояния.

Например:

* активная медиасессия;
* соединение с оборудованием;
* WebSocket-соединение;
* потоковый процессор;
* локальный spatial index.

Важно различать:

```text
Operational State
```

и:

```text
Authoritative Domain State
```

Операционное состояние может принадлежать конкретному экземпляру.

Предметное состояние цифрового мира не должно случайно зависеть от его жизненного цикла.

---

## Изоляция отказов

Отдельная единица развёртывания создаёт возможность изолировать отказ.

Но только если архитектура коммуникации действительно допускает независимость.

---

## Пример

Analytics Service недоступен.

```text
Analytics
    X
```

При правильной границе:

```text
Transport     ✔
Cameras       ✔
Map           ✔
Commands      ✔
Analytics     X
```

Платформа продолжает выполнять основные функции.

---

## Неправильная изоляция

Если каждый запрос Transport Module синхронно требует Analytics Service:

```text
Transport
    │
    ▼
Analytics
    X
```

то физическое разделение не создало изоляцию.

Оно только добавило сетевую точку отказа.

```text
Analytics X
    │
    ▼
Transport X
```

Поэтому физическое разделение должно сопровождаться правильной моделью коммуникации.

---

## Единица развёртывания является границей отказа

После физического разделения необходимо считать, что другая единица может быть:

* недоступна;
* перегружена;
* перезапущена;
* иметь другую версию;
* отвечать медленно.

```text
Unit A
  │
  ▼
?????
  │
  ▼
Unit B
```

Любое межпроцессное взаимодействие должно проектироваться с учётом этого факта.

---

## Версии единиц развёртывания

В распределённой системе обновление редко происходит мгновенно на всех узлах.

В течение некоторого времени могут одновременно работать разные версии.

```text
Service A v3
      │
      ▼
Service B v2
```

или:

```text
Instance 1 → v4
Instance 2 → v4
Instance 3 → v3
```

Поэтому публичные контракты должны учитывать временную совместимость версий.

---

## Пример

Camera Service обновлён первым.

Он начинает публиковать новый вариант события.

Transport или UI ещё работают на предыдущей версии.

Если изменение контракта несовместимо:

```text
Camera v2 ─────X────► Consumer v1
```

обновление становится невозможным без одновременной остановки всей системы.

Стабильные контракты позволяют:

```text
Camera v2 ──────────► Consumer v1
```

в течение периода миграции.

---

## Развёртывание не меняет владение данными

Вынос части модуля в отдельный процесс не должен случайно создавать нового владельца состояния.

---

## Пример

Появился:

```text
Media Service
```

Он отвечает за видеосессии.

Это не означает, что он автоматически становится владельцем всей Camera Domain Model.

```text
Camera Module
    │
    └── Camera Domain State

Media Service
    │
    └── Media Operational State
```

Граница владения определяется предметным смыслом.

Не расположением кода.

---

## Развёртывание не меняет контракты автоматически

Если два модуля были внутри одного процесса:

```text
A ──► Contract ──► B
```

а затем `B` вынесен:

```text
A
│
▼
Contract
│
▼
Network
│
▼
B
```

архитектурный контракт желательно сохранить.

Изменяется адаптер коммуникации.

Не смысл взаимодействия.

---

## Географическое размещение

Некоторые единицы в будущем могут находиться рядом с источниками данных.

Например, локальный узел предприятия может работать непосредственно с оборудованием.

```text
                 Central Platform
                       │
                       │
                    Network
                       │
                       ▼
                   Edge Node
                       │
             ┌─────────┼─────────┐
             ▼         ▼         ▼
          Camera    Vehicle    Sensors
```

Это позволяет:

* уменьшить задержки;
* переживать временную потерю внешней связи;
* выполнять локальную обработку;
* уменьшать объём передаваемых данных.

---

## Пример

Камеры предприятия передают несколько видеопотоков.

Не обязательно отправлять весь внутренний трафик через центральный сервер.

```text
Cameras
   │
   ▼
Local Media Node
   │
   ├── local processing
   ├── stream management
   └── selected data
           │
           ▼
      Central Prizma
```

Архитектура модулей при этом остаётся общей.

Меняется место исполнения отдельных возможностей.

---

## Edge не является отдельным цифровым миром

Локальный узел не должен автоматически создавать независимую модель мира.

```text
Central World
     │
     ▼
Edge Representation
```

Если edge способен работать автономно, необходимо отдельно определить:

* какую часть состояния он хранит;
* чем владеет;
* какие изменения способен выполнять;
* как происходит последующая синхронизация.

Наличие edge deployment само по себе не решает эти вопросы.

---

## Frontend как единица развёртывания

Пользовательский интерфейс также является самостоятельной единицей развёртывания.

```text
Browser
   │
   ▼
Frontend Application
   │
   ▼
Platform Contracts
```

Frontend не является частью backend Domain Model.

Он потребляет опубликованные проекции и команды.

---

## Пример

В будущем могут существовать:

```text
Web Application

Mobile Application

Operator Workstation

AR Application
```

Все они являются разными клиентскими единицами развёртывания.

```text
          Platform Contracts
          ▲       ▲       ▲
          │       │       │
         Web    Mobile    AR
```

Для этого не требуется создавать отдельную Domain Model для каждого интерфейса.

---

## Deployment topology должна быть заменяемой

Архитектура должна позволять изменять физическую топологию без полного пересмотра предметной модели.

---

## Этап 1

```text
┌─────────────────────────┐
│       Prizma API        │
│                         │
│ Core                    │
│ Transport               │
│ Cameras                 │
│ Analytics               │
└─────────────────────────┘
```

---

## Этап 2

```text
┌─────────────────────────┐
│       Prizma API        │
│                         │
│ Core                    │
│ Transport               │
│ Cameras                 │
└────────────┬────────────┘
             │
             ▼
      Analytics Workers
```

---

## Этап 3

```text
                  Prizma API
                 /          \
                /            \
               ▼              ▼
        Media Cluster   Analytics Cluster
               │
               ▼
           Edge Nodes
```

Предметные понятия при этом не должны перепроектироваться на каждом этапе.

---

## Когда не следует разделять

Единицу развёртывания не следует выделять только потому, что:

* код находится в отдельной директории;
* существует отдельный модуль;
* используется отдельная таблица;
* команда хочет использовать микросервисы;
* предполагается возможный рост в будущем;
* отдельный компонент выглядит достаточно большим.

Разделение должно решать конкретную проблему.

---

## Пример

Предположение:

> Когда-нибудь Transport Module будет очень большим.

не является достаточной причиной создавать отдельный сервис сейчас.

Сначала сохраняется архитектурная граница:

```text
Prizma API
   │
   └── Transport Module
```

Если позже появится реальная причина:

```text
Transport Load ↑
```

физическую границу можно пересмотреть.

---

## Стоимость разделения

Перед выделением новой единицы необходимо учитывать не только преимущества.

```text
Benefit
   │
   ├── independent scaling
   ├── failure isolation
   └── independent deployment

Cost
   │
   ├── network
   ├── observability
   ├── retries
   ├── distributed consistency
   ├── deployment complexity
   └── operational support
```

Решение оправдано только тогда, когда преимущества превышают эту стоимость.

---

## Практическое правило

Начальная стратегия «Призмы»:

```text
Логически разделять рано.
Физически разделять поздно.
```

То есть модульные границы проектируются сразу.

Сервисные границы появляются по мере необходимости.

---

## Пример развития

В начале:

```text
              Prizma Backend

┌──────────────────────────────────────┐
│ Core                                 │
│ Transport                            │
│ Cameras                              │
│ Analytics                            │
│ Scenarios                            │
└──────────────────────────────────────┘
```

После появления реальной нагрузки:

```text
                 Prizma Backend
                      │
           ┌──────────┴──────────┐
           ▼                     ▼
      Media Cluster       Analytics Workers
```

Позже при необходимости:

```text
                    Central Prizma
                   /              \
                  ▼                ▼
             Edge Node A      Edge Node B
```

Эволюция происходит постепенно.

---

## Проверка новой единицы развёртывания

Перед физическим разделением необходимо ответить:

* Какую конкретную проблему решает разделение?
* Требуется ли независимое масштабирование?
* Требуется ли изоляция отказов?
* Отличается ли жизненный цикл обновлений?
* Существует ли естественная архитектурная граница?
* Можно ли сохранить существующие публичные контракты?
* Кто владеет состоянием после разделения?
* Что произойдёт при недоступности новой единицы?
* Какие операции становятся сетевыми?
* Как обрабатываются таймауты и повторы?
* Как обеспечивается наблюдаемость?
* Как будут сосуществовать разные версии?
* Оправдывает ли выигрыш операционную сложность?

Если на первый вопрос нет конкретного ответа, разделение, скорее всего, преждевременно.

---

## Инварианты единиц развёртывания

Физическая архитектура обязана соблюдать следующие правила.

* Архитектурный модуль не обязан быть отдельной единицей развёртывания.
* Единица развёртывания не обязана соответствовать одному модулю.
* Platform Core не рассматривается автоматически как отдельный сетевой сервис.
* Физическое разделение выполняется только при наличии конкретной причины.
* Модульные границы должны существовать до физического разделения.
* Развёртывание не меняет владельца данных автоматически.
* Межпроцессная коммуникация считается потенциально ненадёжной.
* Независимая единица должна учитывать возможность частичной недоступности системы.
* Публичные контракты должны допускать независимое обновление единиц.
* Горизонтальное масштабирование не должно требовать изменения Domain Model.
* Физическая топология должна иметь возможность эволюционировать независимо от предметной архитектуры.

## Архитектурное значение

Разделение логической и физической архитектуры позволяет «Призме» начинать с простой эксплуатационной модели, не жертвуя возможностью масштабирования.

```text
Архитектура

Core
 │
 ├── Transport
 ├── Cameras
 └── Analytics

          │
          │ mapping
          ▼

Deployment

Сегодня:
┌──────────────────┐
│  Prizma Backend  │
└──────────────────┘

Позже:
┌────────┐ ┌────────┐ ┌────────┐
│ Prizma │ │ Media  │ │Analytics│
└────────┘ └────────┘ └────────┘
```

Архитектурные границы определяются предметным смыслом.

Физические — эксплуатационной необходимостью.

## Заключение

Единицы развёртывания определяют, где физически выполняются части платформы.

По мере роста системы некоторые из этих единиц будут иметь несколько экземпляров, другие окажутся на отдельных серверах, а часть может работать непосредственно на локальных узлах предприятий.

В такой системе невозможно считать сам факт сетевого соединения достаточным доказательством того, что участнику разрешено выполнять действие.

Возникают вопросы:

> Кто инициировал команду?

> От имени кого она выполняется?

> Имеет ли этот субъект право видеть или изменять конкретную часть цифрового мира?

> Сохраняются ли эти ограничения при прохождении команды через несколько модулей и сервисов?

Поэтому следующим архитектурным слоем должна стать **модель безопасности и доступа**.
