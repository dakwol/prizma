# Модель безопасности и доступа

## Статус

Accepted

---

## Введение

Платформа «Призма» объединяет множество объектов, модулей, пользователей, устройств и внешних систем.

Не каждый участник должен иметь доступ ко всему цифровому миру.

Один оператор может видеть только определённую территорию.

Другой может управлять камерами, но не изменять состояние транспорта.

Внешняя система может передавать телеметрию, но не выполнять пользовательские команды.

Локальный узел может работать только с частью мира, относящейся к конкретному объекту инфраструктуры.

Поэтому безопасность должна быть встроена в архитектурную модель исполнения.

Она не является дополнительным фильтром поверх API.

---

## Основной принцип

Любое значимое действие в платформе выполняется:

* конкретным субъектом;
* в определённом контексте;
* над конкретным ресурсом;
* с явно проверенным правом.

```text id="90fxxs"
Subject
   │
   ▼
Action
   │
   ▼
Resource
   │
   ▼
Authorization
   │
   ├── allowed
   └── denied
```

Если субъект, действие или ресурс невозможно определить, исполнение не должно считаться авторизованным.

---

## Субъект

Субъект — это участник, от имени которого выполняется действие.

Субъектом может быть:

* пользователь;
* сервис;
* устройство;
* внешний интеграционный клиент;
* сценарий;
* локальный узел платформы.

Субъект не обязательно является человеком.

---

## Пример

Оператор вручную изменяет направление камеры.

```text id="4hskae"
Operator #17
    │
    ▼
ChangeCameraDirection
```

Внешняя система передаёт координаты автомобиля.

```text id="nd9ozd"
GPS Integration
    │
    ▼
UpdateVehiclePosition
```

Оба действия имеют субъект.

Но права и контекст этих субъектов различаются.

---

## Authentication и Authorization

Архитектура различает два процесса.

**Authentication** отвечает на вопрос:

> Кто выполняет действие?

**Authorization** отвечает:

> Имеет ли этот субъект право выполнить это действие?

```text id="b3tpj3"
Credentials
    │
    ▼
Authentication
    │
    ▼
Subject
    │
    ▼
Authorization
    │
    ▼
Action allowed?
```

Успешная идентификация не означает наличие прав.

---

## Пример

Пользователь успешно вошёл в систему.

Это означает, что платформа знает его Identity.

Но команда:

```text id="ycaupb"
ChangeCameraDirection
```

всё ещё должна пройти проверку доступа к конкретной камере.

```text id="f0gg37"
Authenticated User
      │
      ▼
Camera #12
      │
      ▼
Can control?
   │       │
  yes      no
```

---

## Security Context

Информация о субъекте и его правах передаётся через контекст исполнения.

Этот контекст сопровождает команду на всём пути выполнения.

```text id="0o68k9"
Command
  │
  ├── Payload
  └── Security Context
          │
          ▼
      Execution
```

Security Context не должен исчезать при переходе между модулями или сервисами.

---

## Пример

Оператор запускает команду:

```text id="p2xvvt"
AssignVehicleRoute
```

Команда проходит:

```text id="tww293"
UI
 │
 ▼
API
 │
 ▼
Execution Model
 │
 ▼
Transport Module
```

На каждом этапе должно быть известно:

```text id="zgmoy6"
subject = Operator #17
```

Недопустимо, чтобы после первого сетевого вызова команда выполнялась уже от имени:

```text id="kp7w5o"
system
```

без явной причины.

---

## Делегирование

Иногда один компонент выполняет действие от имени другого субъекта.

Это называется делегированием.

Делегирование должно быть явным.

---

## Пример

Оператор запускает сценарий.

```text id="97na0m"
Operator
   │
   ▼
Scenario
   │
   ▼
ChangeCameraDirection
```

Нужно определить:

> выполняет ли сценарий команду от имени оператора;

или:

> сценарий имеет собственную системную Identity и собственные права.

Это архитектурно разные модели.

```text id="8dwv4r"
Variant A

Operator
   │
   ▼
Scenario
   │
   ▼
acts as Operator


Variant B

Operator
   │
   ▼
Scenario
   │
   ▼
Scenario Identity
```

Система не должна смешивать их неявно.

---

## Ресурс доступа

Авторизация относится не только к типу команды.

Она также должна учитывать конкретный ресурс.

---

## Пример

Пользователю разрешено:

```text id="w0pzew"
ChangeCameraDirection
```

Но только для камер определённого объекта.

```text id="fk2k80"
Camera #1  ✔
Camera #2  ✔
Camera #3  X
```

Проверка вида:

```text id="hu37o7"
user.hasPermission("camera.control")
```

может быть недостаточной.

Необходимо учитывать контекст конкретного ресурса.

---

## Область доступа

Права могут быть ограничены частью цифрового мира.

Например:

* миром;
* пространством;
* организацией;
* группой объектов;
* отдельным объектом;
* типом отношения;
* конкретной операцией.

```text id="dylhz2"
World
 │
 ├── Space A
 │     ├── Object 1
 │     └── Object 2
 │
 └── Space B
       ├── Object 3
       └── Object 4
```

Оператор может иметь доступ только к `Space A`.

---

## Пример

Пользователь открывает карту.

Проекция не должна сначала вернуть весь цифровой мир, а затем скрыть часть объектов на frontend.

```text id="a5xzzf"
Плохо

Full World
   │
   ▼
Frontend
   │
   └── hide unauthorized objects
```

Правильнее:

```text id="dfj1ko"
Security Context
      │
      ▼
Authorized Projection
      │
      ▼
Objects user may see
```

Ограничение доступа применяется до выдачи данных.

---

## Чтение и изменение — разные права

Право видеть объект не означает право его изменять.

```text id="6cfm1v"
Object
  │
  ├── read
  ├── update
  ├── control
  └── delete
```

Архитектура не должна сводить доступ к одному булевому признаку.

---

## Пример

Оператор может наблюдать камеру:

```text id="6zt2da"
view stream ✔
```

но не может:

```text id="fuhqph"
change direction X
delete camera X
change settings X
```

Другой пользователь может иметь более широкие права.

---

## Предметные и системные права

Некоторые ограничения относятся к безопасности платформы.

Другие являются предметными правилами.

Их необходимо различать.

---

## Пример

Пользователь не имеет права управлять камерой.

Это авторизация:

```text id="fq614j"
AccessDenied
```

Пользователь имеет право управлять камерой, но запрошенный угол недопустим.

Это предметная проверка:

```text id="om4j3e"
DirectionNotAllowed
```

Порядок:

```text id="43d4gq"
Command
   │
   ▼
Authentication
   │
   ▼
Authorization
   │
   ▼
Domain Validation
   │
   ▼
Execution
```

Безопасность и Domain Validation решают разные задачи.

---

## Авторизация выполняется до изменения состояния

Недопустимая команда не должна начинать изменение цифрового мира.

```text id="3m7psi"
Command
   │
   ▼
Authorization
   │
  denied
   X

World unchanged
```

---

## Пример

Пользователь пытается удалить автомобиль без необходимых прав.

Не должны выполняться:

* изменение состояния;
* создание новой версии объекта;
* предметное событие удаления.

Может существовать отдельное событие аудита попытки доступа, но это уже другая семантика.

---

## Авторизация не должна жить только в UI

Frontend может скрывать недоступные действия для удобства пользователя.

Но это не является механизмом безопасности.

```text id="j7kwam"
Frontend

Hide button
```

не заменяет:

```text id="1vvval"
Backend Authorization
```

Пользователь может:

* вызвать API напрямую;
* использовать устаревший клиент;
* модифицировать frontend;
* отправить запрос из другой системы.

Поэтому авторитетная проверка выполняется на доверенной стороне архитектурной границы.

---

## Пример

Кнопка управления камерой скрыта.

Но пользователь вручную отправляет команду.

```text id="jkeh42"
Manual Request
      │
      ▼
Authorization
      │
      X
AccessDenied
```

Модель остаётся защищённой независимо от интерфейса.

---

## Межмодульный доступ

Модули не должны автоматически доверять друг другу только потому, что находятся внутри одной платформы.

Необходимо различать:

* архитектурную зависимость;
* безопасность выполнения.

---

## Пример

Analytics Module инициирует команду изменения статуса автомобиля.

```text id="bfn8fq"
Analytics Module
      │
      ▼
ChangeVehicleStatus
```

Transport Module должен понимать, от имени какого субъекта выполняется действие.

Это может быть:

```text id="iftqxj"
Analytics Service Identity
```

с ограниченными системными правами.

---

## Service Identity

Каждая самостоятельная системная единица, выполняющая защищённые действия, должна иметь собственную Identity.

```text id="dm8eoa"
Transport Service
Camera Service
Analytics Service
Edge Node
Integration Client
```

не должны все использовать одну безликую Identity:

```text id="gcciga"
system
```

иначе невозможно определить источник действия и ограничить его возможности.

---

## Пример

```text id="t32j5q"
GPS Adapter
   │
   └── may UpdateVehiclePosition

Analytics Service
   │
   └── may read movement history

Camera Service
   │
   └── may control camera state
```

Компрометация одного компонента не должна автоматически давать полномочия всей платформы.

---

## Принцип минимальных полномочий

Субъект должен иметь только те права, которые необходимы для выполнения его функции.

```text id="99ki5j"
Needed permissions
      │
      ▼
Granted permissions
```

не:

```text id="ceidw5"
Admin everywhere
```

---

## Пример

GPS Integration требуется:

```text id="4cem4l"
vehicle.position.update
```

Ему не требуются:

```text id="uql1rl"
camera.control
vehicle.delete
user.manage
world.configure
```

Даже если технически проще выдать интеграции полный доступ.

---

## Deny by default

Отсутствие явно разрешённого действия означает запрет.

```text id="xay9o3"
Permission exists?
    │
 ┌──┴──┐
 │     │
yes    no
 │     │
 ▼     ▼
allow deny
```

Это предотвращает случайное появление доступа при добавлении новой функции.

---

## Пример

Добавлена новая команда:

```text id="jex3s7"
ExportVehicleHistory
```

Если модель доступа о ней ничего не знает, команда не должна автоматически стать доступной всем пользователям Transport Module.

Сначала определяется политика доступа.

---

## Роли

Роль может использоваться как удобный способ группировки прав.

```text id="x5u6n7"
Role
 │
 ├── Permission A
 ├── Permission B
 └── Permission C
```

Но роль не должна быть единственным фундаментальным понятием модели доступа.

---

## Пример

Роль:

```text id="ekrqd7"
CameraOperator
```

может включать:

```text id="y5462x"
camera.read
camera.stream.read
camera.control
```

Но конкретный пользователь может иметь эту роль только в определённом пространстве.

```text id="w7lq5p"
CameraOperator
      │
      ▼
Space A
```

В другом пространстве те же действия запрещены.

---

## Policy-based авторизация

Для сложных сценариев решение о доступе может зависеть от нескольких факторов.

Например:

* субъекта;
* ресурса;
* мира;
* пространства;
* времени;
* состояния объекта;
* типа действия.

```text id="k4y979"
Subject
   │
Resource
   │
Action
   │
Context
   │
   ▼
Policy
   │
   ▼
Decision
```

---

## Пример

Оператор может управлять камерой, если:

* камера находится в его зоне ответственности;
* пользователь имеет право управления;
* камера не находится в режиме обслуживания.

Здесь часть правила является security policy, а часть может опираться на предметное состояние.

```text id="a1ic6p"
Permission
   +
Space scope
   +
Camera state
   │
   ▼
Decision
```

---

## Доступ к отношениям

Поскольку Relation является самостоятельной сущностью, доступ может относиться не только к объектам.

---

## Пример

Пользователь может видеть:

```text id="m6086g"
Camera
Vehicle
```

но не иметь права видеть отношение:

```text id="xkrsum"
Camera observes Vehicle
```

если сама связь содержит ограниченную информацию.

```text id="guj6ot"
Object access      ✔
Relation access    X
```

Политика должна учитывать модель мира, а не только таблицы объектов.

---

## Доступ к истории

Исторические данные также могут иметь отдельные ограничения.

Право видеть текущее состояние не обязательно означает право видеть всю историю объекта.

---

## Пример

Пользователь видит текущее положение автомобиля.

```text id="gt594t"
Current Position ✔
```

Но история перемещений за месяц:

```text id="cq508e"
Movement History X
```

может требовать отдельного разрешения.

---

## Доступ к проекциям

Проекция должна учитывать Security Context.

Нельзя считать проекцию безопасной только потому, что она read-only.

---

## Пример

Общая аналитическая проекция содержит данные нескольких территорий.

```text id="jxru17"
Analytics Projection
  │
  ├── Space A
  ├── Space B
  └── Space C
```

Пользователю разрешён только `Space A`.

Результат запроса должен быть ограничен до выдачи:

```text id="00lp8g"
Security Context
      │
      ▼
Projection Query
      │
      ▼
Space A only
```

---

## Интеграционная безопасность

Внешний клиент также является субъектом.

Он получает только необходимые ему права.

```text id="f1mfrv"
External System
      │
      ▼
Authentication
      │
      ▼
Integration Identity
      │
      ▼
Authorization
      │
      ▼
Internal Contract
```

Интеграция не становится доверенной частью Core.

---

## Пример

Система обслуживания автомобилей может:

```text id="su2ozb"
read TechnicalState
submit MaintenanceResult
```

Но не должна автоматически иметь доступ к:

```text id="1p0uwj"
camera streams
user management
world configuration
```

---

## Edge и безопасность

Локальный узел платформы может находиться вне центрального доверенного периметра.

Поэтому edge node должен иметь собственную Identity и ограниченную область полномочий.

```text id="3yw3hm"
Edge Node A
   │
   └── Space A permissions

Edge Node B
   │
   └── Space B permissions
```

---

## Пример

Если Edge Node A скомпрометирован, он не должен иметь возможность отправить команду управления камерой из `Space B`.

```text id="d1ernd"
Edge A
  │
  ▼
Camera in Space B
  │
  X
AccessDenied
```

Физическая близость к системе не создаёт глобальное доверие.

---

## Аудит действий

Для значимых действий должна существовать возможность определить:

* кто выполнил действие;
* когда;
* над каким ресурсом;
* с каким результатом;
* откуда пришла команда.

```text id="vx6d5h"
Audit Record
   │
   ├── Subject
   ├── Action
   ├── Resource
   ├── Time
   ├── Result
   └── Correlation
```

Аудит не заменяет Domain Event.

Это отдельная задача наблюдаемости и безопасности.

---

## Пример

Предметное событие:

```text id="e3wraa"
CameraDirectionChanged
```

описывает изменение цифрового мира.

Аудит:

```text id="c5855w"
Operator #17
executed ChangeCameraDirection
on Camera #12
at 16:42
result Success
```

описывает ответственность за действие.

Оба события могут относиться к одной операции, но имеют разный смысл.

---

## Неуспешные попытки также важны

Неудачная авторизация не изменяет Domain Model.

Но может быть важна для аудита безопасности.

```text id="4qwfek"
Unauthorized command
      │
      X
World unchanged
      │
      ▼
Security Audit
```

---

## Пример

Пользователь десять раз пытается получить доступ к чужой камере.

Цифровой мир не меняется.

Однако система безопасности должна иметь возможность увидеть такую последовательность.

---

## Security Context и асинхронность

При асинхронном взаимодействии необходимо решить, должна ли информация о первоначальном субъекте сохраняться.

---

## Пример

```text id="ju9hki"
Operator #17
    │
    ▼
AssignVehicleRoute
    │
    ▼
VehicleRouteAssigned
    │
    ▼
Analytics Handler
```

Analytics может знать:

```text id="39mzxc"
causedBy = Operator #17
```

если это необходимо для аудита или последующих политик.

Но событие не должно автоматически предоставлять обработчику все полномочия первоначального пользователя.

---

## Propagation не означает делегирование прав

Передача Identity через цепочку вызовов не должна автоматически передавать все полномочия.

```text id="vwnx18"
User
 │
 ▼
Service A
 │
 ▼
Service B
```

Service B должен понимать:

* кто первоначальный субъект;
* кто непосредственный вызывающий;
* какие права действительно делегированы.

Это особенно важно в распределённой системе.

---

## Секреты не являются Domain State

API keys, пароли, токены и другие секреты не должны становиться обычными компонентами цифрового мира.

Они относятся к инфраструктуре безопасности.

```text id="nh019s"
Domain Model
   │
   X
API Token
```

Система может хранить ссылку или состояние интеграции, но сам секрет имеет отдельный жизненный цикл и правила защиты.

---

## Пример

Camera Integration может содержать:

```text id="f3slk7"

  └── connected
```

Но не должна публиковать в Domain Model:

```text id="uo2u34"
password = ...
```

## Практическое значение

При реализации любой новой команды необходимо определить:

```text id="l0wgyg"
Кто может её инициировать?
        │
        ▼
Над какими ресурсами?
        │
        ▼
В каком контексте?
        │
        ▼
Какие права необходимы?
        │
        ▼
Как сохраняется Subject?
        │
        ▼
Что необходимо аудитировать?
```

Авторизация не должна добавляться после реализации функциональности.

Она является частью контракта действия.

Каждый этап отвечает за собственную область.

## Инварианты безопасности

Модель безопасности обязана соблюдать следующие правила.

* Любое защищённое действие выполняется от имени определённого субъекта.
* Authentication и Authorization являются различными процессами.
* Идентифицированный субъект не получает права автоматически.
* Security Context сохраняется через границы исполнения там, где он необходим.
* Внутренний сетевой вызов не создаёт доверие автоматически.
* Каждый сервис и интеграция должны иметь собственную системную Identity при выполнении защищённых действий.
* Права ограничиваются минимально необходимым объёмом.
* Отсутствие разрешения означает запрет.
* Авторизация выполняется до изменения Domain State.
* Frontend не является авторитетной границей безопасности.
* Доступ к чтению и изменению рассматривается раздельно.
* Область доступа может ограничиваться конкретной частью цифрового мира.
* Проекции также обязаны соблюдать ограничения доступа.
* Делегирование Identity и прав должно быть явным.
* Секреты не являются обычным Domain State.
* Значимые действия должны иметь возможность аудита.

---

## Архитектурное значение

Модель безопасности определяет, **кто имеет право взаимодействовать с цифровым миром**.

Domain Model определяет, что существует.

Execution Model определяет, как это изменяется.

Security Model добавляет третью обязательную координату:

> Кто имеет право выполнить изменение или получить информацию?

```text id="0dqva7"
                   Subject
                      │
                      ▼
Command ───────► Authorization
                      │
                      ▼
                 Validation
                      │
                      ▼
                 Execution
                      │
                      ▼
                  Digital World
```

Без этой координаты архитектурно корректная команда всё равно может быть недопустимой.

---

## Заключение

Модель безопасности определяет доверие, идентичность субъектов и границы доступа к цифровому миру.

Однако после появления множества модулей, сервисов, интеграций, команд и асинхронных процессов становится недостаточно знать только конечный результат операции.

Необходимо иметь возможность понять:

> Где сейчас находится конкретное исполнение?

> Почему оно завершилось ошибкой?

> Как команда прошла через несколько модулей?

> Какие внешние системы участвовали?

> Где возникла задержка?

> Как состояние системы менялось во времени?

Для этого архитектуре необходим единый подход к **наблюдаемости и трассировке**.
