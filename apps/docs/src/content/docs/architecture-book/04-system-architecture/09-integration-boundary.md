# Интеграционная граница

## Статус

Accepted

---

## Введение

Значительная часть данных цифрового мира поступает из внешних источников.

Это могут быть:

* устройства;
* внешние API;
* корпоративные системы;
* системы видеонаблюдения;
* телеметрические платформы;
* файловые хранилища;
* сторонние сервисы.

Каждая внешняя система использует собственные:

* идентификаторы;
* форматы;
* протоколы;
* правила;
* жизненные циклы;
* модели ошибок.

Эти особенности не должны проникать внутрь архитектурной модели «Призмы».

Для этого существует интеграционная граница.

---

## Что такое интеграционная граница

Интеграционная граница отделяет модель внешней системы от внутренней модели платформы.

Она отвечает за преобразование внешней семантики во внутренние архитектурные контракты.

```text id="x9vq1b"
External System
      │
      ▼
Integration Boundary
      │
      ▼
Internal Contract
      │
      ▼
Prizma
```

Внешняя система заканчивается на границе.

Внутри платформы используются только внутренние понятия.

---

## Пример

GPS-провайдер передаёт сообщение:

```text id="n8gqt2"
deviceId: 481
latitude: 50.595
longitude: 36.587
speed: 12.4
```

Для провайдера `deviceId = 481` является достаточным идентификатором.

Для «Призмы» это внешний идентификатор.

Интеграционный слой должен определить, какому объекту цифрового мира он соответствует.

```text id="xmda0k"
Provider device 481
        │
        ▼
Identity Mapping
        │
        ▼
Object #42
```

После этого формируется внутренняя команда:

```text id="m9u3s1"
UpdateVehiclePosition
```

Внутренняя модель не должна знать о `deviceId = 481`.

---

## Внешний формат не является внутренним контрактом

Полученный JSON, XML, protobuf или иной формат не должен автоматически становиться частью Domain Model.

Транспортный формат существует только на интеграционной границе.

---

## Пример

Внешняя камера возвращает:

```text id="pxd8h9"
{
  "cam_id": "A-791",
  "online": 1,
  "az": 18100,
  "el": -1500
}
```

Внутри платформы не должно появляться состояние:

```text id="wl8v5k"
cam_id
online
az
el
```

только потому, что так устроен внешний API.

Интеграционный адаптер преобразует его:

```text id="97fs4f"
CameraIdentity
Availability
Direction
```

```text id="fny7uc"
External Payload
       │
       ▼
Transformation
       │
       ▼
Internal Model
```

---

## Интеграционный адаптер

Конкретное подключение к внешней системе реализуется адаптером.

Адаптер знает:

* внешний протокол;
* способ авторизации;
* структуру данных;
* особенности ошибок;
* правила повторов;
* внешние идентификаторы.

Он также знает внутренний контракт, в который необходимо преобразовать эти данные.

```text id="thm37w"
External API
     │
     ▼
┌────────────────────┐
│ Integration Adapter│
│                    │
│ Protocol            │
│ Mapping             │
│ Transformation      │
│ Error translation   │
└──────────┬─────────┘
           │
           ▼
Internal Contract
```

Остальная платформа не должна знать деталей внешней системы.

---

## Пример

Первоначально автомобили получают координаты от Provider A.

```text id="nsvj0m"
Provider A
    │
    ▼
Adapter A
    │
    ▼
UpdateVehiclePosition
```

Позже подключается Provider B:

```text id="a027vp"
Provider B
    │
    ▼
Adapter B
    │
    ▼
UpdateVehiclePosition
```

Execution Model получает одну и ту же внутреннюю команду.

Смена поставщика не меняет транспортный модуль.

---

## Anti-Corruption Layer

Интеграционная граница выполняет роль anti-corruption layer.

Её задача — не позволить чужой модели постепенно изменить внутренний язык платформы.

Особенно важно это при подключении крупных корпоративных систем.

---

## Пример

Внешняя система использует понятие:

```text id="a73f94"
AssetUnit
```

и объединяет в него:

* автомобиль;
* камеру;
* здание;
* оборудование.

«Призма» не обязана повторять эту модель.

```text id="j07o8s"
External
AssetUnit
   │
   ▼
Integration Mapping
   │
   ├────────► Vehicle Object
   ├────────► Camera Object
   ├────────► Building Object
   └────────► Equipment Object
```

Интеграционный слой интерпретирует внешний смысл через язык «Призмы».

---

## Внешняя модель не должна определять Domain Model

Особенно опасна ситуация, когда первая интеграция начинает определять внутреннюю архитектуру.

---

## Пример

Первый GPS-провайдер использует:

```text id="yqgl1f"
deviceId
```

Неправильное решение:

```text id="71xt9c"
Object {
  deviceId
}
```

Теперь фундаментальный Object зависит от конкретного способа интеграции.

Правильнее:

```text id="9b8cqx"
Object
   │
   └── Identity

Integration Mapping
   │
   └── external deviceId → Object Identity
```

Если позже появится другой провайдер, Domain Model останется прежней.

---

## Сопоставление идентичности

Одной из ключевых задач интеграции является сопоставление внешней и внутренней идентичности.

Внешняя система может использовать собственный идентификатор.

«Призма» использует собственную Identity.

```text id="qprtxb"
External Identity
       │
       ▼
Identity Mapping
       │
       ▼
Prizma Identity
```

Это соответствие является частью интеграции, а не частью объекта.

---

## Пример

Один автомобиль может иметь:

```text id="iv8kxt"
Prizma Object ID: 42

GPS Provider:
device = 481

Camera Recognition:
vehicle = "CAR-11992"

Maintenance System:
asset = "VH-000342"
```

Все внешние идентификаторы относятся к одному объекту.

```text id="g7b84l"
481 ───────────┐
CAR-11992 ─────┼────► Object #42
VH-000342 ─────┘
```

Объект не должен превращаться в коллекцию идентификаторов всех существующих интеграций.

---

## Входящие интеграции

Входящая интеграция получает данные или запросы от внешней системы.

Она должна преобразовать их в допустимые внутренние взаимодействия.

```text id="cnky5a"
External System
      │
      ▼
Inbound Adapter
      │
      ├────────► Command
      ├────────► Event Import
      └────────► Data Update
                  │
                  ▼
            Execution Model
```

Внешняя система не изменяет состояние напрямую.

---

## Пример

Система видеонаблюдения сообщает, что камера стала недоступна.

```text id="71xmr0"
External Camera Platform
       │
       ▼
Camera Integration Adapter
       │
       ▼
SetCameraUnavailable
       │
       ▼
Validation
       │
       ▼
Execution
```

Даже автоматическая интеграция проходит через внутренний жизненный цикл изменения.

---

## Исходящие интеграции

Платформа также может передавать информацию наружу.

Исходящий адаптер преобразует внутренний контракт в формат внешней системы.

```text id="d2gfem"
Prizma Event
     │
     ▼
Outbound Adapter
     │
     ▼
External Payload
     │
     ▼
External System
```

---

## Пример

После изменения технического состояния автомобиля необходимо обновить внешнюю систему обслуживания.

Внутри платформы произошло:

```text id="k2fznw"
VehicleTechnicalStateChanged
```

Интеграционный адаптер преобразует событие:

```text id="ol8xkz"
VehicleTechnicalStateChanged
       │
       ▼
Maintenance Adapter
       │
       ▼
External API Request
```

Transport Module не должен знать формат API системы обслуживания.

---

## Внешняя ошибка не является доменной ошибкой автоматически

Внешние системы имеют собственные ошибки.

Они не должны напрямую распространяться через внутреннюю архитектуру.

---

## Пример

Provider возвращает:

```text id="uz31n1"
HTTP 503
PROVIDER_GATEWAY_TIMEOUT
```

Это техническая ошибка интеграции.

Внутреннему потребителю может быть важно только:

```text id="1qxuvt"
ExternalSourceUnavailable
```

```text id="g20jda"
Provider Error
     │
     ▼
Adapter
     │
     ▼
Integration Error
```

Внутренние модули не должны зависеть от кодов конкретного поставщика.

---

## Ошибка данных

Отдельно следует различать техническую недоступность и некорректные данные.

---

## Пример

GPS-провайдер прислал:

```text id="h9k36n"
latitude = 500
```

Сообщение успешно доставлено.

Но данные некорректны.

```text id="gg671d"
External Payload
      │
      ▼
Adapter Validation
      │
      X
Invalid External Data
```

Такой пакет не должен превращаться во внутреннюю команду с заведомо некорректным состоянием.

---

## Доверие внешним данным

Внешние данные не должны автоматически считаться истинными.

Интеграционная граница является первым уровнем защиты платформы.

Она может выполнять:

* синтаксическую проверку;
* сопоставление идентичности;
* нормализацию;
* фильтрацию;
* устранение очевидных дублей;
* проверку формата.

После этого предметные проверки всё равно выполняются Execution Model.

```text id="qlpx6f"
External Data
     │
     ▼
Integration Validation
     │
     ▼
Internal Command
     │
     ▼
Domain Validation
     │
     ▼
Execution
```

Это разные уровни проверки.

---

## Пример

Внешний сервис сообщает скорость автомобиля:

```text id="y8o3je"
speed = -50
```

Интеграционная граница может определить, что формат значения недопустим.

Но правило:

> этот автомобиль не может двигаться быстрее установленного ограничения

уже является предметным правилом Transport Module.

```text id="vo9a4d"
Format validation
      │
      ▼
Integration Boundary

Domain validation
      │
      ▼
Transport Module
```

---

## Нормализация единиц измерения

Внешние системы могут использовать разные единицы измерения.

Внутренние контракты платформы должны использовать единый канонический формат.

---

## Пример

Один поставщик передаёт скорость в:

```text id="zm1452"
km/h
```

Другой:

```text id="hr9gqw"
m/s
```

Интеграционные адаптеры приводят значения к внутреннему стандарту:

```text id="oeqb7v"
Provider A: km/h ──┐
                   ├──► Canonical speed
Provider B: m/s ───┘
```

Предметный модуль не должен проверять источник и самостоятельно выбирать формулу преобразования.

---

## Внешнее время

Особое внимание необходимо уделять времени.

Внешняя система может передавать:

* время создания данных;
* время отправки;
* время получения;
* локальное время устройства;
* время без часового пояса.

Интеграционный слой должен явно различать эти понятия.

---

## Пример

Камера создала событие:

```text id="plhkv2"
10:00:00
```

Передала его:

```text id="mr9c0u"
10:00:02
```

Платформа получила:

```text id="0a9fgo"
10:00:05
```

```text id="7ewjiu"
Observed At : 10:00:00
Sent At     : 10:00:02
Received At : 10:00:05
```

Эти значения описывают разные факты.

Интеграция не должна незаметно заменять одно другим.

---

## Повторная доставка

Внешние системы могут отправлять одно сообщение повторно.

Интеграционная граница должна учитывать идемпотентность там, где это необходимо.

```text id="4bbxg9"
External Message #781
        │
        ├────────► delivery 1
        └────────► delivery 2
```

Один внешний факт не должен автоматически становиться двумя внутренними изменениями.

---

## Пример

Провайдер повторно прислал событие недоступности камеры.

```text id="g01xwr"
providerEventId = 951
```

Адаптер определяет, что событие уже было обработано.

```text id="fz79dl"
Event 951
   │
   ├── first → process
   └── second → duplicate
```

---

## Потеря связи с внешней системой

Недоступность внешней системы не должна автоматически нарушать внутреннюю согласованность цифрового мира.

Платформа должна явно моделировать состояние интеграции.

---

## Пример

Связь с GPS-провайдером потеряна.

Это не означает:

```text id="du8nrc"
Vehicle deleted
```

или:

```text id="xgl63m"
Vehicle position = null
```

Автомобиль продолжает существовать.

Меняется достоверность или актуальность поступающих данных.

```text id="h979sw"
Vehicle
   │
   ├── Last Known Position
   └── Position Source Status
           │
           ▼
       unavailable
```

Факт отсутствия обновлений и отсутствие самого объекта — разные состояния.

---

## Интеграция не должна определять доступность платформы

Если внешняя система не участвует непосредственно в текущей границе согласованности, её недоступность не должна останавливать всю платформу.

```text id="gyu6jy"
External Provider
      X

Prizma
  │
  ├── Objects      ✔
  ├── History      ✔
  ├── UI           ✔
  └── Integration  degraded
```

Деградирует конкретная возможность.

Не весь цифровой мир.

---

## Несколько поставщиков одной возможности

Архитектура должна допускать несколько внешних систем, предоставляющих похожие данные.

```text id="9hfp2i"
Provider A ──► Adapter A ──┐
                           │
Provider B ──► Adapter B ──┼──► Internal Contract
                           │
Provider C ──► Adapter C ──┘
```

Внутренняя модель остаётся общей.

---

## Пример

Координаты автомобилей могут поступать:

* от GPS-оборудования;
* от корпоративной транспортной системы;
* из ручного ввода оператора.

Каждый источник использует собственный путь входа.

Но итогом становится единая модель положения объекта.

```text id="th80rq"
GPS ──────────┐
              │
Corporate ────┼────► Position Update
              │
Operator ─────┘
```

Правила приоритета источников должны быть определены отдельно от конкретного транспорта интеграции.

---

## Внешние данные могут конфликтовать

Несколько источников могут сообщать разные состояния одного объекта.

Интеграционный слой не должен произвольно выбирать значение.

Конфликт должен разрешаться согласно явным правилам предметной области.

---

## Пример

GPS сообщает:

```text id="o0ed6m"
Vehicle #42 → Zone A
```

другая система:

```text id="y89e6r"
Vehicle #42 → Zone B
```

Интеграция сохраняет происхождение данных.

```text id="rh6te9"
Source A ──┐
           ├──► Domain Resolution
Source B ──┘
```

Решение о доверенном состоянии является предметным, а не транспортным.

---

## Интеграция и безопасность

Внешняя система всегда находится за границей доверия.

Интеграционный слой должен обеспечивать необходимые механизмы:

* аутентификации;
* авторизации;
* проверки источника;
* ограничения частоты;
* проверки размера данных;
* фильтрации недопустимых сообщений.

Эти механизмы не должны проникать в Domain Model как особенности конкретной интеграции.

---

## Пример

Внешняя система имеет API token.

```text id="3pb34x"
External Token
      │
      ▼
Integration Authentication
      │
      ▼
Trusted Internal Identity
      │
      ▼
Command
```

Предметная команда не должна содержать:

```text id="z70x96"
providerApiToken
```

Техническая авторизация заканчивается до формирования внутреннего контракта.

---

## Наблюдаемость интеграций

Интеграционная граница должна быть наблюдаемой.

Для каждого подключения необходимо иметь возможность определить:

* доступен ли источник;
* когда было получено последнее сообщение;
* сколько сообщений отклонено;
* сколько находится в повторной обработке;
* присутствуют ли ошибки сопоставления;
* насколько данные отстают по времени.

---

## Пример

```text id="j2kymi"
GPS Provider A

Status: connected
Last message: 2 sec ago
Rejected: 3
Retry queue: 0
Identity mapping errors: 1
```

Это операционное состояние интеграции.

Оно не является состоянием автомобиля.

---

## Практическое значение

При подключении новой внешней системы разработчик не должен начинать с вопроса:

> Куда записать полученный JSON?

Правильная последовательность:

```text id="mtkb69"
Внешняя система
       │
       ▼
Какую семантику несут данные?
       │
       ▼
Каким сущностям мира они соответствуют?
       │
       ▼
Как сопоставляется Identity?
       │
       ▼
Какой внутренний контракт нужен?
       │
       ▼
Какие преобразования необходимы?
       │
       ▼
Как обрабатывать ошибки и повторы?
       │
       ▼
Только затем — технический адаптер
```

Это защищает архитектуру от проникновения случайных особенностей внешних систем.

---

## Инварианты интеграционной границы

Любая интеграция обязана соблюдать следующие правила.

* Внешний формат не является внутренней Domain Model.
* Внешняя идентичность не заменяет Identity «Призмы».
* Внешние данные преобразуются во внутренние контракты.
* Входящее изменение проходит стандартный Execution Model.
* Исходящие данные формируются через адаптер.
* Ошибки конкретного поставщика не должны бесконтрольно проникать внутрь модулей.
* Единицы измерения нормализуются на границе.
* Внешнее время интерпретируется явно.
* Повторная доставка учитывается там, где она возможна.
* Недоступность интеграции не означает исчезновение связанных объектов.
* Данные внешнего источника не считаются автоматически истинными.
* Несколько поставщиков одной возможности не должны требовать разных Domain Model.
* Внешняя система не должна определять внутреннюю архитектуру платформы.

## Архитектурное значение

Интеграционная граница защищает внутренний язык «Призмы» от моделей внешних систем.

Она позволяет подключать, заменять и комбинировать поставщиков данных без изменения фундаментальной архитектуры.

```text id="qt2vya"
            External World

      A          B          C
      │          │          │
      ▼          ▼          ▼
   Adapter    Adapter    Adapter
      │          │          │
      └──────┬───┴────┬─────┘
             ▼        ▼
        Internal Contracts
                 │
                 ▼
               Prizma
```

Чем больше интеграций появляется у платформы, тем важнее становится эта граница.

---

## Заключение

Интеграционная граница позволяет подключать внешние системы, не загрязняя ими внутреннюю архитектуру.

Однако развитие «Призмы» не ограничивается подключением данных.

Со временем платформе потребуется добавлять новые возможности, которые невозможно заранее включить в основной продукт:

* новые предметные модули;
* специализированные обработчики;
* дополнительные проекции;
* пользовательские интеграции;
* расширения отдельных отраслей.

Возникает следующий вопрос:

> Как позволить платформе расширяться новыми возможностями, не изменяя её ядро и не превращая каждое расширение в отдельную версию всей системы?

Эту задачу решает **модель расширения платформы**.
