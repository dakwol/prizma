# Ядро платформы

## Статус

Accepted

---

## Введение

В центре архитектуры «Призмы» находится Platform Core — ядро платформы.

Именно ядро содержит фундаментальные понятия цифрового мира и правила их существования.

Вокруг него могут появляться новые модули.

Могут меняться пользовательские интерфейсы.

Могут подключаться новые источники данных.

Могут заменяться технологии хранения и доставки сообщений.

Но фундаментальная модель цифрового мира должна оставаться стабильной.

Эту стабильность обеспечивает Platform Core.

---

## Что такое Platform Core

Platform Core представляет собой минимальный набор архитектурных механизмов, необходимых для существования цифрового мира.

Он определяет:

* какие фундаментальные сущности существуют;
* как определяется их идентичность;
* как представляется состояние;
* как сущности связаны между собой;
* как фиксируется история;
* какие правила должны соблюдаться;
* каким образом модель сохраняет целостность.

Ядро не описывает конкретное предприятие, автомобиль или камеру.

Оно предоставляет универсальный язык, с помощью которого такие сущности могут быть описаны.

---

## Пример

В одном мире «Призмы» существует предприятие.

Внутри него находятся:

* автомобили;
* камеры;
* здания;
* помещения;
* оборудование.

Для Platform Core это не пять фундаментально различных архитектурных сущностей.

Все они могут быть представлены через общие примитивы цифрового мира.

```text
                  Platform Core

                      Object
                        │
          ┌─────────────┼─────────────┐
          │             │             │
          ▼             ▼             ▼
      Автомобиль      Камера        Здание
          │
          ▼
      Компоненты
```

Ядру не требуется знать устройство каждого конкретного типа объекта.

Оно должно знать только правила существования объектов вообще.

---

## Ядро определяет язык платформы

Domain Model можно рассматривать как язык описания цифрового мира.

Его основными конструкциями являются:

```text
World
  │
  ├── Space
  │
  ├── Object
  │     └── Component
  │
  ├── Relation
  │
  ├── Event
  │
  └── Scenario
```

Platform Core реализует фундаментальные правила работы этого языка.

Модули используют его для описания конкретных предметных областей.

---

## Пример

Модуль транспорта не вводит собственное понятие идентичности.

Он использует Identity из Core.

Модуль видеонаблюдения не создаёт собственную модель истории.

Он использует Event.

Модуль здания не создаёт отдельный механизм пространственной вложенности.

Он использует Space.

```text
                  Platform Core
                       │
        ┌──────────────┼──────────────┐
        │              │              │
        ▼              ▼              ▼
   Транспорт     Видеонаблюдение    Здания
        │              │              │
        └──────────────┼──────────────┘
                       │
               Общая модель мира
```

Благодаря этому разные предметные области существуют внутри одной архитектурной модели.

---

## Что входит в Platform Core

В ядро входят только концепции, без которых цифровой мир не способен существовать как единая модель.

К ним относятся:

* World;
* Object;
* Component;
* Relation;
* Event;
* Space;
* Time;
* Scenario;
* Identity;
* State;
* Version;
* Invariant;
* Constraint;
* Consistency.

Также ядро содержит фундаментальные контракты работы с этими сущностями.

---

## Что не входит в Platform Core

Ядро не должно содержать функциональность только потому, что она используется во многих частях системы.

Распространённость функциональности ещё не делает её фундаментальной.

В Core не должны попадать:

* автомобили;
* камеры;
* видеопотоки;
* GPS;
* маршруты конкретного типа транспорта;
* отчёты;
* пользовательские панели;
* уведомления;
* конкретные протоколы интеграции;
* конкретные технологии хранения;
* сетевые транспорты.

Все эти возможности строятся поверх ядра.

---

## Пример

GPS используется большим количеством объектов.

Это не означает, что GPS должен стать частью Platform Core.

Ядро знает только о пространственном состоянии объекта.

```text
GPS
 │
 ▼
Интеграция
 │
 ▼
Команда изменения положения
 │
 ▼
Execution Model
 │
 ▼
Object + Spatial Component
 │
 ▼
Platform Core
```

Если через несколько лет GPS будет заменён другим способом позиционирования, фундаментальная модель мира не изменится.

---

## Критерий принадлежности к ядру

Перед добавлением новой концепции в Platform Core необходимо задать вопрос:

> Может ли цифровой мир существовать без этой концепции?

Если ответ — да, скорее всего, концепция не относится к ядру.

Дополнительный вопрос:

> Будет ли эта концепция иметь одинаковый смысл независимо от предметной области?

Если нет, она должна находиться в модуле.

---

## Пример

Рассмотрим две концепции.

### Identity

Без идентичности невозможно однозначно различать сущности.

Она необходима автомобилю, камере, зданию и любой другой сущности.

Следовательно:

```text
Identity → Platform Core
```

### Video Stream

Без видеопотока цифровой мир продолжает существовать.

Кроме того, видеопоток относится только к определённым предметным областям.

Следовательно:

```text
Video Stream → Module
```

Этот принцип позволяет защищать ядро от постепенного разрастания.

---

## Ядро должно быть небольшим

Platform Core намеренно должен оставаться минимальным.

Добавить функциональность в ядро легко.

Удалить её значительно сложнее.

Чем больше концепций находится в Core, тем больше частей системы начинают зависеть от них.

Со временем такая связанность делает развитие платформы дорогим.

```text
Маленькое Core

        Core
      /  |  \
     /   |   \
    A    B    C


Разросшееся Core

    ┌─────────────────────┐
    │        Core         │
    │ A B C D E F G H I J │
    └─────────────────────┘
       ▲ ▲ ▲ ▲ ▲ ▲ ▲ ▲
       зависимости везде
```

Поэтому добавление новой концепции в ядро должно рассматриваться как архитектурное решение, а не как удобное место для общего кода.

---

## Ядро не является shared-библиотекой

Platform Core нельзя использовать как место для хранения всего переиспользуемого кода.

Переиспользуемость и фундаментальность — разные свойства.

Например:

* форматирование даты может использоваться всей платформой;
* HTTP-клиент может использоваться десятками модулей;
* логирование необходимо почти каждому сервису.

Но ни одна из этих возможностей не является частью модели цифрового мира.

```text
                    Platform Core
                          │
                   модель мира


Shared / Infrastructure
      │
      ├── Logging
      ├── HTTP
      ├── Serialization
      └── Utilities
```

Эти области должны оставаться архитектурно разделёнными.

---

## Ядро не зависит от модулей

Platform Core не должно знать, какие прикладные модули существуют в системе.

Зависимость направлена только в одну сторону.

```text
Транспорт ───────┐
                 │
Камеры ──────────┼────► Platform Core
                 │
Здания ──────────┘
```

Но недопустимо:

```text
Platform Core
     │
     ▼
Модуль транспорта
```

Иначе ядро перестаёт быть универсальным.

---

## Ядро не зависит от инфраструктуры

Фундаментальные правила цифрового мира не должны определяться способом их технической реализации.

Platform Core не должен зависеть от:

* конкретной базы данных;
* брокера сообщений;
* HTTP;
* WebSocket;
* файловой системы;
* облачного провайдера;
* конкретного фреймворка пользовательского интерфейса.

```text
            Infrastructure
          /       |        \
         ▼        ▼         ▼
     Database   Broker    Network
         \        |         /
          \       |        /
           ▼      ▼       ▼
              Adapters
                 │
                 ▼
           Platform Core
```

Инфраструктура адаптируется к контрактам ядра.

Не ядро адаптируется к инфраструктуре.

---

## Стабильность ядра

Platform Core является наиболее стабильной частью архитектуры.

Это не означает, что ядро никогда не изменяется.

Изменения возможны.

Однако изменение фундаментальной концепции должно рассматриваться как изменение самой архитектурной модели платформы.

Например, изменение API конкретного GPS-провайдера не является изменением Core.

Изменение определения Object или Relation — является.

---

## Пример

Предприятие заменяет систему видеонаблюдения.

Было:

```text
Camera Provider A
```

Стало:

```text
Camera Provider B
```

Изменяются интеграционные адаптеры.

Возможно, изменяется модуль видеонаблюдения.

Platform Core остаётся прежним.

```text
Provider A ──X

Provider B
    │
    ▼
Camera Module
    │
    ▼
Platform Core
```

Но если платформа решит изменить фундаментальную модель отношения между объектами, это уже затрагивает само ядро.

---

## Расширение через модули

Большая часть развития «Призмы» должна происходить не через изменение Platform Core, а через создание и развитие модулей.

Core предоставляет стабильные примитивы.

Модули комбинируют их для описания предметной области.

```text
                       Platform Core
                            │
            ┌───────────────┼───────────────┐
            │               │               │
            ▼               ▼               ▼
        Transport        Cameras         Buildings
            │               │               │
            └───────────────┼───────────────┘
                            ▼
                       Digital World
```

Таким образом платформа может расширяться практически неограниченно без постоянного изменения фундаментальной архитектуры.

---

## Практическое значение

При разработке новой функциональности команда не должна начинать с изменения Platform Core.

Сначала необходимо определить, может ли задача быть реализована существующими фундаментальными примитивами.

Например, при добавлении контроля топлива автомобиля:

не нужно добавлять `Fuel` в Core.

Необходимо определить соответствующий компонент транспортного модуля.

```text
Vehicle
   │
   ├── PositionComponent
   ├── MovementComponent
   └── FuelComponent
```

Core при этом продолжает работать только с общей концепцией Component.

Это позволяет предметной модели развиваться независимо от ядра.

---

## Инварианты Platform Core

Platform Core обязан соблюдать следующие правила.

* Core содержит только фундаментальные концепции цифрового мира.
* Core не зависит от прикладных модулей.
* Core не зависит от пользовательских интерфейсов.
* Core не зависит от конкретных внешних систем.
* Core не зависит от конкретных технологий хранения и передачи данных.
* Переиспользуемость сама по себе не является причиной добавления функциональности в Core.
* Предметная функциональность реализуется через модули.
* Изменение Core рассматривается как изменение фундаментальной архитектуры платформы.
* Core должен оставаться минимальным.

---

## Архитектурное значение

Platform Core является стабильным центром «Призмы».

Он предоставляет общий язык, на котором различные предметные области описывают свои цифровые модели.

Благодаря этому автомобили, камеры, здания, оборудование и будущие типы сущностей могут существовать внутри одного цифрового мира, не требуя отдельной архитектуры для каждой предметной области.

---

## Заключение

Platform Core намеренно ничего не знает о большинстве возможностей «Призмы».

Его задача — предоставить минимальный и стабильный фундамент.

Вся прикладная функциональность строится поверх этого фундамента.

Следовательно, возникает следующий вопрос:

> Как добавлять новые предметные возможности, не расширяя ядро и не связывая между собой независимые части платформы?

Для этого архитектура использует модули.
