# Обзор архитектуры

## Статус

Accepted

---

## Введение

Первые разделы архитектурной книги определили две фундаментальные части платформы.

**Domain Model** отвечает на вопрос:

> Что существует в цифровом мире?

**Execution Model** отвечает на вопрос:

> Как цифровой мир изменяется?

Теперь необходимо определить, как эти модели организованы внутри самой платформы.

Системная архитектура описывает основные части «Призмы», их ответственность и правила взаимодействия.

Она не определяет конкретные технологии реализации.

Она определяет архитектурные границы системы.

---

## Общая структура платформы

Платформа состоит из нескольких крупных областей ответственности.

```text
                    ┌──────────────────────────────┐
                    │       Пользователи          │
                    └──────────────┬───────────────┘
                                   │
                    ┌──────────────▼───────────────┐
                    │       Представления         │
                    │  3D • Карта • UI • API      │
                    └──────────────┬───────────────┘
                                   │
                 ┌─────────────────▼─────────────────┐
                 │         Execution Model           │
                 │ Command → Validation → Transaction│
                 └─────────────────┬─────────────────┘
                                   │
                    ┌──────────────▼───────────────┐
                    │        Platform Core         │
                    │                              │
                    │         World Model          │
                    └──────────────┬───────────────┘
                                   │
             ┌─────────────────────┼─────────────────────┐
             │                     │                     │
             ▼                     ▼                     ▼
        Интеграции             Хранилища            Синхронизация
```

Каждый слой решает собственную задачу.

Ни один из них не должен подменять остальные.

---

## Представления

Представления являются точкой взаимодействия пользователя и внешних потребителей с цифровым миром.

К ним могут относиться:

* карта;
* трёхмерная сцена;
* таблицы;
* панели мониторинга;
* мобильный интерфейс;
* программный API.

Представления отображают цифровой мир и формируют команды.

Они не определяют правила существования мира.

---

## Пример

Оператор открывает карту предприятия.

На карте отображаются автомобили и камеры.

Оператор выбирает автомобиль и назначает ему новую точку маршрута.

Интерфейс не изменяет объект напрямую.

Он формирует команду и передаёт её в Execution Model.

```text
Оператор
   │
   ▼
Карта
   │
   ▼
Команда
   │
   ▼
Execution Model
```

Таким образом пользовательский интерфейс остаётся представлением, а не источником бизнес-правил.

---

## Execution Model

Execution Model является единственным архитектурным путём изменения цифрового мира.

Он принимает команды и выполняет их через последовательность механизмов:

```text
Command
   │
   ▼
Validation
   │
   ▼
Transaction
   │
   ▼
Consistency Boundary
```

После успешного исполнения возникает новое согласованное состояние мира.

---

## Пример

Камера передаёт новое положение наблюдаемого автомобиля.

Полученное изменение не записывается напрямую в объект.

Система формирует команду обновления состояния.

Команда проходит проверку.

После этого изменение применяется внутри транзакции.

Только затем новое состояние становится частью цифрового мира.

---

## Platform Core

Platform Core содержит фундаментальные механизмы цифрового мира.

Именно здесь существуют базовые понятия:

* World;
* Object;
* Component;
* Relation;
* Event;
* Scenario;
* Identity;
* State;
* Version;
* Invariant.

Core определяет правила, но не знает о конкретных пользовательских интерфейсах или внешних системах.

---

## Пример

В цифровом мире существует автомобиль.

Для Core это объект с идентичностью, компонентами, отношениями и состоянием.

Core не знает, что этот объект отображается:

* на карте;
* в трёхмерной сцене;
* в мобильном приложении;
* в аналитическом отчёте.

Все эти способы отображения существуют вне ядра.

```text
                 Представления
            ┌────────┬────────┬────────┐
            ▼        ▼        ▼        ▼
          Карта      3D      UI       API
              \       |       |       /
               \      |       |      /
                └─────▼───────▼─────┘
                     Object
                 Platform Core
```

---

## Модули

Отраслевая и прикладная функциональность строится поверх Platform Core в виде модулей.

Модуль определяет новые:

* компоненты;
* типы отношений;
* команды;
* проверки;
* сценарии;
* проекции.

При этом модуль не изменяет фундаментальные правила Core.

---

## Пример

Модуль видеонаблюдения может добавить:

* компонент видеопотока;
* состояние доступности камеры;
* команды управления камерой;
* проекцию списка видеопотоков.

Но ему не требуется изменять понятие Object.

Он использует уже существующую модель объекта.

```text
Platform Core
      │
      ├────────► Модуль транспорта
      ├────────► Модуль видеонаблюдения
      ├────────► Модуль аналитики
      └────────► Другие модули
```

Core остаётся неизменным.

Модули расширяют его возможности.

---

## Интеграции

Интеграции связывают «Призму» с внешними системами.

Они отвечают за преобразование внешних данных в архитектурные контракты платформы.

Внешняя система не должна напрямую изменять внутреннюю модель мира.

---

## Пример

GPS-сервис передаёт координаты автомобиля.

Интеграционный адаптер преобразует данные во внутреннюю команду.

```text
GPS-сервис
    │
    ▼
Integration Adapter
    │
    ▼
Command
    │
    ▼
Execution Model
    │
    ▼
Digital World
```

Таким образом смена внешнего поставщика GPS не требует изменения Domain Model.

---

## Хранилища

Хранилища отвечают за долговременное сохранение состояния и истории цифрового мира.

Архитектура не связывает модель мира с конкретным способом хранения.

Хранилище является техническим механизмом сохранения модели, но не определяет её смысл.

---

## Пример

Состояние объекта может сохраняться одним механизмом, история событий — другим.

Для Domain Model это не имеет значения.

```text
              Platform Core
                   │
          ┌────────┴────────┐
          ▼                 ▼
   Текущее состояние      История
          │                 │
          ▼                 ▼
     Хранилище A        Хранилище B
```

Технологии хранения могут измениться, не меняя архитектурную модель.

---

## Синхронизация

После изменения цифрового мира информация должна распространяться на другие узлы и представления.

Этим занимается слой синхронизации.

Он работает после завершения изменения и не входит в транзакционную границу самого изменения.

---

## Пример

Автомобиль изменил положение.

После завершения транзакции синхронизация передаёт изменение:

* на карту оператора;
* на мобильный интерфейс;
* в аналитический модуль;
* на другой узел платформы.

```text
Digital World
     │
     ▼
Synchronization
     │
     ├────────► Карта
     ├────────► Mobile
     ├────────► Analytics
     └────────► Другой узел
```

---

## Направление зависимостей

Внешние слои могут зависеть от внутренних архитектурных контрактов.

Внутренние слои не должны зависеть от внешних.

```text
Представления
      │
      ▼
Execution Model
      │
      ▼
Platform Core
```

Но никогда наоборот.

Platform Core не должен знать:

* каким интерфейсом пользуется оператор;
* где физически хранятся данные;
* какой транспорт используется для сообщений;
* какая внешняя система предоставляет информацию.

---

## Практическое значение

Такое разделение позволяет независимо развивать разные части платформы.

Например, команда может:

* заменить карту;
* создать новый интерфейс;
* добавить новый модуль;
* сменить механизм хранения;
* подключить новый внешний источник данных;

не изменяя фундаментальную модель цифрового мира.

Это снижает связанность системы и позволяет развивать платформу в течение многих лет без постоянного переписывания ядра.

---

## Инварианты системной архитектуры

Системная архитектура обязана соблюдать следующие правила.

* Platform Core не зависит от пользовательских представлений.
* Внешние системы не изменяют цифровой мир напрямую.
* Любое изменение проходит через Execution Model.
* Модули расширяют Core, но не изменяют его фундаментальные сущности.
* Проекции не являются источником истины.
* Хранилища не определяют Domain Model.
* Синхронизация происходит за пределами границы согласованности.
* Направление зависимостей идёт от внешних слоёв к внутренним.

---

## Архитектурное значение

System Architecture соединяет ранее определённые Domain Model и Execution Model с реальной структурой платформы.

Она задаёт границы ответственности между ядром, исполнением, модулями, представлениями, интеграциями и инфраструктурой.

Благодаря этим границам «Призма» может развиваться как единая платформа, а не как набор постепенно связанных между собой приложений.

---

## Заключение

В центре системной архитектуры находится Platform Core.

Именно он содержит фундаментальную модель цифрового мира и остаётся стабильным независимо от количества модулей, интеграций и пользовательских приложений.

Поэтому следующим шагом необходимо точно определить:

> Что входит в Platform Core, а что никогда не должно становиться частью ядра?
