# Распространение и проекции

## Статус

Accepted

---

## Введение

Изменение цифрового мира не должно требовать синхронного обновления каждого потребителя внутри одной гигантской транзакции.

После commit изменение распространяется дальше.

---

## Модель

```text
Authoritative Change
        │
        ▼
      Event
        │
        ├── Projection A
        ├── Projection B
        ├── Realtime
        ├── Integration
        └── Automation
```

---

## Проекция

Projection оптимизирована под конкретный способ чтения.

Например:

```text
Vehicle State
    │
    ├── Map Projection
    ├── Search Projection
    ├── History View
    └── Analytics Projection
```

Они могут обновляться независимо.

---

## Eventual consistency

В определённый момент:

```text
Domain State = v105
Map          = v105
Analytics    = v104
```

Это допустимо, если архитектурный контракт допускает задержку аналитической проекции.

Через некоторое время:

```text
Domain State = v105
Map          = v105
Analytics    = v105
```

---

## Rebuild

Производное состояние должно по возможности восстанавливаться.

```text
Source of Truth
      │
      ▼
Rebuild
      │
      ▼
Projection
```

Это важное отличие projection от авторитетного состояния.

---

## Realtime

Realtime — транспорт доставки актуального представления клиенту.

Он не становится новым источником истины.

```text
World
  │
Projection
  │
Realtime
  │
Client
```

После reconnect клиент должен иметь способ восстановить актуальное состояние.

---

## Инварианты

- Post-commit propagation отделена от Domain Transaction.
- Projection является производным состоянием.
- Допустимая задержка projection определяется контрактом.
- Realtime не является источником истины.
- Consumer поддерживает idempotency там, где доставка может повторяться.
- Производные данные имеют rebuild/recovery strategy.

---

## Заключение

Когда система становится распределённой, ошибки и задержки неизбежны. Следующая страница показывает, как reliability удерживает эту цепочку.
