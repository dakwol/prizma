# Architecture Decision Records

## Статус

Accepted

---

## Введение

Через два года команда часто видит только итоговое решение.

Она уже не знает:

- почему оно появилось;
- какие ограничения существовали;
- какие альтернативы отклонили.

ADR сохраняет контекст решения.

---

## Когда нужен ADR

ADR нужен, если решение:

- меняет архитектурную границу;
- создаёт новый fundamental concept;
- меняет ownership;
- вводит новый deployment unit;
- меняет consistency model;
- создаёт существенную технологическую зависимость;
- делает решение, которое дорого отменять.

---

## Структура

```text
Context
  │
Decision
  │
Consequences
  │
Alternatives
  │
Status
```

---

## Статусы

```text
Proposed
  │
Accepted
  │
Deprecated / Superseded
```

Принятое решение не переписывается задним числом.

Новое решение создаёт новый ADR и ссылается на старый.

---

## Пример

```text
ADR-017
Title: Separate Media Plane
Status: Accepted
```

Причина:

- media workload стал независимым bottleneck;
- требуются отдельные resource limits;
- Domain Camera ownership остаётся прежним.

Такой ADR объясняет не только «что сделали», но и что сознательно не изменили.

---

## ADR не заменяет документацию

ADR фиксирует решение.

Архитектурная книга объясняет постоянную модель.

Техническая документация описывает реализацию.

```text
ADR → why
Architecture Book → rules
Technical Docs → how
```

---

## Инварианты

- ADR создаётся для архитектурно значимых решений.
- Accepted ADR не переписывается для изменения истории.
- Superseding decision ссылается на предыдущий ADR.
- ADR содержит последствия, а не только решение.
- ADR не используется для каждого локального рефакторинга.
- Архитектурная книга обновляется, если ADR меняет постоянные правила.

---

## Заключение

ADR фиксирует решение. Но крупное изменение часто требует обсуждения до принятия.

Для этого используется RFC.
