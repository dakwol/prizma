# Модель нагрузки

## Статус

Accepted

## Введение

Количество пользователей само по себе плохо описывает нагрузку.

Один пользователь может открыть статичную карточку, а другой — карту с тысячами объектов и несколькими видеопотоками.

## Основные измерения

```text
Workload
 ├── objects
 ├── active users
 ├── commands/sec
 ├── reads/sec
 ├── events/sec
 ├── realtime updates/sec
 ├── history volume
 ├── media streams
 └── spatial operations
```

## Read workload

Чтение текущего состояния обычно значительно чаще изменений.

Поэтому read path может масштабироваться отдельно через проекции, индексы и кэширование.

## Write workload

Команды должны сохранять согласованность цифрового мира.

```text
Command
  │
Validation
  │
Transaction
  │
State change
```

Write scaling не должно обходить правила владения состоянием.

## Realtime workload

Автомобиль может обновлять положение несколько раз в секунду.

```text
1000 vehicles × 2 updates/sec
= 2000 updates/sec
```

Но не каждый пользователь должен получать каждое обновление каждого объекта.

## Burst workload

Нагрузка может быть неравномерной.

```text
normal ──────────┐
                 │ spike
                 ▼
             ███████
```

Capacity planning учитывает не только среднее значение, но и пики.

## Инварианты

- Нагрузка описывается несколькими измерениями.
- Reads, writes, realtime, media и analytics рассматриваются раздельно.
- Средняя нагрузка не заменяет оценку peak load.
- Масштабирование write path сохраняет data ownership.
- Realtime fan-out учитывается отдельно от частоты поступления событий.

## Заключение

После определения нагрузки необходимо установить допустимые временные характеристики системы — latency budgets.
