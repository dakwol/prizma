# Кэширование

## Статус

Accepted

## Введение

Cache ускоряет доступ ценой появления ещё одной копии данных.

Поэтому главный вопрос кэша — не где его разместить, а насколько допустимо использовать устаревшее значение.

## Cache не является источником истины

```text
Authoritative State
       │
       ▼
      Cache
       │
       ▼
     Consumer
```

Потеря cache не должна означать потерю предметных данных.

## Cacheability

Не каждое чтение следует кэшировать.

Хорошие кандидаты:

- дорогие производные вычисления;
- редко меняющиеся справочные данные;
- повторяемые read projections;
- статические ресурсы.

Плохой кандидат — значение, которое должно быть строго актуальным для принятия команды.

## Invalidation

```text
There are only two hard things...
```

Архитектурно важен не конкретный алгоритм invalidation, а определённая freshness policy.

Возможны:

- TTL;
- event invalidation;
- versioned cache;
- explicit refresh.

## Cache stampede

После истечения популярного ключа множество запросов могут одновременно пересчитывать значение.

```text
Key expires
   │
   ├── request A
   ├── request B
   └── request C
          │
          ▼
      same expensive work
```

Для дорогих значений нужна защита от stampede.

## Client cache

Frontend также является уровнем кэширования.

Он должен понимать version/freshness и корректно reconciliate данные после realtime reconnect.

## Инварианты

- Cache не является Domain source of truth.
- Для кэшируемых данных определена freshness policy.
- Строго актуальные проверки не используют потенциально stale cache без явной семантики.
- Потеря cache восстанавливаема.
- Популярные дорогие ключи защищаются от stampede при необходимости.
- Client cache участвует в общей модели freshness.

## Заключение

После оптимизации отдельных путей необходимо заранее понимать пределы инфраструктуры. Это задача capacity planning.
