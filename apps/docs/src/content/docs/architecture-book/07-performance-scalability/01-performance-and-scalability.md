# Производительность и масштабирование

## Статус

Accepted

## Введение

Корректная и надёжная система всё равно может стать непригодной, если время ответа растёт вместе с количеством объектов, пользователей, событий и потоков данных.

«Призма» должна масштабироваться не абстрактно, а относительно конкретных типов нагрузки.

## Основной принцип

```text
Growth
  │
  ▼
Measured workload
  │
  ▼
Known bottleneck
  │
  ▼
Targeted scaling
```

Масштабирование не начинается с добавления серверов. Сначала определяется, какой ресурс ограничивает систему.

## Производительность является свойством пути

Пользовательская операция проходит несколько компонентов.

```text
Client
  │
API
  │
Domain
  │
Storage
  │
Projection
  │
Client
```

Общее время определяется всем critical path.

## Пример

На карте отображаются автомобили и камеры.

Рост количества объектов может увеличить:

- размер snapshot;
- число realtime updates;
- стоимость spatial query;
- нагрузку на сериализацию;
- работу frontend;
- GPU rendering.

Ускорение только API не решит проблему, если bottleneck находится в браузере.

## Масштабирование по измерениям

Архитектурное решение должно опираться на:

- latency;
- throughput;
- concurrency;
- resource utilization;
- queue lag;
- data volume;
- frontend frame time.

## Инварианты

- Производительность измеряется end-to-end.
- Оптимизация выполняется по измеренному bottleneck.
- Масштабирование не должно нарушать Domain Invariants.
- Разные типы нагрузки рассматриваются отдельно.
- Производительность является частью архитектурных контрактов критических путей.

## Заключение

Для масштабирования сначала необходимо определить, какую нагрузку создаёт платформа. Это задача workload model.
