# Идемпотентность

## Статус

Accepted

## Введение

Клиент, broker или интеграция могут повторить доставку. Поэтому система должна отличать новое намерение от повторной доставки уже обработанного.

## Основной принцип

```text
Intent #42
 ├── delivery 1 → effect
 └── delivery 2 → no second effect
```

## Idempotency Key

Команда, способная быть повторённой транспортом, получает стабильный идентификатор намерения.

```text
Command
 ├── CommandId
 └── Payload
```

Повтор использует тот же `CommandId`. Новое осознанное действие получает новый.

## Пример

`AssignVehicleRoute` был committed, но HTTP-ответ потерян. Клиент повторяет команду с тем же ID. Платформа возвращает известный результат и не создаёт второе предметное изменение.

## Payload не определяет намерение

Два одинаковых payload могут быть двумя отдельными действиями. Deduplication только по содержимому поэтому недостаточна.

## Commit

Для критической операции запись обработанного CommandId должна быть согласована с Domain commit.

```text
Transaction
 ├── Domain change
 └── Processed CommandId
```

## Event handlers

Обработчик события предполагает повторную доставку.

```text
Event #781
 ├── delivery 1
 └── delivery 2
```

Повтор одной версии не должен создавать второй эффект.

## Инварианты

- Повтор одного намерения не создаёт новый Domain effect.
- Identity намерения не выводится только из payload.
- Новый осознанный запрос имеет новую Identity.
- Критическая idempotency information согласуется с commit.
- Event handlers готовы к повторной доставке.
- Idempotency и optimistic concurrency являются разными механизмами.

## Заключение

Идемпотентность делает повторы безопаснее, но не защищает от длительно падающей зависимости. Далее необходима изоляция отказов.
