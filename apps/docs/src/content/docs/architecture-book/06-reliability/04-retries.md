# Повторные попытки

## Статус

Accepted

## Введение

Retry полезен только тогда, когда следующая попытка имеет разумную вероятность завершиться иначе. Бесконтрольные повторы увеличивают нагрузку и способны усилить отказ.

## Retryable failures

Повтор может быть допустим при кратком сетевом сбое, временной перегрузке или явно retryable ответе зависимости.

Не повторяются автоматически Domain rejection, AccessDenied, validation errors, неверные credentials и несовместимые контракты.

## Backoff и jitter

```text
Attempt 1
  │ 100ms
Attempt 2
  │ 200ms
Attempt 3
```

К задержке добавляется jitter, чтобы множество клиентов не повторяли запрос одновременно.

## Retry budget

Количество попыток ограничено.

```text
attempt 1
attempt 2
attempt 3
   │
   X
final failure
```

## Retry amplification

```text
API ×3
 │
Service ×3
 │
Adapter ×3

= up to 27 downstream calls
```

У retry policy должен быть определённый владелец.

## Очереди и DLQ

Повторная доставка сообщения является нормальным сценарием. Persistent failure после исчерпания попыток переводится в наблюдаемое quarantine/DLQ состояние, а не повторяется бесконечно.

## Инварианты

- Retry применяется только к transient failures.
- Используются ограниченный budget, backoff и при необходимости jitter.
- Deadline не продлевается бесконечно.
- Неидемпотентные операции не повторяются без защиты.
- Retry не усиливается независимо на каждом слое.
- Persistent failures становятся наблюдаемыми.

## Заключение

Безопасный retry требует распознавания повторной доставки одного намерения. Эту задачу решает идемпотентность.
