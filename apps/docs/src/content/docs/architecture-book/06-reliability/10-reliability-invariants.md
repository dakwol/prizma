# Инварианты надёжности

## Статус

Accepted

## Основной принцип

```text
Failure is expected.
Corruption is not.
```

Платформа ожидает отказ компонентов, но не принимает нарушение согласованности как цену доступности.

## Обязательные правила

### Частичный отказ локализуется

Отказ одной возможности не останавливает независимые части платформы.

### Внешние зависимости ненадёжны

Сеть, сервис и внешний provider могут отвечать медленно, не отвечать или выполнить операцию без доставки ответа.

### Ожидание ограничено

Потенциально блокирующие операции имеют timeout или явный lifecycle.

### Retry осознанный

Ошибка сначала классифицируется. Retry используется только там, где повтор способен помочь.

### Повтор одного намерения безопасен

Транспортный дубль не создаёт второй предметный эффект.

### Перегрузка ограничивается

Применяются необходимые bulkhead, rate limit, queue, backpressure, circuit breaker и load shedding механизмы.

### Деградация явная

```text
fresh
stale
unknown
unavailable
```

не смешиваются.

### Security не деградирует в разрешение

Неизвестный результат критической авторизации по умолчанию означает deny.

### Restart не равен recovery

```text
Started ≠ Ready ≠ Recovered
```

### Проекции восстанавливаемы

Производное состояние имеет resume/replay/rebuild strategy.

### Reconciliation имеет владельца

Конфликт разрешается по авторитетности состояния или явному предметному правилу.

### Recovery наблюдаем

Lag, backlog, retry, DLQ, recovery progress и reconciliation conflicts доступны Observability.

### Критическое состояние защищено

Для него определены durability, backup, restore и при необходимости replication, RPO и RTO.

### Backup проверяется

Возможность восстановления подтверждается restore test.

### Ошибка не скрывается fallback-значением

Недоступность не маскируется валидным предметным значением вроде `0`, если это меняет смысл данных.

## Полный жизненный цикл отказа

```text
GPS Provider X
      │
    Timeout
      │
 Retry policy
      │
 Circuit opens
      │
Integration unavailable
      │
      ├── last position retained
      ├── freshness becomes stale
      ├── alert generated
      └── unrelated modules continue
      │
Provider recovers
      │
Circuit half-open
      │
Connection restored
      │
Reconciliation
      │
Fresh telemetry
```

## Проверка новой возможности

Перед выпуском необходимо ответить:

1. Какие зависимости имеет функция?
2. Что произойдёт при отказе каждой?
3. Какой timeout используется?
4. Какие ошибки retryable?
5. Как обеспечивается идемпотентность?
6. Как ограничивается перегрузка?
7. Как выглядит degraded mode?
8. Как пользователь видит stale data?
9. Как происходит restart/recovery?
10. Нужны ли replay и reconciliation?
11. Какие метрики показывают деградацию?
12. Требуются ли backup, RPO и RTO?

## Архитектурное значение

```text
Normal
  │
Failure
  │
Detection
  │
Isolation
  │
Controlled degradation
  │
Recovery
  │
Reconciliation
  │
Normal
```

Цель — не система, в которой ничего не ломается, а система, которая при отказе сохраняет смысл цифрового мира и имеет определённый путь обратно к нормальной работе.
