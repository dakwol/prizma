# Таймауты и отмена

## Статус

Accepted

## Введение

Ожидание потребляет соединения, память и вычислительные ресурсы. Потенциально блокирующая операция не должна ждать бесконечно.

## Таймаут как часть контракта

```text
Caller
 ├── Request
 └── Time budget
       │
       ▼
     Callee
```

## Пример

Если Camera API зависло без timeout, новые запросы продолжают накапливаться. Локальная проблема камеры постепенно становится проблемой API «Призмы».

С timeout операция завершается контролируемым failure.

## Timeout и cancellation

Timeout ограничивает ожидание. Cancellation сообщает нижележащей операции, что её результат больше не нужен.

```text
Caller timeout
     │
Cancellation
     │
Downstream work stops
```

## Deadline propagation

Если первоначальный бюджет равен 5 секундам и первый компонент потратил 2 секунды, следующий получает оставшиеся 3 секунды, а не новый полный бюджет.

## Commit boundary

Потеря соединения после commit не отменяет уже произошедшее изменение.

```text
Client → Command → Commit ✔ → X Response
```

Клиент может не знать результата, но цифровой мир уже изменён.

## Инварианты

- Внешние блокирующие операции имеют timeout.
- Cancellation распространяется вниз, когда это безопасно.
- Нижележащие вызовы учитывают оставшийся deadline.
- Retry не сбрасывает общий временной бюджет.
- Client disconnect не отменяет committed изменение.
- Долгие операции не маскируются под бесконечные HTTP-запросы.

## Заключение

Некоторые временные ошибки допускают повтор. Следующая страница определяет правила retry.
