# Наблюдаемость

## Статус

Accepted

---

## Введение

По мере развития «Призмы» одно пользовательское действие может проходить через несколько модулей, единиц развёртывания, интеграций и асинхронных процессов.

Сам факт того, что система вернула ошибку или стала работать медленнее, уже недостаточен для понимания причины.

Необходимо иметь возможность ответить:

- что произошло;
- где произошло;
- когда произошло;
- какое исполнение было затронуто;
- какие компоненты участвовали;
- какое состояние наблюдалось;
- где возникла задержка;
- почему операция завершилась ошибкой.

Эту возможность обеспечивает наблюдаемость.

---

## Что такое наблюдаемость

Наблюдаемость — это способность определить внутреннее состояние работающей системы на основании сигналов, которые она создаёт во время исполнения.

Она не является отдельным экраном мониторинга.

Не является набором логов.

Не является конкретным продуктом для сбора метрик.

Это архитектурное свойство системы.

```text
             Работающая система
                    │
        ┌───────────┼───────────┐
        ▼           ▼           ▼
       Logs       Metrics      Traces
        │           │           │
        └───────────┼───────────┘
                    ▼
              Наблюдаемость
                    │
                    ▼
          Понимание состояния
```

---

## Пример

Оператор изменяет направление камеры.

Внешне операция выглядит простой:

```text
Operator
   │
   ▼
ChangeCameraDirection
   │
   ▼
Success
```

Внутри платформы она может пройти значительно более длинный путь:

```text
UI
 │
 ▼
API
 │
 ▼
Authorization
 │
 ▼
Camera Module
 │
 ▼
Device Adapter
 │
 ▼
External Camera System
 │
 ▼
Event
 │
 ▼
Projection
```

Если операция заняла восемь секунд, наблюдаемость должна позволить определить, на каком именно участке возникла задержка.

---

## Наблюдаемость не изменяет цифровой мир

Сигналы наблюдаемости описывают работу системы.

Они не являются предметным состоянием цифрового мира.

Например:

```text
CameraDirectionChanged
```

является Domain Event.

А запись:

```text
Camera command processed in 183 ms
```

является операционным сигналом.

Эти данные имеют разный смысл.

---

## Пример

Автомобиль изменил положение.

Domain Model фиксирует факт:

```text
VehiclePositionChanged
```

Observability может дополнительно зафиксировать:

```text
integration.gps.message.received
execution.duration = 24ms
projection.lag = 110ms
```

Потеря операционной телеметрии не должна изменять историю автомобиля.

Потеря Domain Event — уже нарушение модели мира.

---

## Наблюдаемость должна проходить через границы

Одно исполнение может пересекать:

- процессы;
- сервисы;
- модули;
- очереди;
- интеграции;
- edge-узлы.

При этом наблюдаемость должна сохранять связь между всеми частями операции.

```text
Execution #812
     │
     ├── API
     ├── Transport Module
     ├── Event Bus
     ├── Projection Worker
     └── External Integration
```

Если после каждой границы операция становится новым несвязанным набором логов, архитектура наблюдаемости не выполняет свою задачу.

---

## Наблюдаемость и контекст исполнения

Каждое значимое исполнение должно иметь контекст, позволяющий связать его сигналы.

Например:

```text
ExecutionId
CorrelationId
TraceId
SubjectId
WorldId
Module
DeploymentUnit
```

Не каждый сигнал обязан содержать весь набор явно.

Но система должна позволять восстановить связь.

---

## Пример

Оператор назначает автомобилю новый маршрут.

```text
ExecutionId = E-142
Subject     = Operator-17
World       = Factory-A
Object      = Vehicle-42
```

Команда проходит через несколько частей системы.

```text
API                 E-142
Transport Module    E-142
Database            E-142
Event Publisher     E-142
Projection Worker   E-142
```

Теперь все сигналы можно собрать в одну историю исполнения.

---

## Три основных сигнала

Основой наблюдаемости являются три взаимодополняющих типа телеметрии.

### Логи

Отвечают на вопрос:

> Что конкретно произошло?

### Метрики

Отвечают:

> Как система ведёт себя в целом?

### Трассировки

Отвечают:

> Как конкретное исполнение прошло через систему?

```text
                Observability
                     │
        ┌────────────┼────────────┐
        ▼            ▼            ▼
       Logs        Metrics       Traces
       что?        сколько?       где?
```

Ни один из этих сигналов не заменяет остальные.

---

## Наблюдаемость должна быть встроенной

Диагностические сигналы нельзя добавлять только после появления проблем.

Новый модуль, интеграция или единица развёртывания должны сразу определять:

- какие операции необходимо наблюдать;
- какие ошибки важны;
- какие задержки измеряются;
- какие зависимости отслеживаются;
- какие признаки деградации существуют.

---

## Пример

Добавляется новая интеграция камер.

Помимо функционального контракта необходимо заранее определить:

```text
camera.integration.requests
camera.integration.errors
camera.integration.duration
camera.integration.last_success
camera.integration.connected_devices
```

Тогда при сбое не придётся сначала изменять приложение только для того, чтобы понять причину ошибки.

---

## Наблюдаемость не должна зависеть от одного инструмента

Архитектура не должна определяться конкретным продуктом мониторинга.

```text
Application
    │
    ▼
Observability Contracts
    │
    ▼
Telemetry Adapter
    │
    ▼
Concrete Platform
```

Технология сбора и хранения телеметрии может меняться.

Смысл сигналов должен оставаться стабильным.

---

## Стоимость наблюдаемости

Телеметрия имеет стоимость.

Она потребляет:

- процессорное время;
- сеть;
- хранилище;
- деньги;
- внимание инженеров.

Поэтому цель — не собрать максимально возможное количество данных.

Цель — собрать достаточные данные для понимания поведения системы.

---

## Пример

Координаты автомобилей поступают десять раз в секунду.

Записывать отдельный подробный log на каждую координату для тысячи автомобилей может быть бессмысленно.

```text
1000 vehicles
× 10 updates/sec
= 10 000 log records/sec
```

Вместо этого могут использоваться:

- агрегированные метрики;
- sampling;
- логирование ошибок и аномалий;
- трассировка отдельных исполнений.

Наблюдаемость не должна сама становиться причиной деградации платформы.

---

## Практическое значение

Для любой новой функциональности разработчик должен уметь ответить:

```text
Как понять, что функция работает?
          │
          ▼
Как понять, что она деградирует?
          │
          ▼
Как найти конкретную ошибку?
          │
          ▼
Как связать её с исполнением?
          │
          ▼
Как определить затронутый мир или объект?
```

Если ответы требуют воспроизводить проблему вручную в production, наблюдаемость недостаточна.

---

## Инварианты наблюдаемости

Наблюдаемость обязана соблюдать следующие правила.

- Операционная телеметрия не является Domain State.
- Значимые исполнения должны быть коррелируемыми между архитектурными границами.
- Логи, метрики и трассировки дополняют друг друга.
- Наблюдаемость проектируется вместе с функциональностью, а не после сбоя.
- Телеметрия не должна требовать знания внутренностей потребителем сигнала.
- Технология хранения телеметрии не определяет архитектурный смысл сигналов.
- Система должна оставаться диагностируемой при распределённом исполнении.
- Наблюдаемость не должна создавать недопустимую нагрузку на рабочую систему.
- Секреты и чувствительные данные не должны бесконтрольно попадать в телеметрию.

---

## Архитектурное значение

Наблюдаемость превращает распределённую архитектуру из набора работающих процессов в систему, поведение которой можно объяснить.

```text
Execution
   │
   ▼
Telemetry
   │
   ▼
Observation
   │
   ▼
Explanation
```

Без неё ошибка существует только как симптом.

С ней появляется возможность установить причинную цепочку.

---

## Заключение

Для связи логов, метрик и трассировок необходимо определить общий контекст наблюдения.

Если каждый сервис использует собственные идентификаторы и не передаёт контекст дальше, сигналы невозможно собрать в одну историю.

Поэтому следующим шагом является определение **контекста наблюдения и корреляции**.
