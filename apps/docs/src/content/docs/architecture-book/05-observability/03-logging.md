# Логирование

## Статус

Accepted

---

## Введение

Логи позволяют исследовать конкретные факты работы системы.

Они особенно полезны, когда необходимо понять:

- какое решение принял компонент;
- почему операция завершилась ошибкой;
- какие внешние зависимости участвовали;
- какой этап исполнения был достигнут.

Однако бесконтрольное логирование быстро превращается в поток текста, который сложно анализировать.

Поэтому логи «Призмы» должны быть структурированными и семантически осмысленными.

---

## Структурированный лог

Лог должен представлять событие работы системы как набор полей, а не как строку, предназначенную только для человека.

Плохо:

```text
Failed to update camera 42 because provider returned 503 after 1821 ms
```

Лучше концептуально:

```text
message       = Camera provider request failed
cameraId      = 42
provider      = ProviderA
statusCode    = 503
durationMs    = 1821
traceId       = T-91
executionId   = E-12
```

Текст остаётся полезным человеку.

Структура делает сигнал пригодным для поиска и анализа.

---

## Уровни логирования

Уровень отражает значимость записи.

### Debug

Подробные данные для диагностики разработки и сложных случаев.

### Information

Ожидаемые значимые этапы работы.

### Warning

Необычная ситуация, из которой система смогла восстановиться или продолжить работу.

### Error

Операция завершилась ошибкой или часть функциональности потеряна.

### Critical

Система или критическая часть платформы не способна продолжать нормальную работу.

Уровень не должен использоваться как декоративная метка.

---

## Пример

GPS-провайдер один раз прислал дубликат сообщения.

```text
Warning
Duplicate external message ignored
```

Provider полностью недоступен:

```text
Error
GPS integration unavailable
```

Основное хранилище недоступно и команды не могут исполняться:

```text
Critical
Authoritative storage unavailable
```

---

## Не логировать каждую успешную мелочь

Высокочастотные операции не должны автоматически создавать подробный Information log на каждый пакет.

```text
VehiclePosition #1
VehiclePosition #2
VehiclePosition #3
...
```

Для потоковых данных чаще подходят метрики и sampling.

Логирование должно сохранять полезный сигнал среди шума.

---

## Пример

Тысяча автомобилей передаёт координаты десять раз в секунду.

Вместо 10 000 Information logs в секунду:

```text
vehicle_position_updates_total
vehicle_position_update_errors_total
vehicle_position_processing_duration
```

А подробный log создаётся при:

- ошибке формата;
- неизвестной Identity;
- аномальной задержке;
- нарушении ограничения.

---

## Логи и Domain Events

Domain Event не должен существовать только как log.

```text
VehicleRouteAssigned
```

является частью истории цифрового мира.

```text
Published VehicleRouteAssigned event in 12ms
```

является диагностической записью.

Потеря второго не должна уничтожить первый.

---

## Логи ошибок

Ошибка должна логироваться там, где имеется достаточный контекст для её интерпретации.

Не следует логировать одну ошибку на каждом уровне только потому, что exception проходит через стек.

```text
Storage logs error
Service logs same error
API logs same error
Gateway logs same error
```

Одна проблема превращается в четыре независимые ошибки.

Предпочтительно иметь один основной диагностический сигнал и trace, показывающий путь ошибки.

---

## Пример

Camera Adapter получает timeout.

```text
Camera Adapter
   │
   └── Error: provider timeout
```

Верхние уровни могут добавить статус span и вернуть контрактную ошибку без повторного полного логирования того же исключения.

---

## Исключения

Лог исключения должен содержать достаточно информации для диагностики, но не раскрывать чувствительные данные.

Необходимо сохранять:

- тип ошибки;
- безопасное сообщение;
- stack trace там, где уместно;
- correlation context;
- релевантные идентификаторы.

---

## Чувствительные данные

В логи запрещено бесконтрольно записывать:

- токены;
- пароли;
- ключи API;
- cookies;
- полные payload защищённых документов;
- персональные данные без необходимости.

```text
Request Authorization: Bearer ...   X
```

Секрет, попавший в централизованный log storage, становится значительно сложнее удалить и контролировать.

---

## Логи интеграций

Интеграционный адаптер должен позволять связать внутреннюю ошибку с внешним запросом.

```text
traceId            = T-51
externalRequestId  = provider-991
provider           = CameraProviderA
result             = timeout
```

Но внутренние модули не должны зависеть от формата этих логов.

---

## Логи жизненного цикла

Единицы развёртывания должны создавать понятные сигналы о собственном жизненном цикле:

```text
Application starting
Configuration loaded
Dependencies initialized
Application ready
Shutdown requested
Shutdown completed
```

Это помогает отличать предметную ошибку от перезапуска или проблем инфраструктуры.

---

## Практическое значение

Хорошая диагностическая запись должна отвечать минимум на несколько вопросов:

```text
Что произошло?
Где произошло?
К какому исполнению относится?
Что было затронуто?
Каков результат?
```

Если для поиска ошибки инженер вынужден grep-ить случайные текстовые строки, структура логирования недостаточна.

---

## Инварианты логирования

- Производственные логи должны быть структурированными.
- Значимые записи должны содержать корреляционный контекст.
- Один технический сбой не должен бесконтрольно логироваться на каждом уровне.
- Domain Events не заменяются логами.
- Высокочастотные успешные операции не должны создавать неконтролируемый поток записей.
- Секреты и чувствительные данные не логируются без явной необходимости и защиты.
- Уровень записи должен соответствовать её операционной значимости.
- Логи не являются авторитетным хранилищем состояния цифрового мира.

---

## Заключение

Лог позволяет исследовать отдельный факт.

Но для понимания поведения системы в целом необходимо видеть частоту ошибок, нагрузку, задержки и насыщение ресурсов.

Для этого используются **метрики**.
