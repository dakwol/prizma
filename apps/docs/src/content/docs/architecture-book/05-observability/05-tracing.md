# Распределённая трассировка

## Статус

Accepted

---

## Введение

В распределённой системе ошибка редко находится там, где пользователь увидел её симптом.

Запрос может провести большую часть времени во внешней интеграции.

Команда может успешно завершиться, но проекция обновиться значительно позже.

Событие может несколько раз переходить между очередями и обработчиками.

Трассировка показывает путь конкретного исполнения через систему.

---

## Trace

Trace представляет связанную историю выполнения одной технической операции.

Он состоит из spans.

```text
Trace T-100
   │
   ├── API request
   ├── Authorization
   ├── Transport command
   ├── Storage write
   └── Event publish
```

---

## Span

Span описывает отдельную операцию внутри trace.

Он имеет:

- начало;
- завершение;
- длительность;
- результат;
- атрибуты;
- связь с parent span.

```text
API Request [---------------------------]
     Transport [----------------]
          Storage [----]
          Event Publish [--]
```

Так становится видно распределение времени.

---

## Пример

Команда изменения камеры занимает 3.4 секунды.

Trace показывает:

```text
API                    3400 ms
└── Authorization         8 ms
└── Camera Command     3370 ms
    └── Provider Call  3310 ms
    └── State Update     22 ms
```

Проблема находится не в API и не в хранилище.

Практически всё время занял внешний поставщик камеры.

---

## Трассировка асинхронных процессов

Асинхронная граница не должна уничтожать причинность.

```text
Command Trace
     │
     ▼
Event
     │
     ├────────► Projection Trace
     └────────► Analytics Trace
```

Реализация может продолжить тот же trace или создать связанные traces.

Архитектурное требование — сохранить причинную связь.

---

## Пример

```text
AssignVehicleRoute
      │
      ▼
VehicleRouteAssigned
      │
      ├── MapProjectionUpdate
      └── AnalyticsRouteUpdate
```

Инженер должен иметь возможность перейти от исходной команды к последующим обработчикам.

---

## Span boundaries

Не каждая функция должна становиться span.

Span полезен для архитектурно значимых или потенциально дорогих операций:

- входящий запрос;
- команда;
- обращение к storage;
- публикация сообщения;
- обработка сообщения;
- внешний вызов;
- важная вычислительная операция.

Слишком подробная трассировка создаёт шум и стоимость.

---

## Атрибуты span

Span может содержать безопасный контекст:

```text
module = cameras
operation = ChangeCameraDirection
world = W-1
result = timeout
provider = A
```

Уникальные Object IDs могут быть полезны для диагностики trace, где проблема высокой metric cardinality отсутствует в той же форме.

---

## Ошибки в trace

Span должен отражать результат операции.

```text
Provider Call
   │
   └── status = error
       error.type = Timeout
```

При этом ошибка не обязана несколько раз логироваться на каждом parent span.

Trace уже показывает распространение результата вверх.

---

## Sampling

Хранить полный trace для каждого высокочастотного события может быть слишком дорого.

Поэтому допускается sampling.

```text
100 000 traces
      │
      ▼
 sampling
      │
      ▼
 5 000 stored
```

Однако ошибки и аномально медленные операции могут иметь повышенный приоритет сохранения.

---

## Пример

Обновления координат автомобилей происходят постоянно.

Обычные успешные traces могут сохраняться выборочно.

Но trace, где:

```text
processing_duration > threshold
```

или:

```text
result = error
```

желательно сохранить полностью.

---

## Frontend tracing

Путь пользователя начинается не обязательно на backend.

Для важных пользовательских операций полезно связывать клиентскую и серверную части.

```text
User Click
    │
    ▼
Frontend Operation
    │
    ▼
Network Request
    │
    ▼
Backend Trace
```

Это позволяет различать:

- задержку UI;
- сеть;
- backend;
- внешнюю интеграцию.

---

## Пример

Карта открывает карточку автомобиля за две секунды.

Backend отвечает за 70 ms.

Trace показывает:

```text
Frontend render       1500 ms
Network                300 ms
Backend                 70 ms
```

Оптимизация backend не решит проблему.

---

## Практическое значение

Для критичной операции должна существовать возможность увидеть:

```text
Начало
  │
  ▼
Все значимые границы
  │
  ▼
Внешние зависимости
  │
  ▼
Асинхронные продолжения
  │
  ▼
Результат
```

Трассировка особенно важна после выделения отдельных deployment units.

---

## Инварианты трассировки

- Trace должен сохранять причинный путь исполнения.
- Значимые процессные и сетевые границы должны быть видимыми.
- Асинхронность не должна уничтожать возможность корреляции.
- Span создаётся для полезной архитектурной операции, а не для каждой функции.
- Ошибки должны отражаться в соответствующих spans.
- Sampling не должен делать критичные проблемы полностью ненаблюдаемыми.
- Чувствительные данные не должны бесконтрольно попадать в span attributes.
- Трассировка не является Domain History.

---

## Заключение

Логи, метрики и трассировки позволяют исследовать работающую систему.

Но система также должна уметь прямо сообщить оркестратору и другим компонентам, способна ли она сейчас принимать работу.

Для этого используются **health и readiness signals**.
