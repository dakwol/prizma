# Состояние и готовность компонентов

## Статус

Accepted

---

## Введение

Наблюдаемость используется не только инженерами.

Инфраструктуре также необходимо понимать, способен ли конкретный процесс продолжать работу.

Для этого единицы развёртывания предоставляют сигналы состояния и готовности.

Важно различать несколько разных вопросов.

---

## Liveness

Liveness отвечает:

> Процесс жив и способен продолжать собственное выполнение?

Если liveness потерян, процесс обычно необходимо перезапустить.

```text
Process
  │
  ├── alive   ✔
  └── dead    X
```

---

## Readiness

Readiness отвечает:

> Способен ли процесс сейчас принимать новую рабочую нагрузку?

Процесс может быть жив, но не готов.

```text
Process alive ✔
Database unavailable
      │
      ▼
Ready X
```

Это не обязательно требует немедленного перезапуска.

---

## Пример

Prizma API запущен, event loop работает.

Но основное хранилище временно недоступно.

```text
Liveness  = healthy
Readiness = unhealthy
```

Оркестратор может временно перестать направлять новые команды на этот экземпляр, не уничтожая процесс.

---

## Startup

Некоторым компонентам требуется время на инициализацию.

Например:

- загрузка конфигурации;
- построение индекса;
- подключение к equipment;
- восстановление локального состояния.

До завершения startup процесс не должен считаться готовым.

```text
Start
 │
 ▼
Initialization
 │
 ▼
Ready
```

---

## Health не означает отсутствие ошибок

Сервис может иметь отдельные ошибочные запросы и при этом оставаться здоровым.

```text
1000 requests
   │
   ├── 995 success
   └── 5 validation errors
```

Validation errors не делают deployment unit unhealthy.

Health описывает способность компонента выполнять свою функцию, а не успех каждой операции.

---

## Зависимости health checks

Не каждую внешнюю зависимость следует включать в liveness.

Иначе сбой Provider A вызовет перезапуск здорового приложения.

```text
Provider A X
    │
    ▼
Application restart
    │
    ▼
Provider A still X
```

Получается бесполезный restart loop.

---

## Пример

Camera Provider недоступен.

Основная платформа продолжает работать.

```text
Prizma API       healthy
Transport        healthy
Camera Provider  unavailable
Camera feature   degraded
```

Глобальный liveness приложения остаётся healthy.

Состояние интеграции отражается отдельным сигналом.

---

## Частичная деградация

Сложная платформа редко бывает только полностью healthy или полностью unavailable.

Необходимо уметь отражать деградацию отдельных возможностей.

```text
Platform
  │
  ├── Commands       healthy
  ├── Maps           healthy
  ├── Analytics      degraded
  └── Camera Streams unavailable
```

Такой статус значительно полезнее одного общего boolean.

---

## Readiness и локальная зависимость

В readiness включаются зависимости, без которых конкретный экземпляр действительно не может выполнять предназначенную ему работу.

Например, worker проекций без доступа к очереди событий не способен выполнять основную функцию.

```text
Projection Worker
      │
      ├── Queue ✔
      └── Projection Store ✔
           │
           ▼
         Ready
```

---

## Health endpoint не является мониторингом

Health signal сообщает текущее агрегированное состояние.

Он не заменяет:

- метрики;
- traces;
- logs;
- alerting.

```text
Health = unhealthy
```

говорит, что проблема существует.

Observability signals объясняют почему.

---

## Практическое значение

Для каждой deployment unit необходимо определить:

```text
Что означает alive?
      │
      ▼
Что необходимо для ready?
      │
      ▼
Какие зависимости критичны?
      │
      ▼
Какие возможности могут деградировать отдельно?
```

Нельзя автоматически включать все внешние зависимости во все health checks.

---

## Инварианты состояния компонентов

- Liveness и readiness имеют разный смысл.
- Живой процесс может временно быть не готов к нагрузке.
- Ошибка внешней необязательной зависимости не должна автоматически делать весь процесс dead.
- Health checks не заменяют telemetry.
- Частичная деградация должна быть наблюдаемой там, где платформа способна продолжать работу.
- Startup должен быть отделён от устойчивого ready state.
- Проверка здоровья не должна сама создавать существенную нагрузку или побочные эффекты.

---

## Заключение

Health signals говорят, способен ли компонент работать сейчас.

Но эксплуатационной команде также необходимо понимать, насколько хорошо система выполняет обещанный уровень сервиса на протяжении времени.

Для этого используются **индикаторы и цели уровня сервиса**.
