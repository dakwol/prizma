# Оповещения

## Статус

Accepted

---

## Введение

Метрики могут содержать тысячи временных рядов.

Логи — миллионы записей.

Инженер не может постоянно наблюдать за всеми сигналами вручную.

Alerting автоматически определяет ситуации, требующие внимания.

Главное требование к alert — он должен быть основанием для действия.

---

## Что такое alert

Alert — уведомление о значимом состоянии системы, требующем оценки или вмешательства.

```text
Telemetry
   │
   ▼
Condition
   │
   ▼
Alert
   │
   ▼
Human / Automation
   │
   ▼
Action
```

Если после alert никто не знает, что делать, его ценность сомнительна.

---

## Alert не равен Error log

Каждая ошибка не должна автоматически создавать alert.

Например, пользователь отправил недопустимую команду.

```text
ValidationError
```

Это ожидаемый результат системы.

Он может быть отражён в метрике и trace, но не требует ночного уведомления инженера.

---

## Пример

Одна камера недоступна пять секунд.

Возможно, вмешательство не требуется.

Но если:

```text
30% камер одного объекта недоступны 10 минут
```

это уже может быть операционно значимым событием.

Alert должен отражать влияние, а не каждую техническую ошибку.

---

## Симптомы важнее причин

Для основных alerts предпочтительно наблюдать пользовательский симптом.

Например:

```text
Command success rate below SLO
```

лучше как основной сигнал, чем:

```text
CPU > 80%
```

Высокий CPU может быть нормальным.

Но он полезен как диагностический сигнал после срабатывания симптомного alert.

---

## Пример

```text
camera_control_latency p95 > objective
```

Alert сообщает о реальной деградации управления камерой.

Дальше инженер смотрит:

```text
CPU
network latency
provider duration
connection pool
```

для поиска причины.

---

## Severity

Alerts могут иметь разные уровни срочности.

Например:

### Critical

Требуется немедленное вмешательство.

### Warning

Наблюдается деградация, но система продолжает выполнять основную функцию.

### Informational

Состояние важно для эксплуатации, но не требует немедленного реагирования.

Severity должна отражать влияние, а не эмоциональность сообщения.

---

## Alert fatigue

Если alerts срабатывают слишком часто и не требуют действия, инженеры перестают им доверять.

```text
100 alerts/day
      │
      ▼
ignored alerts
      │
      ▼
real incident missed
```

Количество сигналов не является показателем качества alerting.

---

## Устойчивое условие

Кратковременный spike не всегда является проблемой.

Alert может учитывать продолжительность.

```text
Error rate high
     │
     ├── 5 sec  → observe
     └── 10 min → alert
```

Конкретное окно зависит от природы функции.

---

## Пример

Projection lag на несколько секунд вырос после deployment и быстро восстановился.

Не обязательно уведомлять инженера.

Но:

```text
projection_lag > 5 min for 15 min
```

означает устойчивую деградацию.

---

## Группировка

Одна инфраструктурная проблема может вызвать сотни одинаковых симптомов.

Alerting должен по возможности группировать связанные сигналы.

```text
Database unavailable
    │
    ├── API errors
    ├── Worker errors
    ├── Projection errors
    └── Command errors
```

Инженеру полезнее одна инцидентная картина, чем сто уведомлений.

---

## Контекст alert

Alert должен содержать минимум информации для начала расследования:

```text
what happened
affected component
severity
current value
expected value
time window
links to dashboards/traces/logs
```

Без контекста уведомление превращается в приглашение начать поиск с нуля.

---

## Пример

Плохо:

```text
ALERT: ERROR RATE HIGH
```

Лучше концептуально:

```text
Camera Control SLO violation
World: Factory-A
Success rate: 91.4%
Objective: 99.5%
Window: 10m
Started: 17:42
```

---

## Alerts внешних зависимостей

Необходимо различать:

- внутреннюю деградацию;
- внешнюю деградацию.

```text
Camera Provider unavailable
```

может иметь отдельный alert и показывать затронутые функции.

Это ускоряет определение ответственности.

---

## Deployment correlation

Alerts желательно связывать с изменениями deployment.

```text
17:00 deploy v42
17:04 error rate ↑
17:06 alert
```

Это не доказывает причинность, но значительно ускоряет расследование.

---

## Практическое значение

Перед созданием alert необходимо ответить:

```text
Какой реальный ущерб означает условие?
        │
        ▼
Нужно ли действие человека?
        │
        ▼
Насколько срочно?
        │
        ▼
Как начать диагностику?
        │
        ▼
Когда alert считается resolved?
```

Если действия нет, возможно, нужен dashboard, а не alert.

---

## Инварианты alerting

- Alert должен быть actionable.
- Каждая отдельная ошибка не создаёт alert автоматически.
- Пользовательские симптомы предпочтительнее случайных инфраструктурных thresholds для основных alerts.
- Severity отражает влияние и срочность.
- Кратковременный шум должен фильтроваться там, где это допустимо.
- Связанные alerts должны группироваться по возможности.
- Alert должен содержать контекст для начала расследования.
- Alerting не должен создавать постоянный шум, которому перестают доверять.

---

## Заключение

Alert сообщает, что произошло значимое отклонение.

После этого начинается расследование: необходимо определить масштаб, причинную цепочку, затронутые компоненты и безопасный способ восстановления.

Этому посвящена следующая страница — **диагностика и расследование инцидентов**.
