# Индикаторы и цели уровня сервиса

## Статус

Accepted

---

## Введение

Фраза:

> система работает нормально

не является измеримым критерием.

Для критичных возможностей необходимо заранее определить, что означает приемлемая работа.

Для этого используются Service Level Indicators и Service Level Objectives.

---

## Service Level Indicator

SLI — измеримый показатель качества конкретной пользовательской или системной возможности.

Например:

```text
доля успешных команд
latency запросов
актуальность проекции
доступность видеопотока
```

SLI должен измерять результат, имеющий реальный смысл для потребителя.

---

## Service Level Objective

SLO задаёт целевое значение SLI за определённый период.

Например концептуально:

```text
99.9% команд изменения маршрута
успешно завершаются за месяц
```

или:

```text
95% обновлений карты
отстают от источника истины менее чем на 1 секунду
```

Конкретные числа определяются требованиями продукта и эксплуатации.

---

## Пример

Backend API доступен 99.99% времени.

Но Projection Worker отстаёт на двадцать минут.

Технически API healthy.

Для оператора карта почти бесполезна.

Поэтому хороший SLI может измерять:

```text
projection_freshness
```

а не только:

```text
http_up
```

---

## Пользовательский результат важнее внутреннего компонента

SLO желательно строить вокруг возможностей, воспринимаемых пользователем или важным потребителем.

```text
User Action
    │
    ▼
Desired Result
    │
    ▼
SLI
```

Не вокруг каждого внутреннего класса или сервиса.

---

## Пример

Для управления камерой пользователю важны:

- доступность команды;
- время выполнения;
- корректный результат.

Поэтому возможные indicators:

```text
camera_control_success_rate
camera_control_latency
```

CPU Camera Service сам по себе не является SLI пользовательского качества.

Он является диагностической метрикой.

---

## Error budget

Если SLO допускает определённую долю неуспешных операций, эта доля образует error budget.

```text
Allowed reliability loss
        │
        ▼
   Error Budget
```

Он позволяет принимать инженерные решения не на основе требования «никогда не ошибаться», а на основе измеримого качества.

---

## Пример

Если функция уже значительно превышает требуемый уровень надёжности, команда может безопаснее инвестировать в развитие.

Если error budget почти исчерпан, приоритет смещается на устойчивость и устранение деградации.

---

## Несколько классов возможностей

Не все части «Призмы» требуют одинакового SLO.

Например:

```text
Command Execution      высокий приоритет
Operator Map           высокий приоритет
Analytics Report       средний приоритет
Optional Extension     более низкий приоритет
```

Одинаковые требования ко всему увеличивают стоимость без необходимости.

---

## SLO не является SLA

SLO — внутренняя инженерная цель.

SLA — внешнее договорное обязательство.

Архитектурная книга определяет необходимость измеримого качества, но не фиксирует коммерческие обязательства.

---

## Измерение с точки зрения потребителя

Важно выбирать точку измерения корректно.

Backend может считать команду завершённой после записи состояния.

Пользователь может считать её завершённой только после отображения результата.

```text
Command committed
      │
      ▼
Synchronization
      │
      ▼
Projection updated
      │
      ▼
UI visible
```

Это разные latency indicators.

---

## Пример

```text
execution_latency       = 40 ms
projection_latency      = 120 ms
user_visible_latency    = 320 ms
```

Все значения корректны.

Они измеряют разные границы.

---

## Практическое значение

Для критичной возможности необходимо определить:

```text
Кто потребитель?
      │
      ▼
Какой результат ему важен?
      │
      ▼
Как это измерить?
      │
      ▼
Какой уровень считается приемлемым?
      │
      ▼
За какой период?
```

Без этих ответов alerting и capacity planning будут опираться на произвольные thresholds.

---

## Инварианты SLI и SLO

- SLI должен измерять значимое качество сервиса.
- SLO должен иметь измеримый показатель и временное окно.
- Не все возможности обязаны иметь одинаковый SLO.
- Внутренняя техническая метрика не становится SLI автоматически.
- Измеряемая граница должна быть определена явно.
- SLO не следует смешивать с договорным SLA.
- Цели должны пересматриваться при изменении продуктовых требований.

---

## Заключение

Когда ожидаемое качество определено, система может автоматически обнаруживать значимые отклонения.

Следующая задача — сделать так, чтобы инженеры получали сигнал именно тогда, когда требуется действие.

Эту задачу решает **alerting**.
