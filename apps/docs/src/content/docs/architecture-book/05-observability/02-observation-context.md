# Контекст наблюдения и корреляция

## Статус

Accepted

---

## Введение

В распределённой системе одно действие редко выполняется внутри одного компонента.

Команда может пройти через API, модуль, очередь, worker, интеграционный адаптер и внешний сервис.

Каждый из этих компонентов создаёт собственную телеметрию.

Без общего контекста получится несколько независимых историй.

Корреляция объединяет их в одно наблюдаемое исполнение.

---

## Что такое контекст наблюдения

Контекст наблюдения — набор идентификаторов и атрибутов, позволяющий определить, к какому исполнению относится сигнал.

```text
User Action
    │
    ▼
Observation Context
    │
    ├── TraceId
    ├── ExecutionId
    ├── SubjectId
    ├── WorldId
    └── CorrelationId
```

Контекст сопровождает исполнение при прохождении архитектурных границ.

---

## Trace ID

Trace ID идентифицирует одну распределённую трассировку.

Все операции, относящиеся к одному техническому пути исполнения, могут быть связаны через него.

```text
Trace T-901
   │
   ├── API
   ├── Authorization
   ├── Transport
   ├── Database
   └── Event Publish
```

---

## Execution ID

Execution ID связывает телеметрию с архитектурным Execution Model «Призмы».

Trace и Execution не обязаны быть одним понятием.

Например, одно предметное исполнение может вызвать несколько асинхронных trace.

```text
Execution E-42
   │
   ├── Trace T-1   synchronous command
   ├── Trace T-2   projection update
   └── Trace T-3   external synchronization
```

Такое разделение сохраняет предметную связь даже после разрыва технической цепочки вызовов.

---

## Пример

Оператор назначает маршрут автомобилю.

```text
Execution E-42
      │
      ▼
Trace T-1
API → Transport → Storage
      │
      ▼
VehicleRouteAssigned
      │
      ├────────► Trace T-2 → Map Projection
      └────────► Trace T-3 → Analytics
```

Технические traces разные.

Но все они относятся к одному Execution.

---

## Correlation ID

Correlation ID используется для связывания сообщений, операций или процессов, относящихся к общей бизнес-цепочке.

Он особенно полезен, когда один процесс длится дольше одного Execution.

---

## Пример

Сценарий въезда автомобиля включает несколько исполнений:

```text
Correlation C-77
      │
      ├── Execution E-100  RegisterEntry
      ├── Execution E-101  StartCameraObservation
      └── Execution E-102  OpenAccessPoint
```

Теперь можно исследовать сценарий целиком, не смешивая отдельные исполнения.

---

## Предметный контекст

Технических идентификаторов недостаточно для диагностики.

Телеметрия должна позволять при необходимости связать операцию с предметным контекстом:

- World Identity;
- Object Identity;
- Relation Identity;
- Scenario Identity;
- Subject Identity.

```text
Trace
 │
 ├── World = W-1
 ├── Object = Vehicle-42
 └── Subject = Operator-17
```

При этом чувствительные данные не должны дублироваться без необходимости.

---

## Пример

Инженер видит рост ошибок команды `ChangeCameraDirection`.

Без предметного контекста известно только количество ошибок.

С контекстом можно определить:

```text
World A     1% errors
World B    38% errors
```

А затем:

```text
World B
   │
   └── Camera Provider X
```

Проблема оказывается не глобальной, а связанной с конкретной интеграцией.

---

## Контекст должен передаваться через сообщения

Асинхронная коммуникация не должна обрывать корреляцию.

```text
Producer
   │
   ▼
Message
   │
   ├── payload
   └── observation context
            │
            ▼
         Consumer
```

Получатель создаёт собственную локальную операцию, сохраняя связь с причиной.

---

## Пример

```text
VehiclePositionChanged
TraceId         = T-121
ExecutionId     = E-900
CorrelationId   = C-44
```

Projection Worker получает событие и создаёт новый span.

```text
Trace T-121
   │
   └── ProjectionUpdate
```

Или создаёт новый trace с причинной ссылкой, если асинхронная модель этого требует.

Главное — причинная связь не теряется.

---

## Контекст внешних систем

Внешняя система может иметь собственные request ID или event ID.

Они должны сохраняться как внешний контекст, но не заменять внутренние идентификаторы «Призмы».

```text
Provider RequestId
       │
       ▼
Integration Adapter
       │
       ├── ExternalRequestId
       └── Prizma TraceId
```

---

## Пример

Камера возвращает ошибку с:

```text
providerRequestId = req-9912
```

Внутренний trace:

```text
traceId = T-728
```

Лог интеграции сохраняет оба значения.

Это позволяет исследовать проблему как со стороны «Призмы», так и со стороны поставщика.

---

## Контекст не должен использоваться как глобальное хранилище

Нельзя помещать в observation context произвольные данные только потому, что их удобно получить в любом месте.

Контекст должен оставаться компактным и стабильным.

Плохо:

```text
Context
 ├── full user object
 ├── entire vehicle state
 ├── access token
 └── camera credentials
```

Лучше:

```text
Context
 ├── SubjectId
 ├── ObjectId
 ├── WorldId
 └── TraceId
```

---

## Кардинальность атрибутов

Не все атрибуты безопасно использовать в метриках.

Например, `ObjectId` полезен в trace и log, но создание отдельной metric series для каждого автомобиля может привести к огромной кардинальности.

```text
100 000 ObjectId
      │
      ▼
100 000 metric series
```

Контекст сигнала должен учитывать тип телеметрии.

---

## Безопасность контекста

Наблюдаемость не должна становиться обходным каналом доступа к данным.

В telemetry context запрещено бесконтрольно помещать:

- access tokens;
- пароли;
- секретные ключи;
- полные персональные данные;
- содержимое защищённых документов.

При необходимости используются безопасные идентификаторы и маскирование.

---

## Практическое значение

При создании новой точки коммуникации необходимо определить:

```text
Принимаем контекст?
      │
      ▼
Продолжаем trace?
      │
      ▼
Сохраняем ExecutionId?
      │
      ▼
Передаём причинную связь?
      │
      ▼
Добавляем безопасный domain context?
```

Если после перехода через границу невозможно связать операцию с источником, корреляция нарушена.

---

## Инварианты контекста наблюдения

- Значимые распределённые операции должны иметь корреляционный контекст.
- Контекст должен пересекать разрешённые процессные и сетевые границы.
- Технический Trace ID и архитектурный Execution ID могут иметь разные жизненные циклы.
- Асинхронное выполнение не должно уничтожать причинную связь.
- Внешние идентификаторы не заменяют внутренний контекст «Призмы».
- Контекст должен быть компактным.
- Чувствительные данные не должны попадать в контекст без необходимости.
- Атрибуты высокой кардинальности должны использоваться осознанно.

---

## Заключение

После определения общего контекста система может создавать отдельные наблюдаемые сигналы.

Самым детальным текстовым описанием происходящего являются **структурированные логи**.
