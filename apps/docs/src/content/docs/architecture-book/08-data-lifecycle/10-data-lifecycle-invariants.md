# Инварианты жизненного цикла данных

## Статус

Accepted

---

## Основной принцип

```text
Data has meaning
      │
      ▼
Meaning defines lifecycle
```

Не объём диска определяет семантику данных.

Сначала определяется смысл и ценность информации, затем storage policy.

---

## Обязательные правила

### Авторитетное и производное состояние различаются

```text
Authoritative → protect
Projection    → rebuild
Cache         → recreate
```

### Current и Historical State имеют разные access patterns

Текущая работа не требует постоянного сканирования всей истории.

### Retention определяется по классу данных

Одна глобальная policy для всей платформы не используется.

### Телеметрия имеет отдельный lifecycle

Высокочастотные observations не превращаются автоматически в Domain Versions.

### Storage tier соответствует частоте использования

```text
Hot → Warm → Cold
```

если такая градация экономически и технически оправдана.

### Архив остаётся читаемым

Формат архивных данных versioned и проверяем.

### Файлы имеют identity

Domain objects ссылаются на File Identity, а не на случайный storage URL.

### Logical deletion отличается от physical erasure

Прекращение существования активного объекта не требует автоматически уничтожать всю историю.

### Referential integrity сохраняется

Удаление не оставляет невалидных отношений.

### Backup учитывается при erasure

Нельзя обещать мгновенное физическое исчезновение данных, если backup policy этого не обеспечивает.

### Schema evolution контролируема

Долгоживущие данные остаются читаемыми после обновлений приложения.

### Большие миграции restartable

```text
Batch
Checkpoint
Resume
```

### Lifecycle operations наблюдаемы

Retention, archival, migration и deletion имеют progress и failure signals.

### Фоновые процессы ограничены ресурсами

Они не вытесняют основные пользовательские операции.

## Пример жизненного цикла телеметрии автомобиля

```text
Vehicle sends position
        │
        ▼
Raw telemetry
        │
        ├── current projection
        ├── realtime map
        └── historical storage
                 │
                 ▼
          retention boundary
                 │
          ┌──────┴──────┐
          │             │
      aggregate       archive
          │             │
          └──────┬──────┘
                 ▼
            cold history
                 │
                 ▼
          deletion policy
```

При этом сам автомобиль и его Domain History могут иметь совершенно другой lifecycle.

## Проверка нового типа данных

Перед добавлением необходимо ответить:

1. Кто владеет данными?
2. Являются ли они source of truth?
3. Как часто они создаются?
4. Как часто читаются?
5. Нужна ли полная история?
6. Каков retention?
7. Допустима ли aggregation?
8. Нужен ли archive?
9. Как данные удаляются?
10. Есть ли связанные файлы?
11. Как schema будет эволюционировать?
12. Как выполняется migration?
13. Как данные восстанавливаются?
14. Какие lifecycle metrics нужны?
15. Что произойдёт через несколько лет роста?

## Архитектурное значение

Data Lifecycle связывает время существования цифрового мира с физическим хранением информации.

```text
World changes
    │
    ▼
History grows
    │
    ▼
Lifecycle policies
    │
    ├── retain
    ├── aggregate
    ├── archive
    ├── migrate
    └── delete
```

Это позволяет истории расти управляемо, не превращая основной storage в бесконечный архив.
