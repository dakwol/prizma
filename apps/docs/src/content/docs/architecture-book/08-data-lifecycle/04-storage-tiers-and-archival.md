# Уровни хранения и архивирование

## Статус

Accepted

---

## Введение

Не все данные должны находиться в самом быстром хранилище.

Стоимость быстрого доступа оправдана только для информации, которая действительно используется часто.

---

## Storage tiers

```text
Hot
 │
 ▼
Warm
 │
 ▼
Cold
```

### Hot

Данные, необходимые для текущей работы.

### Warm

История, к которой обращаются периодически.

### Cold

Редко используемые данные, для которых допустимо более медленное получение.

---

## Пример

История перемещений автомобиля:

```text
Last 7 days       → Hot
Previous months   → Warm
Several years ago → Cold
```

Это только пример модели, а не фиксированная политика платформы.

---

## Архив остаётся доступным

Cold storage не означает потерю данных.

Пользовательский сценарий может выглядеть так:

```text
Historical request
       │
       ▼
Cold data required
       │
       ▼
Restore / fetch
       │
       ▼
Result
```

Такой запрос может иметь другой latency contract.

---

## Aggregation before archival

Высокочастотные данные могут агрегироваться перед долгосрочным хранением, если предметные требования допускают потерю исходной детализации.

```text
Raw positions
  │
  ▼
Aggregation
  │
  ▼
Historical route summary
```

Нельзя применять aggregation там, где исходные данные должны сохраняться.

---

## Archive format

Архивный формат должен быть:

- versioned;
- документирован;
- проверяем;
- восстанавливаем.

Дешёвый storage бесполезен, если через пять лет данные невозможно прочитать.

---

## Инварианты

- Storage tier соответствует частоте доступа.
- Архивирование не означает логическое удаление.
- Cold access имеет отдельный latency contract.
- Aggregation допускается только при разрешённой потере детализации.
- Archive format versioned и восстанавливаем.
- Перемещение между tiers наблюдаемо и повторяемо.

---

## Заключение

Отдельный класс быстрорастущих данных — телеметрия. Она требует собственной lifecycle-модели.
