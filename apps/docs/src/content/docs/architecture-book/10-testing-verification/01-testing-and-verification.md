# Тестирование и верификация

## Статус

Accepted

---

## Введение

Тесты нужны не для доказательства того, что код был написан.

Они нужны для доказательства того, что система сохраняет требуемые свойства.

Для «Призмы» особенно важны свойства цифрового мира:

- Domain Invariants;
- корректность переходов состояния;
- согласованность истории;
- безопасность доступа;
- совместимость контрактов;
- устойчивость к отказам;
- производительность;
- восстановимость.

---

## Основной принцип

```text
Architecture rule
      │
      ▼
Observable property
      │
      ▼
Verification
```

Архитектурное правило, которое невозможно проверить ни автоматически, ни эксплуатационно, со временем легко нарушить.

---

## Testing и Verification

Testing проверяет конкретное поведение.

Verification отвечает на более широкий вопрос:

> сохраняет ли система архитектурные гарантии?

```text
Unit tests
Integration tests
Contract tests
System tests
Load tests
Recovery tests
        │
        ▼
Architecture verification
```

---

## Пример

Правило:

> повтор одной команды не должен создавать второй предметный эффект.

Его недостаточно описать в документации.

Необходимо проверить:

```text
Command #42
   │
execute
   │
retry same Command #42
   │
   ▼
One Domain Effect
```

---

## Пирамида не является целью

Количество unit, integration и end-to-end tests не определяется универсальной пропорцией.

Тест выбирается по границе риска.

```text
Pure rule       → unit
Database logic  → integration
API contract    → contract/integration
Critical flow   → system
Failure mode    → resilience
```

---

## Production verification

Некоторые свойства невозможно полностью доказать до production:

- реальную capacity;
- внешние интеграции;
- сетевые условия;
- поведение долгоживущих процессов.

Поэтому verification продолжается после deployment через observability и controlled rollout.

---

## Инварианты

- Тесты проверяют свойства системы, а не внутреннюю структуру ради структуры.
- Domain Invariants имеют автоматическую проверку там, где это возможно.
- Тип теста выбирается по характеру риска.
- Критические архитектурные контракты проверяются на своих границах.
- Production observability является частью verification.
- Наличие большого количества тестов не считается доказательством корректности само по себе.

---

## Заключение

Основа цифрового мира — Domain Model.

Поэтому первая специализированная область проверки — Domain Invariants.
