# System и End-to-End Testing

## Статус

Accepted

---

## Введение

Некоторые ошибки видны только при прохождении полного пути.

```text
User
 │
Frontend
 │
API
 │
Domain
 │
Storage
 │
Realtime
 │
Frontend
```

Локальные тесты каждого звена не гарантируют правильность всей цепочки.

---

## Что проверяет E2E

E2E полезен для небольшого числа критических сценариев:

- создание объекта;
- изменение состояния;
- отображение результата;
- authorization boundary;
- realtime update;
- восстановление после reconnect.

---

## Пример

Оператор изменяет привязку камеры.

```text
UI command
   │
API
   │
Domain validation
   │
Commit
   │
Event
   │
Projection
   │
Realtime
   │
Updated UI
```

Тест подтверждает полный observable outcome.

---

## Почему не всё E2E

Полные тесты:

- медленнее;
- сложнее диагностируются;
- требуют больше инфраструктуры;
- чаще нестабильны.

Поэтому E2E не заменяет нижние уровни проверки.

---

## Stable assertions

Тест должен проверять смысл сценария, а не случайные детали интерфейса.

Плохо:

> третий `div` содержит нужный текст.

Лучше:

> карточка объекта показывает новое состояние.

---

## Deterministic setup

Сценарий должен иметь известное начальное состояние.

```text
Known world
   │
Action
   │
Expected world
```

---

## Инварианты

- E2E покрывает критические cross-component flows.
- Полные тесты не дублируют все варианты Domain Rules.
- Assertions ориентированы на пользовательский смысл.
- Test data setup воспроизводим.
- Нестабильность теста считается дефектом test system.
- Failure E2E должен быть диагностируем через observability artifacts.

---

## Заключение

Корректный сценарий при одном пользователе ещё не доказывает работу под реальной нагрузкой.

Следующая страница определяет performance testing.
